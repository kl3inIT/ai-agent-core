## 1. System Classification

**System Type:** Tool-Calling Multimodal Chat — Media-augmented user turns + transactional bulk-write tool over the Phase 11 mutation chain. Hybrid extension of an existing Conversational + RAG system (Phases 4–5) with a new multimodal input pathway (Phase 13) and a new bulk-write tool (Phase 13 extending Phase 11).

**Description:**
Enterprise users (CRM-style staff in Vietnamese + English locales) attach files (xlsx, pdf, docx, csv, png, jpg, …) to a chat turn. The file bytes flow into the LLM (Qwen3.6-35B-A3B, multimodal, 262K context, Apache 2.0 self-hostable) via Spring AI `Media` injected into the user message ON THE SEND TURN ONLY (matches `D:/DTH/jmix-crm` `AiAttachmentMediaResolver` pattern; `JdbcChatMemoryRepository` persists text only, so re-injection every turn is structurally avoided). The LLM acts on the file content using existing Phase 9–11 tools (`list_entities`, `describe_entity`, `find_records`, `create_record`, `update_record`, `add_related_record`, `remove_related_record`) plus a new `bulk_save_records(entityName, records[], idempotencyKey)` tool that persists multiple host entities in one audited `@Transactional` span with rollback-all semantics, reusing the entire Phase 11 chain (`LlmExposurePolicy` → `AccessManager` per-row + per-attribute → `AiMutationIntent` reservation once per batch → `MutationGuard` per row → `DataManager.save` → `AuditWriter.writeToolCall` once per batch). "Good" = LLM correctly maps xlsx columns to entity attributes, dispatches create vs update by `id`-presence, never bypasses Jmix security, and the assistant response cites the row count + a verify-link the user can audit.

**Critical Failure Modes:**
1. **Wrong-record creation from misinterpreted file content** — LLM reads xlsx column "Email" into `phone` field, calls `bulk_save_records` with malformed records → silent corruption of customer master data. Mitigation: per-attribute `EntityAttributeContext.canModify` + Bean Validation + rich tool description with FORMATS examples + per-row failure rolls back batch.
2. **Cross-user data leak via attached file** — User A attaches PDF containing user B's PII; LLM uses `find_records` to look up matching customer rows but Phase 9 RAG/data tools are user-scoped via Jmix `AccessManager` row policies. Failure mode: bypass would let LLM surface unauthorized rows. Mitigation: Phase 9 `LlmExposurePolicy` + `AccessManager` already gate this; TEST-16 + Phase 9 TEST-08 prompt-contract regression must remain green.
3. **Audit trail leak of raw PII through `argumentsJson`** — Bulk batch carries 10 customers' full payloads; if `AuditWriter.writeToolCall` writes raw record values to `argumentsJson`, audit log becomes a PII reservoir. Mitigation: store `{count, entityName, sampleHashes (SHA-256), idempotencyKey}` only — NEVER raw record values; Phase 11 `MutationErrorTranslator` PII-safe templates.
4. **Idempotency bypass via row-reordering retry** — Naive caller retries same logical batch with rows in different order; non-canonical hash treats it as a new batch → duplicate entity creation. Mitigation: `requestHash` is SHA-256 over canonical JSON in **submission order** (NOT order-independent — Stripe-style byte-identical retry).
5. **VectorStore contamination from task-file blob** — `IngesterManager` accidentally invoked on `AiTaskFile` upload → file content lands in pgvector and surfaces in unrelated RAG retrievals across users. Mitigation: TEST-16 source-scanner asserts task-file pathway has zero references to `IngesterManager`/`VectorStore`; structurally separate code paths.
6. **Multimodal hallucination on out-of-domain image** — User attaches a screenshot the model misreads (e.g. blurry table → fabricated rows). Mitigation: rich tool description requires LLM to echo extracted rows back to the user before calling `bulk_save_records`; rollback-all on per-row failure ensures partial commits cannot occur silently.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Enterprise SaaS / B2B CRUD copilot — generic Jmix add-on shipped into customer-master / order / invoice / contact data systems run by Vietnamese SMB CRM and ERP teams (EN + VI locales). NOT a single regulated vertical (no healthcare / legal / finance specialization), but operates on customer & employee PII the same way a Salesforce / HubSpot / Microsoft Dataverse import action does.

**User Population:** CRM-style staff at small-to-medium VN/regional enterprises using the host Jmix application — sales operations, customer-success ops, data-entry analysts, account managers, and back-office admins. Daily workflow today: open a Jmix list view, click "import xlsx" or hand-key 10–50 rows from an emailed spreadsheet/PDF. Phase 13 replaces that with: drag the same xlsx into chat, the LLM extracts and saves through the same `DataManager.save` path, the user verifies via the same Jmix detail views.

**Stakes Level:** **Medium-High.** Corrupt customer master data has real business impact (mis-routed billing, broken email blasts, wrong-customer phone calls, contract attachment to the wrong account) but every write is reversible via the host's normal Jmix UI — same blast radius as a human form submit. Stakes climb to High when (a) the host hooks `bulk_save_records` outputs to downstream systems (invoicing, payment provider, email sequence) and (b) the imported rows carry customer PII subject to Vietnam Decree 13/2023/ND-CP (effective 2023-07-01) and Law No. 91/2025/QH15 on Personal Data Protection (effective 2026-01-01).

**Output Consequence:** Writes propagate through the unmodified Phase 11 chain → host's `DataManager.save` → host DB. Same `AccessManager` row/attribute policies, same Bean Validation, same `@Composition` cascades, same Liquibase-backed schema as a hand-typed Jmix form submit. A successful `bulk_save_records` call permanently materializes N entity rows visible to all users with read access; a failed call rolls back atomically (zero partial commits). The `AuditWriter` row is the system-of-record forensic artifact — auditors and the compliance reviewer use it to reconstruct "did the AI commit this batch on this user's behalf, with what idempotency key, and how was the input hashed?".

### Known Failure Modes in This Domain

Concrete failure scenarios drawn from CRM/ERP bulk-import literature and 2024–2026 LLM-on-enterprise-data research — not generic "the model hallucinated".

1. **Silent column-shift on a header-row misread.** A common Salesforce/HubSpot failure: the import file has a merged-cell title row above the real headers, the parser locks onto the title row, and every subsequent column drops one position. In an LLM context this is worse: the model "soft-corrects" — emails parsed into `phone` get re-coerced to look phone-shaped (digits stripped of `@`), so even type validation passes. Mitigation surface: rich tool description forces an "echo first 3 rows + mapping back to user" gate before commit ([Coefficient](https://coefficient.io/use-cases/salesforce-contact-import-field-mapping-errors), [Salesforce Ben](https://www.salesforceben.com/salesforce-import-errors-and-how-to-fix-them/)).

2. **Locale formatting drift on dates and decimals.** VN business spreadsheets routinely use `dd/mm/yyyy` and `1.234.567,89`; US-trained LLMs default to `mm/dd/yyyy` and `1,234,567.89`. Result: silent off-by-month errors on contract dates, off-by-1000x errors on currency. Mitigation: `MutationAttributeBinder` should reject ambiguous dates and require the LLM to disambiguate via the user. The rich tool description's FORMATS section pins ISO-8601 + dot-decimal as the only accepted shape ([HubSpot date format community thread](https://community.hubspot.com/t5/CRM/Dates-missing-or-parse-fail-UK-format-in-Deals-import-from-CSV/td-p/320103)).

3. **Encoding corruption of Vietnamese diacritics.** CSV files from older Excel-on-Windows installs land in CP1258 or Windows-1252; "Nguyễn" becomes "Nguyá»…n" in the LLM's view. The model often does NOT flag this — it commits the corrupted bytes. The host then sees mojibake in customer names, breaking search and comms. Mitigation: detect at the resolver layer (`AiTaskFileMediaResolver`) and reject non-UTF-8 with a clear i18n key ([HubSpot UTF-8 requirement](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)).

4. **Hallucinated FK references / phantom entities.** When the file references a customer by name only, the LLM may fabricate a UUID matching the FK type rather than calling `find_records` and reporting "not found". 2024–2026 research labels this "tool-binding confabulation" — the model fills the gap with a plausible-shaped value when the lookup step would have returned empty. Mitigation: `bulk_save_records` rejects malformed UUIDs at bind time; the rich tool description MANDATORY workflow requires `find_records` for any reference column ([Glean](https://www.glean.com/perspectives/when-llms-hallucinate-in-enterprise-contexts-and-how-contextual-grounding), [B EYE](https://b-eye.com/blog/llm-hallucinations-enterprise-data/)).

5. **Multimodal misread on out-of-domain images.** User attaches a screenshot of a printed table that's rotated, blurry, or with a watermark. The LLM transcribes confidently but with row-level errors (transposed digits in phone numbers, swapped first/last names) and offers no confidence signal. 2025 multimodal hallucination benchmarks (CCHall, Mu-SHROOM) confirm cross-modal confabulation rates spike on low-quality scans. Mitigation: rich tool description forces row-by-row echo before commit; failure-mode #6 in §1 already calls this out ([Lakera 2026 hallucination guide](https://www.lakera.ai/blog/guide-to-hallucinations-in-large-language-models), [Adlib: LLMs Hallucinate More on Enterprise Documents](https://www.adlibsoftware.com/news/why-llms-hallucinate-more-on-enterprise-documents)).

6. **Idempotency-key user-experience mismatch.** Salesforce default semantics is upsert per-row (one row failing does not block the others). Phase 13 chose **rollback-all** — closer to a database transaction than to a Salesforce loader run. Users coming from Salesforce/Data Loader will retry a partially-fixed batch and be surprised by `IDEMPOTENCY_VIOLATION` (same key, different bytes) instead of "row 7 retried, rows 1–6 untouched". Mitigation: the rich tool description's STRICTNESS + ERROR HANDLING sections spell this out; assistant reply on failure must guide the user to **generate a fresh idempotency key** for a corrected re-submission ([Stripe-style byte-identical retry semantics](https://stripe.com/docs/api/idempotent_requests)).

7. **Audit-trail PII leak via raw `argumentsJson`.** A naive Phase 11 implementation that just `JSON.stringify(records)` into the audit row turns the audit log into a PII reservoir — every committed customer row's email/phone/DOB persists in clear text inside `agentstore`. SOC 2 Processing Integrity and Decree 13 both treat this as a control gap. Mitigation: §4 State Management bullet 6 mandates `{count, entityName, sampleHashes, idempotencyKey}` only ([Teleport AI agents SOC 2](https://goteleport.com/blog/ai-agents-soc-2/)).

## 2. Framework Decision

**Selected Framework:** Spring AI (confirm — no change from Phases 4–12)

**Version:** 1.1.4 (pinned in `ai-agent/build.gradle:37` via `springAiVersion = "1.1.4"`; BOM imported via Spring dependency-management plugin)

**Rationale:**
Phase 13 extends an existing Spring AI 1.1.4 pipeline that already powers 12 prior phases (`DefaultChatServiceImpl`, `BuiltInDataTools`, `BuiltInMutationTools`, `AuditAdvisor`, `RetrievalAugmentationAdvisor`, `JdbcChatMemoryRepository`, `PgVectorStore`, `OutputScannerAdvisor`, `ChatPanelFragment`). Every Phase 13 primitive ships natively in Spring AI: `org.springframework.ai.content.Media` for multimodal file injection (verbatim port target = `D:/DTH/jmix-crm` `AiAttachmentMediaResolver`), `@Tool`/`@ToolParam` callbacks for `bulk_save_records`, the `chatClient.prompt().user(u -> u.media(media.toArray(new Media[0])))` fluent API, and OpenAI-compatible transport that targets OpenRouter (dev, `https://openrouter.ai/api`) and self-hosted vLLM/Ollama (prod) via a single `spring.ai.openai.base-url` swap with no other code changes. ### Common Pitfalls

1. **`Media.Format` lives in `org.springframework.ai.content.Media` (NOT `org.springframework.ai.model.Media`)**. Pre-1.0 sample code on the web imports the old package — the class moved during the Spring AI 1.0 GA cleanup. Always verify imports against the 1.1.x package.
2. **`@Tool` JSON Schema is generated reflectively at bean registration, not at call time** — adding/removing Jackson annotations on the parameter type does NOT pick up without an application restart. Verify schema by calling `org.springframework.ai.util.json.schema.JsonSchemaGenerator.generateForType(...)` in a unit test rather than trusting runtime LLM behavior.
3. **`JdbcChatMemoryRepository` persists text only** — any `Media` you inject is GONE the next turn. Building a "summarize this PDF then ask follow-up" UX without re-injection or text summary capture in the assistant turn is a footgun. D-01 already mitigates by stamping `messageId` so the resolver does not re-fire.
4. **Tool-calling reliability degrades with tool count on small/mid-size Qwen models** ([QwenLM/Qwen3-Coder #475](https://github.com/QwenLM/Qwen3-Coder/issues/475)). A single `bulk_save_records` is preferred over `bulk_create_records` + `bulk_update_records`; per-row dispatch via id-presence keeps the tool surface flat.
5. **Bean Validation `@NotNull` is honored as a "required" hint by Jackson schema, but Spring AI's `JsonSchemaGenerator` does NOT auto-merge `@NotNull` into the JSON Schema `required` array as of 1.1.4** — verify by inspecting the generated schema. For required-field semantics, use `@ToolParam(required=true)` (default) or `@JsonProperty(required=true)` on the parameter type field. Bean Validation still runs at execution time and produces a `ConstraintViolationException` that the Phase 11 `MutationErrorTranslator` catches.
6. **`ChatClient.prompt().user(u -> u.media(...))` requires the lambda form** — the convenience `.user(String)` overload has no media seam. Mixing the two on the same builder silently drops media. Match the jmix-crm pattern (`CrmAnalyticsService.java:123-131`) verbatim.
7. **`@Transactional` REQUIRED span rolls back on `RuntimeException` / `Error` only** — checked exceptions thrown from inside `bulk_save_records` per-row dispatch will commit the partial batch unless you call `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` explicitly OR rethrow as a `RuntimeException`. Phase 11's translation chain already wraps all per-row failures as `RuntimeException` via `MutationErrorTranslator`, but the bulk extension MUST preserve that contract on the new code path.

            Map.entry(".csv", Media.Format.DOC_CSV),

            Map.entry(".docx", Media.Format.DOC_DOCX),
            Map.entry(".xls", Media.Format.DOC_XLS),
            Map.entry(".xlsx", Media.Format.DOC_XLSX),
            Map.entry(".html", Media.Format.DOC_HTML), Map.entry(".htm", Media.Format.DOC_HTML),
            Map.entry(".txt", Media.Format.DOC_TXT),   Map.entry(".md", Media.Format.DOC_MD),
            Map.entry(".png", Media.Format.IMAGE_PNG),
            Map.entry(".jpg", Media.Format.IMAGE_JPEG), Map.entry(".jpeg", Media.Format.IMAGE_JPEG),
            Map.entry(".gif", Media.Format.IMAGE_GIF),  Map.entry(".webp", Media.Format.IMAGE_WEBP));

    private final UnconstrainedDataManager unconstrainedDataManager; // system-internal load — see memory feedback_jmix_unconstrained_for_system_writes
    private final FileStorageLocator fileStorageLocator;

    /** Returns Media for files attached to {@code conversationId} that have not yet been sent
     *  (messageId IS NULL). Caller is responsible for stamping messageId after the AiMessage
     *  row is persisted (D-03 two-phase write). */
    public Resolved resolvePending(UUID conversationId) {
        if (conversationId == null) return Resolved.empty();

        // .store("agentstore") is mandatory on raw JPQL for cross-store entities — see
        // memory feedback_jmix_loadvalue_store.
        List<AiTaskFile> pending = unconstrainedDataManager.load(AiTaskFile.class)
                .query("select e from ai_AiTaskFile e " +
                       "where e.conversationId = :cid and e.messageId is null " +
                       "  and e.expiresAt > :now order by e.createdAt asc")
                .parameter("cid", conversationId)
                .parameter("now", OffsetDateTime.now())
                .list();

        List<Media> media = pending.stream().map(this::buildMedia).toList();
        List<UUID> ids   = pending.stream().map(AiTaskFile::getId).toList();
        return new Resolved(media, ids);
    }

    private Media buildMedia(AiTaskFile row) {
        FileRef ref = row.getStorageRef();
        if (ref == null) throw new IllegalStateException("AiTaskFile " + row.getId() + " has no storageRef");
        return Media.builder()
                .mimeType(resolveSupportedMimeType(row.getContentType(), row.getFilename()))
                .data(readBytes(ref))
                .name(sanitizeMediaName(row.getFilename()))
                .build();
    }

    private byte[] readBytes(FileRef ref) {
        FileStorage fs = fileStorageLocator.getByName(ref.getStorageName());
        try (InputStream in = fs.openStream(ref)) { return in.readAllBytes(); }
        catch (IOException e) { throw new IllegalStateException("FileStorage read failed: " + ref.getFileName(), e); }
    }

    // resolveSupportedMimeType / tryParseMimeType / mimeTypeFromExtension / sanitizeMediaName:
    // verbatim port of AiAttachmentMediaResolver:117-164. MAX_MEDIA_NAME_LENGTH=96; sanitize regex
    // [^A-Za-z0-9\s\-()\[\]] -> "_"; collapse whitespace; trim; truncate; default "uploaded-file".

    public record Resolved(List<Media> media, List<UUID> taskFileIds) {
        public static Resolved empty() { return new Resolved(List.of(), List.of()); }
        public boolean isEmpty() { return media.isEmpty(); }
    }
}

        - entityName: exact internal name from list_entities, NEVER a label.
        - records: array of objects. For each row:

**State Management — Phase 11 chain order MUST be preserved in bulk variant:**

1. `LlmExposurePolicy.canCreate(metaClass)` AND `canUpdate(metaClass)` — entity-level, ONCE for the whole batch (per-row would double-count audit-irrelevant denials).
2. `mutationRequestHasher.hash(entityName, records, idempotencyKey)` — SHA-256 over canonical JSON in **submission order** (Stripe semantics).
3. `mutationIntentRepository.reservePending(idempotencyKey, requestHash, userUsername, conversationId)` — ONCE per batch.
   - Returns `IDEMPOTENT_REPLAY` if `(idempotencyKey, hash)` matches a prior committed row → short-circuit, zero rows touched, audit row outcome=`IDEMPOTENT_REPLAY`.
   - Returns `IDEMPOTENCY_VIOLATION` if same key + different hash → audit row outcome=`FAILED`, errorCode=`idempotency_violation`.
4. `mutationSaveExecutor.bulkSave(SaveContext context)` — sole `@Transactional` boundary (proxy-crossing, regular `DataManager` NOT `Unconstrained`). Inside the transaction, per row:
   - `id != null` → `dataManager.load(metaClass).id(id).optional()` → 404 → `optimistic_lock`-class fail; else apply changes
   - `id == null` → `dataManager.create(javaClass)` → bind attributes
   - Per-row: `accessManager.applyRegisteredConstraints(CrudEntityContext{CREATE|UPDATE})` → `EntityAttributeContext.canModify` per-attribute → `MutationAttributeBinder.bind(...)` (type coerce + writable check) → `MutationGuard.veto(MutationIntent)` (host SPI, optional) → add to `SaveContext`.
   - Single `dataManager.save(saveContext)` at end.
   - **ANY row failure inside this method MUST throw `RuntimeException`** so the `@Transactional` REQUIRED span rolls back. If a checked exception sneaks in (e.g. `IOException` from a custom `MutationGuard`), wrap as `RuntimeException` OR call `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.
5. `mutationIntentRepository.markCommitted(intentId, savedIds)` — ONCE per batch on success.
6. `auditWriter.writeToolCall(rootAuditId, runId, user, convId, "bulk_save_records", argumentsJson, resultSummary, latencyMs, outcome, denialReason, errorClass)` — ONCE per batch. `argumentsJson` carries `{count, entityName, sampleHashes:[sha256(row0), sha256(row1), sha256(row2)], idempotencyKey}` — NEVER raw record values.

**Context Window Strategy:**
Qwen3.6-35B-A3B has a 262K token context window. A 5 MB xlsx ~= 30K tokens; a 100 MB PDF (worst case) ~= 600K tokens which would OVERFLOW. The 100 MB cap is a deliberate worst-case ceiling — for typical CRM xlsx inputs (1–500 rows = ~5K–30K tokens) the model has ample headroom for tool calls + RAG context (Phase 5 retrieval still runs). For edge-case oversized files: the Spring AI / OpenAI-compat transport will return a 400 with a context-window error; Phase 13 maps this to a stable i18n key `ai-agent.task-file.context-overflow` and surfaces it via the Phase 6 guard-denial path. No automated chunking ships in v1.1 (deferred — the model is the parser).

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice. **Java/Jmix substitution:** the template's "Pydantic example" is replaced by **Java record + Spring AI tool-param POJO** because Spring AI 1.1.4 derives JSON Schema from Jackson annotations on Java types (`@JsonClassDescription`, `@JsonPropertyDescription`, `@JsonProperty(required=true)`) — no Pydantic analogue is required.

### Structured Outputs — Java record + Spring AI tool-param POJO (substitute for Pydantic)

For Phase 13 the LLM input shape is `List<Map<String,Object>>` (entity-agnostic, see §4 rationale). For phases that need typed extraction (e.g. Phase 14 `prepare_form_draft` for a single entity), the Java-record path is:

```java
// One row of a typed bulk-save variant — used as @ToolParam type when the LLM should emit
// Customer-shaped rows. Not shipped in Phase 13 (entity-agnostic Map is the v1 contract);
// reserved as the migration target for D-02 escalation if Qwen3 confuses create vs update.
@JsonClassDescription("One Customer row to create or update in the bulk batch.")
public record CustomerImportRow(
        @JsonPropertyDescription("UUID of an existing Customer to UPDATE. OMIT this field to CREATE a new row. NEVER set to null.")
        UUID id,

        @NotNull
        @JsonProperty(required = true)
        @JsonPropertyDescription("Primary email address. Must be RFC 5322 valid. Unique across active Customers.")
        String email,

        @NotNull
        @JsonProperty(required = true)
        @JsonPropertyDescription("Full legal name in 'Family Given' order (e.g. 'Nguyen An').")
        String fullName,

        @JsonPropertyDescription("E.164 phone number including country code (e.g. '+84901234567'). Optional.")
        String phone,

        @JsonPropertyDescription("ISO-8601 date of birth (e.g. '1990-04-15'). Optional.")
        LocalDate dateOfBirth
) {}
```

How Spring AI 1.1.4 wires this into the tool schema:
- `@Tool` method declares `List<CustomerImportRow> rows` as a parameter.
- `org.springframework.ai.util.json.schema.JsonSchemaGenerator` walks the record components reflectively and produces:
  ```json
  {"type":"array","items":{"type":"object","properties":{
      "id":         {"type":"string","format":"uuid","description":"UUID of an existing Customer..."},
      "email":      {"type":"string","description":"Primary email...","required":true},
      "fullName":   {"type":"string","description":"Full legal name..."},
      "phone":      {"type":"string","description":"E.164 phone..."},
      "dateOfBirth":{"type":"string","format":"date","description":"ISO-8601 date..."}
  },"required":["email","fullName"]}}
  ```
- `@JsonClassDescription` lands on the `items.description`; `@JsonPropertyDescription` on each property; `@JsonProperty(required=true)` populates the `required` array. **`@NotNull` (Bean Validation) is NOT auto-merged into the JSON Schema `required` array as of Spring AI 1.1.4** — keep `@JsonProperty(required=true)` paired with `@NotNull` for both schema-side and runtime-side enforcement.
- At call time, Jackson deserializes the LLM-emitted JSON into `CustomerImportRow` instances; Bean Validation runs via the existing `jakarta.validation.Validator` injected into `BuiltInMutationTools`; violations are translated by `MutationErrorTranslator` into the stable `validation_failed` code with row index — no PII echo.

**Retry logic:** Phase 13 reuses Phase 6 `askTyped` pattern (`DefaultChatServiceImpl:467-519`) — initial + 1 retry, the second attempt re-prompts with a stricter format hint. For tool-call validation failures (LLM emitted bad JSON for `bulk_save_records`), Spring AI's tool-calling manager surfaces the parse error back to the LLM in the next iteration automatically (Phase 9 `GuardedToolCallingManager` enforces an iteration cap — 4 retries). Log on every failed attempt: `tool name`, `attempt N/M`, `errorCode`, `failedRowIndex`. Surface to user only after iteration cap exceeded → `ai-agent.guard.iteration-cap-exceeded`.

### Async-First Design

Spring AI 1.1.4 in this stack runs synchronous `ChatClient.call()` for `ask(...)` and reactive `ChatClient.stream()` for `stream(...)` (see `DefaultChatServiceImpl` lines 247 vs 369). The Phase 13 resolver runs **synchronously inside the request thread BEFORE the LLM call** — `FileStorage.openStream(...).readAllBytes()` is blocking I/O but bounded by the 100 MB file cap; do NOT wrap it in `Mono.fromCallable(...).subscribeOn(boundedElastic())` for the sync path because the `ChatClient.prompt()` builder must already have the byte arrays before `.call()` fires.

For the `.stream(...)` reactive path: hoist the resolver call into `Flux.defer(() -> { ... })` body and stash the `Resolved` record as a final variable before the `chatClient.prompt()` builder; the existing `.subscribeOn(chatStreamingScheduler)` (line 426) handles the offload onto the bounded scheduler. The **one common mistake** to avoid: calling `taskFileMediaResolver.resolvePending(convId)` OUTSIDE the `Flux.defer(...)` would block the calling thread BEFORE the stream is subscribed — defeating reactivity. Match the Phase 12 streaming pattern.

`stream` for UX (token-by-token rendering); `await` (`.call()`) for tool-call paths because tool-calling reliability — especially for `bulk_save_records` which writes data — depends on the full structured response being available before any DB mutation.

### Prompt Engineering Discipline

- **System vs user prompt separation** — already enforced by `SystemPromptComposer.compose(baselineText, profileSystemPrompt, agentSystemPromptRulesComposer.effectiveRules())`. Phase 13 adds NO new system prompt — the `bulk_save_records` workflow ("call list_entities first, echo rows before invoking, do not retry on access_denied") goes inside the rich `@Tool` description (5-section MANDATORY/INPUT/FORMATS/ERROR/STRICTNESS+EXAMPLES per memory `feedback_rich_tool_descriptions`) so it travels WITH the tool schema.
- **Few-shot in the tool description** — two worked examples (xlsx-create-only batch + mixed PDF-update batch) inline in the `@Tool` description. Dynamic retrieval not used: the examples are short, stable, and entity-agnostic.
- **`max_tokens` set explicitly** — `spring.ai.openai.chat.options.max-tokens=8192` in `application.properties`; per-conversation override via `AiParameters.maxTokens`. Never leave unbounded — Phase 6 `TokenBudgetGuard` would still cap, but the model-side ceiling avoids one runaway turn eating the entire conversation budget.

### Context Window Management

- **Multi-turn task-file conversations** — D-01 single-turn-inject already mitigates the dominant cost: file bytes appear ONCE in the request body, not on every turn. The assistant's first-turn paraphrase ("I see 12 rows of customers from the xlsx, columns email/fullName/phone…") becomes the chat-memory record that survives `JdbcChatMemoryRepository` text-only persistence.
- **RAG retrieval still applies** — `RetrievalAugmentationAdvisor` (Phase 5) runs on every turn including task-file turns; the user-scoped `Filter.Expression` from `RetrievalFilterBuilder` continues to gate cross-tenant exposure (Phase 9 invariant).
- **Conversation summarisation** — not implemented in Phase 13. Token-budget ceiling enforced by Phase 6 `TokenBudgetGuard`; over-budget conversations terminate with `ai-agent.guard.token-budget-exhausted`. Future Phase 13.x may add a `MessageWindowChatMemory` cap if telemetry shows multi-day conversations hitting the ceiling.
- **Bulk-save batch size** — no hard cap in Phase 13; the model emits as many rows as it extracts. For a 1000-row xlsx, the request body is ~30K input tokens (file) + ~50K tool-call output tokens (records JSON) + ~30K system prompt — well within Qwen3.6-35B-A3B 262K. Phase 11's per-batch `@Transactional` span handles 1000 saves comfortably; if hosts hit DB lock contention, planner adds `ai-agent.tools.mutation.bulk-max-rows` knob (deferred).

### Cost and Latency Budget

- **Per-call cost estimate** — OpenRouter Qwen3.6-35B-A3B pricing: $0.15 per M input tokens, $1.00 per M output tokens (Apache 2.0 weights → self-host eliminates cost; OpenRouter is dev-only). Typical task-file turn: 30K in + 5K out = $0.0095. 100 calls/day/user × 50 users = $47.50/day = ~$1,425/month at OpenRouter rates; self-host break-even is well under 1 GPU-month.
- **Caching** —
  - *Exact-match*: Phase 9 `BuiltInDataTools` already caches `list_entities`/`describe_entity` per-user via Spring `@Cacheable`; reused as-is by `bulk_save_records` MANDATORY workflow step 1–2.
  - *Semantic*: not used. The chat-memory layer is text-only; semantic-cache against pgvector embeddings is reserved for Phase 14+ if eval shows a high duplicate-question rate.
  - *Idempotency dedup*: Phase 11 `MutationIntentRepository.reservePending` short-circuits same-key replays at zero LLM cost (no second tool round).
- **Cheaper models for sub-tasks** — NOT used in Phase 13 per D-01 (single-model decision). Routing classification, summarisation, and bulk extraction all run on Qwen3.6-35B-A3B. A dual-model `ChatModelRouter` (text-cheap + vision-strong) is deferred to Phase 15+ if cost telemetry shows >30% of turns are pure-text and the routing-overhead break-even is met.

| A-08 | **VI parity drop** | `M-09` |EN − VI| accuracy delta > 10 pp rolling 7d | Slack `#ai-agent-ops` | Vietnamese-Speaking QA Tester |

**Smart sampling strategy** (per `ai-evals.md` "Smart sampling — weight toward concerning signals"):

- **Always sample (100%):** every `outcome=FAILED` audit row; every turn where `M-08` triggers; every multimodal turn with thumbs-down.
- **Heavy sample (50%):** every `IDEMPOTENT_REPLAY` (replay storms diagnostic); every turn where the tool-call iteration cap was hit.
- **Standard sample (10%):** all other production turns (`management.tracing.sampling.probability=0.1`). Phoenix retention 90 days.
- **Quarterly human review:** Security/Compliance Reviewer pulls a stratified sample of 25 audit rows (5 per outcome class) and labels them against §1b rubric ingredients; results feed the F13-03 κ-drift metric.

**Cost telemetry:**
OpenRouter Qwen3.6-35B-A3B: $0.15/M input + $1.00/M output. Typical task-file turn ~$0.0095 (30K in + 5K out). Self-host break-even (vLLM + 1 H100) ≈ 30 days at 100 calls/day/user × 50 users. Phoenix `gen_ai.usage.*` attributes feed a Grafana panel computing `$/day` per tenant; alert A-04 fires at 1.2× the host-configured daily ceiling.

**Observation properties recap (PII-safe defaults):**
`spring.ai.chat.observations.log-prompt=false`, `spring.ai.chat.observations.log-completion=false`, `spring.ai.tools.observations.include-content=false`. Operators must NOT flip these to `true` in production — flipping any of them surfaces raw user prompts, raw assistant replies, and raw tool arguments (including the `bulk_save_records` `records[]` payload) into Phoenix spans, defeating the §6 G13-05 PII-safe audit trail. Dev-only override allowed in non-customer-data environments.
