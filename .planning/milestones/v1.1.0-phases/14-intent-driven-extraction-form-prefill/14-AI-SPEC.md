> Locks framework selection, implementation guidance, and evaluation strategy before planning begins.

## 1. System Classification

**System Type:** Extraction (PDF/image/text → typed Jmix entity draft) wrapped in a Conversational chat surface with hard-gated tool-use (single `@Tool` exposed on named-intent turns)

**Description:**
On a named-intent chat turn (selected via a card row above `messageInputSlot`) the user optionally attaches an `AiTaskFile` (PDF/image) and submits a prompt. The chat service hard-gates the tool surface to the single `prepare_form_draft(intentId, contextRefs)` tool, augments the system prompt with a named-intent rule, and the LLM invokes the tool. The tool dispatches to a host-registered `IntentExtractor<T>` SPI implementation, which calls Spring AI structured output (`chatClient.prompt().user(...).media(...).call().entity(Map.class)`) against a `MetaClass`-derived JSON-schema instruction, persists an `AiExtractionDraft` row in `agentstore`, and returns `{action:"open_form_with_draft", draftId, entityName, instanceName}`. `StreamEventRenderer` recognises that payload and renders an inline "Open form to confirm — {instanceName}" button in the assistant message bubble; click runs `AccessManager.isPermitted(ViewContext)` then `ViewNavigators.detailView(host, EntityClass.class).newEntity().withInitializer(...)`. Prefill applies via `DataContext.create` + per-attribute `EntityAttributeContext.canModify`-gated `setValueIfPermitted`. On Save the draft is deleted; unsaved drafts are reaped by an hourly TTL cleanup job. "Good" = the right entity-generic JSON shape comes out of the LLM on the first call, every modifiable field that the LLM populated maps to the corresponding form field, denied attributes are silently skipped and counted, and the user sees a Jmix-native validate-then-Save flow indistinguishable from manual data entry — never an LLM-driven server-side mutation.

**Critical Failure Modes:**
1. **Tool-surface leak — LLM gets a UI-mutation primitive.** Any `@Tool`-bearing class (or `ToolContributor` extension) directly or transitively imports `io.jmix.flowui.ViewNavigators` or invokes `.navigate()`. `TEST-15` grep/scanner gate must catch it. If it leaks, the LLM can bypass the user-confirm step and mutate UI state without `AccessManager` validation.
2. **Schema-violation extraction.** The LLM returns prose, markdown fences, extra keys, missing required fields, or wrong-typed values — `MapOutputConverter` parse fails, the tool errors, audit row written with `outcome=FAILED`, the user sees no confirm button. Mitigation: prompt-only strict instruction (D-04), bounded retry, operator-doc note that weak-JSON-adherence models cause this.
3. **Privilege escalation via `payloadJson`.** `DraftLoader` raw-`setValue`s an attribute the user cannot modify (e.g. an admin-only `accountStatus`), bypassing `EntityAttributeContext.canModify`. Mitigation: `setValueIfPermitted`-only contract (REQ-10) plus the `DraftLoaderTest` that asserts denied attrs stay empty AND get counted in the audit row.
4. **Cross-tenant draft read.** `bob` reads / opens / saves a draft created by `alice` because the row-level policy on `AiExtractionDraft.userUsername` is missing or mis-wired. Mitigation: `AiAgentUserRowLevelRole` extension + the multi-user `@UiTest` from REQ-2.
5. **Stale or hostile-LLM draft applied silently.** Confirm button re-clicked after TTL-reap (or after another `prepare_form_draft` call wrote a new draft) — user thinks they are confirming the draft they just saw but a different `payloadJson` loads. Mitigation: idempotent click handler keyed on `draftId` (D-11) + disabled state with `chatView.intent.draftExpired` when row is gone; `AfterSaveEvent` listener deletes immediately on Save.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:**
Two-layer domain — both must be evaluated.
- **Layer 1 (engine, applies to every host of `ai-agent-core`):** Enterprise back-office data entry / Jmix line-of-business apps. The engine is an AI-assisted form-prefill capability bolted onto Jmix detail views. Hosts ship their own intents (Order, Lead, Invoice, Ticket, Contract, Patient-record, etc.); the engine itself is entity-generic.
- **Layer 2 (bundled reference intent in `jmix-app`):** B2B CRM master-data stewardship — the discipline customer-success / operations / finance teams call "data stewardship" or "MDM (master data management)". The reference `CustomerDraftIntentExtractor` extracts a `Customer` row (`name`, `email`, `phone`) from an attached PDF / image of a business card or contact-info document. Industry conventions, regulatory exposure, and "what an expert flags" are well-defined here.

**User Population:**
Internal, authenticated, role-permissioned, audited back-office staff — NOT a public consumer assistant. Concrete archetypes that drive the dominant trigger events:
- **Sales rep at a trade show / field call** — just received a vCard, business card photo, or LinkedIn-export PDF; pastes it into chat with the Customer card selected; expects a prefilled new-customer detail view in seconds rather than retyping.
- **Customer-service agent on a support queue** — opens a customer email with a scanned ID document or contact-info attachment; uses the same picker to spawn a Customer / Ticket / Account draft prefilled from the attachment; reviews and saves.
- **Operations clerk / order-entry staff** — pastes a purchase-order PDF or supplier-confirmation email into chat with a host's Order intent selected; LLM populates `customer`, `lineItems`, `expectedDate`; clerk eyeballs values, corrects, saves.
- **Finance / AR ops** — receives an invoice scan or remittance advice; intent prefills an `Invoice` row; finance officer validates VAT / tax IDs against master data, then saves.
- **Support engineer / KB-author** — types or pastes a support-case summary; intent prefills a structured `KbArticle` or `Incident` row.

Common signature: the user is **already inside Jmix as an authenticated principal**, every prefilled field maps to an attribute on a Jmix entity their role-policy permits, and the click that ultimately writes to the database is **the user's hand on Save** — never the LLM's tool call.

**Stakes Level:** **MEDIUM-to-HIGH** — host-dependent, asymmetric.
- **Floor (always present, every host):** user-time waste reviewing a wrong prefill; trust erosion in the AI surface; users disabling the picker if the prefill is consistently worse than typing.
- **Ceiling (host-entity-dependent):**
    - Customer master with a wrong email → marketing-automation misfire; one bad invoice send.
    - Customer master with a wrong VAT / tax ID → regulatory audit exposure (HMRC, IRS, EU VAT MOSS).
    - Order with a wrong `customer` reference or wrong `lineItem.unitPrice` → revenue leakage, incorrect invoice, customer dispute.
    - Patient-record host (out-of-scope for the engine, host's responsibility) → HIPAA-class incident.
    - Compliance / KYC field misextraction → AML / sanctions-screening failure.
- **Asymmetry note:** the engine NEVER auto-saves. `prepare_form_draft` returns a payload; the user reviews in a Jmix detail view; `dataContext.validate()` runs; user clicks Save; `AccessManager` validates; only then does a row land. Every wrong-prefill outcome therefore requires a **second human failure** (user clicks Save without catching the mistake) on top of the model failure. This caps the system's blast radius below "LLM-with-DB-write tools" but does NOT zero it — the dominant production failure mode in this domain is "subtly wrong values that pass eyeballing and validation but corrupt downstream master data".

**Output Consequence:**
LLM-side path is **defence-in-depth, never direct write**:

```
LLM extracts -> AiExtractionDraft row (agentstore, row-level scoped to userUsername)
  -> chat renders "Open form to confirm" button (D-09, D-10)
  -> user clicks (idempotent per draftId, D-11)
  -> AccessManager.isPermitted(ViewContext) gate
  -> ViewNavigators.detailView(...).newEntity().withInitializer(draftLoader)
  -> DraftLoader.apply uses ONLY EntityAttributeContext.canModify-gated setValueIfPermitted
  -> standard StandardDetailView lifecycle (dataContext.validate + Bean Validation)
  -> user clicks Save -> Jmix AccessManager entity policy gate -> DB INSERT/UPDATE
  -> AfterSaveEvent listener deletes draft
  -> downstream consumers: CRM dashboards, invoice generation, marketing-automation lists,
     regulatory exports (VAT returns, KYC files), BI / analytics rollups
```

The LLM has zero `ViewNavigators` reference (TEST-15 enforces this statically). Phase 14 is explicitly **defence-in-depth against LLM error**: even a fully compromised LLM cannot mutate the database — the worst it can do is fabricate a draft the user must review and reject.

### Known Failure Modes in This Domain

These are **domain-specific manifestations**, not the generic "hallucination" label:

1. **Synthetic-looking PDF / OCR drift.** LLM extracts plausible-but-wrong values from a low-quality scan: blurred "B" read as "8" in a phone number, "rn" read as "m" in an email handle, "Smyth" read as "Smith". The output is shape-valid (`@Email` passes, `@Pattern` passes) but factually wrong; user eyeballs it, doesn't catch the single-character drift, clicks Save → corrupted master record. Source: Vellum 2026 LLM-vs-OCR analysis; standard MDM stewardship-team triage pattern.

2. **Locale / format drift.** Source has "(020) 7946-0958" (UK spaced-paren format) → LLM emits the same string verbatim → host `@Pattern` validator (E.164-or-local-canonical) rejects on Save → user retypes manually → user-effort regression. Or source has German "Müller" → LLM lowercases the umlaut handling → ASCII fallback `Mueller` saved → CRM dedup later treats them as different customers.

3. **Ambiguous-name disambiguation (contact-vs-company).** Business-card PDF says "John Smith — Sales Director, Acme Corp". The reference `Customer` schema is a CONTACT row (Layer 2 reference). Does `Customer.name` = "John Smith" (the contact)? Or "Acme Corp" (the company)? The schema instruction must disambiguate at prompt-build time; otherwise different scans land in different conventions and stewards cannot dedupe. Mitigation: `MetaClassDtoSynthesizer` includes `@InstanceName` semantic hints + the host's bilingual messages; flag for the eval rubric.

4. **Multi-record source (silent loss).** User attaches a 3-customer membership-list PDF. Engine is single-record-per-turn (D-03(c), EXTRACT-11 deferred). LLM picks the FIRST record and emits one Customer; the other two are silently dropped. User sees a confirm card for "Acme Inc." and may not notice "Beta Inc." and "Gamma Inc." were on the same page. Expected v1.1 behaviour but documented as a known surprise — mitigation is operator-doc warning + future EXTRACT-11.

5. **PII bleed via system-prompt clarification rule.** Per D-06, when extracted values are incomplete or ambiguous the assistant MUST ask the user for missing information. The assistant could ask leading questions ("Is the phone +44-20-7946-0958?") that re-volunteer the extracted PII into chat memory — and `JdbcChatMemoryRepository` persists the conversation. Mitigation: chat-memory retention policy is the safety net; eval rubric must verify the assistant asks "the phone number is unclear, please re-enter it" rather than echoing what it extracted.

6. **Prefill that satisfies validation but is factually fabricated.** LLM emits `email="noreply@example.com"` — shape-valid (`@Email` passes), domain real (`example.com` is RFC-reserved but most validators allow it), but factually fake. User clicks Save without noticing because the form looks complete. Downstream marketing email bounces or — worse — lands on a real `noreply@somecompany.com` mailbox. Source: classic LLM "looks valid" silent corruption (Adlib). Mitigation: source-faithfulness LLM-judge dimension on the eval rubric; production sampling weighted toward turns with `extractedFieldCount` matching field-count exactly (zero blanks → suspect for fabrication).

7. **Stale-draft re-click (CFM-5 manifestation).** Confirm button re-clicked after TTL-reap (1h default per `ai-agent.extraction.ttl-seconds`) — D-11 disabled-state with `chatView.intent.draftExpired` is the design mitigation; eval rubric verifies the disabled state rather than allowing a silent fall-through to a different draft.

8. **Cross-tenant draft leak (CFM-4 manifestation).** `bob` reads / opens / saves a draft created by `alice` because `AiAgentUserRowLevelRole`'s `@JpqlRowLevelPolicy` on `AiExtractionDraft.userUsername` is missing or mis-wired. Mitigation: REQ-2 multi-user `@UiTest`; eval rubric includes a paired-user negative-access dimension.

### Regulatory / Compliance Context

The bundled reference intent extracts PII (B2B contact names + emails + phones), and host intents may target patient / financial / regulated entities. The engine's compliance posture rests on three pillars:

- **GDPR Art. 5(1)(c) — Data Minimization (legally binding, not best-practice):** every personal-data field requested must be necessary for the commercial purpose. The reference Customer extracts only `name / email / phone` — defensible. Hosts adding wider intents bear the duty to justify each requested attribute. The engine surfaces `MetaClassDtoSynthesizer` filtered by `EntityAttributeContext.canModify`, which gives the host a structural way to enforce "ask for less". ([Strac](https://www.strac.io/blog/gdpr-data-minimization); [Exabeam GDPR Art. 5](https://www.exabeam.com/explainers/gdpr-compliance/gdpr-article-5-key-principles-and-6-compliance-best-practices/))
- **GDPR Art. 5(1)(d) — Accuracy:** personal data must be kept accurate and up to date; inaccurate data corrected without delay. The Phase 14 design — user reviews the prefill in a Jmix detail view, edits, then saves — is the **direct mechanism** for this duty. The eval rubric's "field-level accuracy" + "source-faithfulness" dimensions are the early-detection signal. ([Legiscope GDPR Accuracy 2026](https://www.legiscope.com/blog/data-accuracy-gdpr.html))
- **GDPR Art. 32 — Security of Processing:** appropriate technical / organizational measures. Phase 14 carries: row-level policy (`userUsername`) on the draft entity; `AccessManager` gating before navigation; `EntityAttributeContext.canModify` per-attribute gating in `DraftLoader`; append-only audit chain (Phase 9 D-01); TEST-15 static guard against tool-surface leak. The Jmix audit chain is the primary compliance artefact. ([Exabeam GDPR Art. 5](https://www.exabeam.com/explainers/gdpr-compliance/gdpr-article-5-key-principles-and-6-compliance-best-practices/))
- **CCPA / CPRA (US):** parallel duties for B2B-PII handling — applies to any host serving California residents. Same minimization + accuracy + security obligations; same engine mechanisms cover.
- **GDPR Art. 22 — Automated Individual Decision-Making:** **NOT triggered.** The engine does NOT make any automated decision about a person; it prefills a form for a human to review and save. The user is the decision-maker; Art. 22 does not apply. Worth recording explicitly so a future host audit doesn't misclassify the system.
- **Sector overlays (HOST RESPONSIBILITY, OUT-OF-SCOPE FOR ENGINE):** HIPAA (healthcare hosts whose `Customer`-equivalent carries PHI), PCI-DSS (hosts whose entity carries cardholder data), MiFID II / FCA (financial hosts), AML / KYC (banking hosts). The engine MUST NOT be deployed against PHI / cardholder / regulated entities without the host conducting its own DPIA + sector compliance review. Operator docs must call this out.

The engine ITSELF does not automate any regulated decision (no auto-save, no profiling, no scoring). Phase 9's append-only audit row is the primary regulatory artefact — every `prepare_form_draft` call, every `extraction.draft_applied` call, every DENIED outcome is written immutably to `agentstore.AI_AUDIT_EVENT` keyed by `runId`, queryable by user / time / outcome.

## 2. Framework Decision

**Selected Framework:** Spring AI

**Version:** 1.1.4 (BOM-pinned across `ai-agent` core + `ai-agent-starter` — same pin as Phases 9-13.1)

**Rationale:**
Phases 9-13.1 already shipped on Spring AI primitives — `ChatClientFactory.prompt()`, `@Tool` / `@ToolParam` tool registration, `JdbcChatMemoryRepository` against `agentstore`, `AiTaskFileMediaResolver` feeding `chatClient.prompt().user(...).media(...)`, `AuditWriter` wrapping `ToolCallback` invocations, and `AgentToolCallbacks` aggregating `@Tool`-bearing beans plus the `ToolContributor` SPI. Phase 14's only **new** Spring AI surface is structured-output binding via `chatClient.prompt().user(...).media(...).call().entity(new ParameterizedTypeReference<Map<String, Object>>() {})` backed by `MapOutputConverter` (the converter Spring AI selects when the target type is `Map`). That call composes cleanly with the existing `Media`-injection path (D-18 — the reference Customer extractor passes ALL non-expired `MediaContent` from `AiTaskFileMediaResolver.resolveActive` in one prompt) and with the existing per-turn tool-callback filter point in `AgentToolCallbacks` (D-05 — when `intentId` is non-null, the aggregator returns the single-callback list `[prepare_form_draft]`). Re-platforming Phase 14 onto a different framework would force a full re-port of the audit, exposure-policy, mutation-chain, media-resolver, and JDBC-chat-memory stack — non-viable for a single phase, and unjustified because Spring AI 1.1.4 already covers every Phase 14 capability (multimodal `Media`, structured-output via `Map`, `@Tool` gating, OpenAI-compatible client over OpenRouter, tool-call audit hook).

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| **LangChain4j 0.36.x** | Only Java-native alternative with comparable `@Tool` + structured-output ergonomics (`AiServices` + `@UserMessage` with response-format JSON-schema, `ChatLanguageModel` over OpenAI-compatible endpoints). Ruled out because porting Phases 9-13.1 (5+ phases of audit wrapping, exposure-policy, mutation chain, media resolver, JDBC chat memory) onto LangChain4j primitives costs an entire milestone for zero functional gain — Spring AI already serves the open-weights / OpenAI-compatible / multimodal needs Phase 14 has. |
| **Provider-native strict mode (`responseFormat = json_schema, strict = true`)** | NOT a framework alternative per se but a within-Spring-AI choice ruled out per **D-04**. - **Model lock-in: REJECTED.** Default model is `qwen/qwen3.6-35b-a3b` (Apache 2.0 open-weights, multimodal native) per Phase 13 swap and the `project_self_hostable_models_only.md` mandate. ### Entry Point Pattern

The reference `CustomerDraftIntentExtractor` follows this shape. The user-prompt text concatenates the human request with the JSON-schema instruction synthesized from `MetaClass`; the `Media` list is the per-turn-all resolution from `AiTaskFileMediaResolver.resolveActive` (zero-file turns pass an empty list, D-19).

```java
// Inside IntentExtractor<Customer>.extract(ExtractionInput input)
List<Media> media = input.taskFileMedia();   // 0..N PDFs/images for this turn (D-18)
String schemaInstruction = metaClassDtoSynthesizer.buildSchema(Customer.class, currentUser);

String promptText = """
        %s

        Respond with ONLY a single JSON object that strictly conforms to this schema.
        No prose, no markdown fences, no extra keys.
        %s
        """.formatted(input.userMessage() == null ? "" : input.userMessage(), schemaInstruction);

// Spring AI structured-output call. MapOutputConverter is auto-selected because
// the target type is Map<String,Object>; ParameterizedTypeReference carries the
// generic info that bare Map.class would erase.
Map<String, Object> raw = chatClient.prompt()
        .user(u -> {
            u.text(promptText);
            for (Media m : media) {
                u.media(m);                  // accepts MimeType + Resource OR a Media instance
            }
        })
        .call()
        .entity(new ParameterizedTypeReference<Map<String, Object>>() {});

// Map -> typed DTO via Jackson (engine stays generic; Map is the wire shape).
Customer draft = objectMapper.convertValue(raw, Customer.class);

// Bean Validation; on violations -> audit FAILED, surface to user (no retry in v1.1).
Set<ConstraintViolation<Customer>> violations = validator.validate(draft);
if (!violations.isEmpty()) {
    throw new ExtractionSchemaException(violations);
}
return draft;

### Common Pitfalls

1. **Markdown-fence wrapping kills `MapOutputConverter`.** Weak-JSON-adherence open-weights models (incl. occasional Qwen3.6-A3B turns) wrap their JSON in <code>```json … ```</code> fences despite the prompt instruction. `MapOutputConverter#convert` calls `JsonParser.readValueAsTree`, which sees the leading <code>```</code> as invalid and throws. Mitigation: keep the D-04 strict-mode prompt instruction ("No prose, no markdown fences, no extra keys"), audit `outcome=FAILED` with the raw text in `resultSummary` so operators can spot the pattern, and document this in operator docs as a known weak-model failure mode (per Phase 14 SPEC §Constraints). No silent retry in v1.1.

2. **`Media` MIME mismatch silently drops the attachment.** `MimeTypeUtils.IMAGE_PNG` must match the file's actual bytes; some providers (Google GenAI, OpenAI vision) reject mismatched MIME with a 400 that surfaces as a Spring AI `ChatException` mid-call, others silently drop the attachment and run text-only. Mitigation: `AiTaskFileMediaResolver` already detects MIME from the stored `AiTaskFile.contentType` (Phase 13.1) — do NOT re-derive MIME from filename in Phase 14 code; trust the resolver.

3. **`@Tool` annotation reflects ALL public methods of the bean if helpers leak `public`.** Spring AI's annotation scanner registers any `@Tool`-annotated method, but a public helper without `@Tool` is fine; the trap is the *opposite*: a `@Tool`-annotated private method is silently ignored (no log warning). Mitigation: every `@Tool` method must be `public`; co-locate `prepare_form_draft` in `ExtractionToolBridge` and keep helpers `private`.

4. **`ParameterizedTypeReference` raw-type usage erases the generic and falls back to `String`.** Writing `entity(new ParameterizedTypeReference() {})` (no diamond) compiles but the converter resolves to `Object`/`String` and `MapOutputConverter` is never selected. Mitigation: always parameterize — `new ParameterizedTypeReference<Map<String, Object>>() {}` — and keep this on a single line for code-review grep.

5. **`ChatClient` is a singleton but `.prompt()` returns a builder; mutating it across threads corrupts state.** The single `ChatClient` `@Bean` in `ChatClientFactory#defaultChatClient` is thread-safe per Spring AI docs, but the `ChatClient.PromptUserSpec` returned from `.prompt()` is NOT — never store it in a field or share it across requests. Mitigation: build, call, and discard the prompt-builder inside `extract(...)`.

6. **Tool-result map keys are NOT preserved insertion order on every Jackson config.** `prepare_form_draft` returns `Map.of("action", ..., "draftId", ..., "entityName", ..., "instanceName", ...)`; `Map.of(...)` does NOT guarantee iteration order, and Spring AI's default `ObjectMapper` may serialize keys in different orders across providers. Mitigation: use `LinkedHashMap` for the tool result so JSON shape is grep-stable in test assertions and audit rows; never rely on Map.of for tool-call result construction.

## 4. Implementation Guidance

**Model Configuration:**

Phase 14 inherits the active `AiParameters` profile per turn (EXTRACT-03 — no separate model pin for extraction). Default profile after Phase 13: `qwen/qwen3.6-35b-a3b` via OpenRouter (Apache 2.0 open-weights, multimodal native, ~131K context). Operator implications:

- **Temperature:** Extraction wants `temperature ≤ 0.2` for deterministic JSON adherence; the active profile inherits whatever the operator set for general chat (often 0.7). Trade-off documented in `docs/operator-extraction-tuning.md` (deferred but tracked) — operators creating an "extraction-optimized" profile should clone the default and drop temperature. Do NOT hard-code per-call overrides in Phase 14 code; the engine must respect profile sovereignty.
- **`maxTokens`:** Set to a value ≥ the largest realistic schema response (3-field Customer ≈ 256 tokens; 30-field invoice ≈ 4096 tokens). Profile default of 4096 is sufficient for v1.1 reference Customer; operators with wider entities tune up.
- **`topP` / `topK`:** Inherit from profile; do not override.
- **Provider strict-mode `responseFormat = json_schema, strict = true`:** NOT used (D-04). Prompt-only enforcement keeps the engine portable across Qwen3.6-A3B / future open-weights / any OpenAI-compatible endpoint. Trade-off — higher schema-violation rate on weak-JSON-adherence models — accepted; mitigated by audit-logged failures and operator-doc note.

**Core Pattern:**

The `IntentExtractor<T>` SPI body. Inline comments call out every contract checkpoint.

```java
@Override
public Customer extract(ExtractionInput input) {
    // 1. Build the JSON-schema instruction from MetaClass (entity-generic engine).
    //    Filtered by EntityAttributeContext.canModify for the calling user (D-03).
    String schemaInstruction = metaClassDtoSynthesizer.buildSchema(
            metadata.getClass(Customer.class), currentAuthentication.getUser());

    // 2. Compose the user prompt: human request + strict-mode schema instruction (D-01, D-04).
    //    Zero-file turns (D-19) still flow here — userMessage carries the structured text.
    String userText = (input.userMessage() == null ? "" : input.userMessage())
            + "\n\nRespond with ONLY a single JSON object that strictly conforms to this schema. "
            + "No prose, no markdown fences, no extra keys.\n"
            + schemaInstruction;

    // 3. Single Spring AI call. .call() blocks (NOT .stream() — see §Async-First).
    //    All Media in one prompt — multi-page PDFs + images merge into one Customer (D-18).
    Map<String, Object> raw = chatClient.prompt()
            .user(u -> {
                u.text(userText);
                for (Media m : input.taskFileMedia()) {
                    u.media(m);
                }
            })
            .call()
            .entity(new ParameterizedTypeReference<Map<String, Object>>() {});

    // 4. Map -> typed DTO via Jackson (engine returns Map; the reference impl narrows).
    //    convertValue handles UUID format=string -> UUID coercion uniformly.
    Customer draft = objectMapper.convertValue(raw, Customer.class);

    // 5. Bean Validation. Violations -> ExtractionSchemaException -> outcome=FAILED audit row.
    //    No silent retry in v1.1 (D-04); user sees the failure and re-submits.
    Set<ConstraintViolation<Customer>> violations = validator.validate(draft);
    if (!violations.isEmpty()) {
        throw new ExtractionSchemaException(targetType(), violations);
    }
    return draft;
}
```

`ExtractionService.prepare(intentId, input)` wraps the SPI call:

```java
@Service
public class ExtractionService {

    @Transactional
    public ExtractionResult prepare(String intentId, ExtractionInput input) {
        IntentExtractor<?> extractor = intentRegistry.requireById(intentId);

        // Phase 10 exposure gate — denial path writes outcome=DENIED + denialReason
        // and short-circuits without persisting a draft (D-14).
        exposureRules.requireAllowed(extractor.entityName(), currentAuthentication.getUser());

        Object payload;
        try {
            payload = extractor.extract(input);
        } catch (ExtractionSchemaException ex) {
            auditWriter.writeToolCall(/* eventName= */ "prepare_form_draft",
                    /* outcome= */ AiToolCallOutcome.FAILED,
                    /* argsJson= */ argsJson(intentId, input),
                    /* resultSummary= */ Map.of("error", ex.getCode()));
            throw ex;
        }

        AiExtractionDraft draft = persistDraft(intentId, payload, input);
        auditWriter.writeToolCall("prepare_form_draft",
                AiToolCallOutcome.SUCCESS,
                argsJson(intentId, input),
                Map.of("draftId", draft.getId(),
                       "entityName", draft.getTargetEntityName(),
                       "instanceName", draft.getInstanceName(),
                       "extractedFieldCount", countNonNullFields(payload)));
        return new ExtractionResult(draft.getId(),
                draft.getTargetEntityName(),
                draft.getInstanceName());
    }
}
```

**Tool Use:**

Single `@Tool` registration via the existing `AgentToolCallbacks` aggregator (no new tool-discovery wiring). Hard-gated when the chat turn carries a non-null `intentId` (D-05).

```java
@Component
public class ExtractionToolBridge {

    private final ExtractionService extractionService;
    private final RunContext runContext;            // current conversationId, userId, runId

    public ExtractionToolBridge(ExtractionService extractionService, RunContext runContext) {
        this.extractionService = extractionService;
        this.runContext = runContext;
    }

    /**
     * Rich-tool-description following the project convention
     * (feedback_rich_tool_descriptions.md: MANDATORY/INPUT/FORMATS/ERROR/STRICTNESS+EXAMPLES).
     * Description is ~50-150 lines for enterprise data tools.
     */
    @Tool(name = "prepare_form_draft", description = """
            MANDATORY: Call this tool to fulfill any named-intent extraction turn. The user
            has already chosen the intent via the card-row picker; intentId is supplied below.

            INPUT:
              intentId      Required. Stable string id of the chosen IntentExtractor. Pass it
                            verbatim — do NOT translate, abbreviate, or invent a new id.
              contextRefs   Optional. Map carrying additional hints if the user provided any
                            structured guidance in chat. Keys are free-form. The extractor
                            implementation decides what to honor; unknown keys are ignored.

            FORMATS:
              Result is a JSON object with EXACTLY these keys:
                action        Literal "open_form_with_draft".
                draftId       UUID of the persisted AiExtractionDraft row.
                entityName    Jmix entity name, e.g. "sample_Customer".
                instanceName  Human-readable summary used for the chat confirm button label.

            ERROR HANDLING:
              On exposure denial, this tool returns an error. Do NOT retry; tell the user the
              entity is not available for extraction.
              On schema-violation (model returned malformed JSON), the tool returns an error.
              Apologize, ask the user to rephrase or attach a clearer source document.

            STRICTNESS:
              Call AT MOST ONCE per turn (single-intent-per-turn). After this tool returns,
              respond ONLY with a brief confirmation sentence; the chat UI will render the
              "Open form to confirm" button automatically — do NOT include any markdown link
              or button-like text in your reply.

            EXAMPLES:
              prepare_form_draft(intentId="customer-from-pdf", contextRefs={})
              prepare_form_draft(intentId="customer-from-pdf",
                                 contextRefs={"hint": "this customer is in EU region"})
            """)
    public Map<String, Object> prepareFormDraft(
            @ToolParam(description = "intent id, supplied by the picker — pass verbatim")
            String intentId,
            @ToolParam(description = "optional context refs map; keys free-form, unknown keys ignored", required = false)
            Map<String, Object> contextRefs) {

        ExtractionInput input = ExtractionInput.from(runContext, contextRefs);
        ExtractionResult result = extractionService.prepare(intentId, input);

        // LinkedHashMap — deterministic key order for grep-stable audit rows + tests (Pitfall 6).
        Map<String, Object> out = new LinkedHashMap<>();
        out.put("action", "open_form_with_draft");
        out.put("draftId", result.draftId());
        out.put("entityName", result.entityName());
        out.put("instanceName", result.instanceName());
        return out;
    }
}
```

`AgentToolCallbacks.forCurrentUser(...)` extension — when `runContext.intentId() != null`, the aggregator returns the single-callback list `[prepare_form_draft]`; all other tools (`list_entities`, `find_records`, mutation tools) are stripped for that turn. Auto turns retain the full surface.

**State Management:**

- **Drafts** persist in `agentstore.AI_EXTRACTION_DRAFT` (NOT `VaadinSession`, NOT in-memory caches). Survives page reload, tab change, and multi-tab — required because the confirm button may be re-clicked across navigations (D-11, D-16).
- **Row-level policy** enforced by Jmix `AccessManager` via `@JpqlRowLevelPolicy` on `AiExtractionDraft.userUsername`. `bob` cannot read `alice`'s draft. Cleanup job is the single exception and uses `UnconstrainedDataManager` (per `feedback_jmix_unconstrained_for_system_writes.md`).
- **Per-turn Media** resolved via `AiTaskFileMediaResolver.resolveActive(conversationId)` (Phase 13.1). All non-expired files for the conversation flow into `ExtractionInput.taskFileMedia` for the single Spring AI call (D-18). Media is NOT cached — re-resolved each turn.
- **Audit** is append-only (Phase 9 D-01): two TOOL-shaped rows linked by `runId` (D-12) — `prepare_form_draft` at tool-call time, `extraction.draft_applied` at prefill time. NO in-place updates.
- **Conversation memory** is NOT touched in Phase 14 — the structured-output extraction call uses the same `ChatClient` singleton, so `MessageChatMemoryAdvisor` rolls in transparently. The Map-typed JSON response is stored as the assistant's tool-call result message; subsequent turns can reference "the draft I just prepared" without extra plumbing.

**Context Window Strategy:**

Single-turn, single-prompt extraction. No retrieval, no RAG, no memory composition needed for the extraction call itself.

- **Multi-page PDFs + images + text** all go in the same `chatClient.prompt().user(u -> u.text(...).media(m1).media(m2)...).call()` invocation. The active profile's context window (default Qwen3.6-A3B ≈ 131K tokens) absorbs typical PDF/image volume; image tokens for a vision model run ~1024 tokens/page so a 50-page PDF can saturate a smaller window.
- **When source exceeds context:** v1.1 escalates the failure to the user (operator docs flag this as a known constraint). Document-splitting upstream is deferred to backlog — would require a chunked extraction protocol Phase 14 SPEC explicitly excludes.
- **Schema attribute count** is bounded by D-03's exclusion rules (collections / `@OneToMany` excluded; system audit fields excluded; per-attribute `canModify` filter applied). For the reference Customer (3 fields) the schema instruction is ~30 tokens; for a 30-attribute entity it remains under ~300 tokens. The cost is dominated by Media, not by schema.
- **No tool-loop iteration cap concern.** The hard tool gate (D-05) means the LLM has exactly one available tool on a named-intent turn; even if it tried to recurse, there's only one path. The existing `IterationCapExceededException` guard from Phase 9 still applies as a safety net.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Typed `Map` + Jackson + Bean Validation

> **Java equivalent of Pydantic.** This project is Java 21 — there is no Pydantic. The same contract (typed structured output, validation at the boundary, retry-or-fail on schema violation) is implemented with Jmix's existing JPA entity classes, Jackson, and Jmix's bundled `jakarta.validation.Validator`. Keeping the engine entity-generic forces the wire shape to be `Map<String, Object>` (D-01); the host extractor does the typed narrowing.

**Step 1 — Define the target as a normal Jmix entity (the validated type).**

```java
// jmix-app/src/main/java/com/vn/jmixapp/entity/Customer.java — already exists
@JmixEntity
@Entity(name = "sample_Customer")
public class Customer {

    @Id @JmixGeneratedValue
    private UUID id;

    @NotBlank
    @Size(max = 255)
    @InstanceName
    private String name;

    @Email
    @Size(max = 255)
    private String email;

    @Pattern(regexp = "\\+?[0-9 \\-()]{6,32}")
    private String phone;

    // ... getters/setters
}
```

The JPA + Bean Validation annotations (`@NotBlank`, `@Email`, `@Pattern`, `@Size`) ARE the schema. No separate Pydantic-style model duplication.

**Step 2 — Convert via Jackson, validate via `jakarta.validation.Validator`.**

```java
// In CustomerDraftIntentExtractor (host module)
private final ChatClient chatClient;
private final ObjectMapper objectMapper;
private final Validator validator;            // Jmix already provides this bean

@Override
public Customer extract(ExtractionInput input) {
    Map<String, Object> raw = chatClient.prompt()
            .user(u -> { u.text(promptText(input)); input.taskFileMedia().forEach(u::media); })
            .call()
            .entity(new ParameterizedTypeReference<Map<String, Object>>() {});

    // Jackson handles UUID coercion, ISO-8601 dates, enum value-name mapping uniformly.
    // configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, true) catches
    // the "extra keys" failure mode mandated by the prompt's strict-mode rule (D-04).
    Customer draft;
    try {
        draft = objectMapper.convertValue(raw, Customer.class);
    } catch (IllegalArgumentException ex) {            // Jackson's wrapper for convertValue parse errors
        throw new ExtractionSchemaException("JACKSON_PARSE_FAILURE", ex);
    }

    // Bean Validation — same Validator Jmix StandardDetailView uses on Save, so
    // anything that passes here will not surprise-fail at user click-Save time.
    Set<ConstraintViolation<Customer>> violations = validator.validate(draft);
    if (!violations.isEmpty()) {
        throw new ExtractionSchemaException("BEAN_VALIDATION_FAILURE", violations);
    }
    return draft;
}
```

**Step 3 — Retry / surface policy.**

| Failure | Code | Action in v1.1 |
|---------|------|----------------|
| Markdown-fence wrap (`MapOutputConverter` JSON parse) | `MAP_CONVERTER_PARSE_FAILURE` | Audit `outcome=FAILED`; surface to user; **no automatic retry** (D-04). |
| Jackson `convertValue` mismatch (e.g. `email` returned as `Map`) | `JACKSON_PARSE_FAILURE` | Audit `outcome=FAILED`; surface to user; **no automatic retry**. |
| Bean Validation violation (`@Email`, `@Size`) | `BEAN_VALIDATION_FAILURE` | Audit `outcome=FAILED` with the violations' property paths and codes (NOT the values — never log raw user PII into audit messages); surface to user. |
| Phase 10 exposure denial | `EXPOSURE_DENIED` | Audit `outcome=DENIED` with `denialReason="exposure_rule:{ruleId}"`; surface to user (D-14). |

**Why no automatic retry in v1.1:** retrying with the same prompt against the same model on the same media is unlikely to converge (the model is deterministic-ish given low temperature, and a model that fails once usually fails again). Retry adds cost without resolution. Backlog item: a "regenerate from same source" button on the failure bubble that re-runs with a stricter "DO NOT include markdown fences" reminder appended.

**What to log:** failure code (one of the 4 above), `intentId`, `entityName`, `runId`, `conversationId`, count of media attachments, total media bytes. **Never log:** raw model response text, attribute values from violations, file content. Per `feedback_rich_tool_descriptions.md` (P-22 contract): never echo LLM-supplied text into audit prose.

### Async-First Design

Spring AI's `ChatClient` exposes both `.call()` (blocking, returns `CallResponseSpec`) and `.stream()` (reactive, returns `StreamResponseSpec`).

**Phase 14 uses `.call()`, not `.stream()`** — three reasons:

1. `MapOutputConverter` parses one complete JSON document. Streaming partial JSON adds a stitching layer (e.g. JSONStream parser) that does not exist in Spring AI 1.1.4 and is not worth building for an extraction call that returns ~256–4096 tokens total.
2. The extraction call is internal — it happens inside the `prepare_form_draft` tool body, behind the user-visible streaming chat. The user sees the surrounding chat stream (Phase 12); they don't see the extractor's prompt/response cycle directly.
3. Bean Validation requires the full DTO. There is no useful intermediate state to render.

**Common mistake to avoid:** wrapping `.call()` in `Mono.fromCallable(...)` and subscribing on the Vaadin UI thread. Vaadin Flow is single-threaded per session (a `UI.access(...)`-required model); doing reactive subscription on the UI thread blocks the same thread we just freed. The existing `ChatStreamingSchedulerConfig` (Phase 9) already routes `chatClient.prompt().stream()` work onto a dedicated scheduler — Phase 14's `.call()` runs inside the tool-call path, which is already off the UI thread because Spring AI executes tools on the streaming scheduler.

**Stream vs. call rule of thumb for this codebase:**
- Surrounding chat → `.stream()` on the streaming scheduler (Phase 12, unchanged).
- Tool body that needs structured output → `.call()` and let the outer stream advance to the next message after the tool returns (Phase 14).
- Tool body that needs simple text output and is short → `.call()` is fine; do NOT introduce streaming inside a tool body.

### Prompt Engineering Discipline

**System vs. user prompt separation.** Two distinct, never-mixed concerns:

- **System prompt** (composed by `AgentSystemPromptRulesComposer`, Phase 9 + Phase 14 D-06 extension) — behavioral rules. Phase 14 adds: "When the user has selected intent `{label}`, you MUST call `prepare_form_draft("{intentId}", contextRefs)`. When extracted/generated values are incomplete or ambiguous, you MUST ask the user for missing information instead of inventing values." This is policy, not data.
- **User prompt** (composed by `MetaClassDtoSynthesizer`, Phase 14 D-01) — the JSON-schema instruction for THIS turn's entity. This is data shape, not policy.

Crossing these (e.g. injecting the schema into the system prompt) leaks per-turn entity details into conversation memory and corrupts subsequent turns; injecting policy into the user prompt makes it ignorable when the user appends their own text.

**Few-shot guidance.** Phase 14 ships **zero** few-shot examples in v1.1. The schema instruction is the only structural guidance the model gets. Reasons:
- Adding few-shot per entity multiplies prompt tokens by 3–5x and creates a maintenance liability for hosts adding their own intents.
- The reference Customer extractor exists precisely so future hosts can copy it as a code-level template; adding few-shot strings would conflate runtime guidance with developer documentation.
- If a specific intent demands few-shot for a weak-JSON-adherence model, the host adds it inside their own `IntentExtractor.extract(...)` body — engine stays clean.

**Token-budget discipline.**
- `maxTokens` is set explicitly via the active `AiParameters` profile (default 4096). Never leave unbounded — OpenRouter and OpenAI-compatible endpoints will happily run a runaway response until they time out and bill the full streamed tokens.
- The schema instruction MUST be cap-bounded by D-03 exclusion rules (collections / system audit fields / non-modifiable attrs excluded). A buggy `MetaClassDtoSynthesizer` that included `@OneToMany` collections would inflate the prompt by every related row and silently push the call past context limits.
- Tool descriptions follow the project's rich-tool-description convention (~50–150 lines per `feedback_rich_tool_descriptions.md`). This is paid once per turn (cached server-side by some providers, prompt-cache-friendly across turns by others) and is worth the tokens for correctness on enterprise data tools.

### Context Window Management

Phase 14 is **single-turn, single-prompt** — the extraction call does not consume conversation history (the `ChatClient` advisor chain handles memory transparently for the surrounding chat). What Phase 14 does manage:

- **Per-turn-all media resolution** (D-18, Phase 13.1) — `AiTaskFileMediaResolver.resolveActive(conversationId)` returns ALL non-expired `AiTaskFile` `Media` for the conversation. Phase 13.1's `perTurnMaxFiles` and `perTurnMaxTotalBytes` caps already apply LRU eviction on `createdDate DESC` if the budget is exceeded — Phase 14 inherits this for free; do NOT re-implement budget logic in `ExtractionService`.
- **Zero-file fallback** (D-19) — when `taskFileMedia` is empty, the extractor falls back to `userMessage` text alone. The reference Customer extractor handles both paths in the same `chatClient.prompt().user(...).call()` shape; no branching `if (media.isEmpty())` required.
- **Schema attribute exclusion** (D-03) — collection attrs (`@OneToMany`, `@ManyToMany`) excluded from schema. Prevents unbounded prompt expansion when a host registers an intent on an entity with deep relationships. EXTRACT-11 (multi-record extraction) is the deferred path that would re-introduce collections.
- **Single-extraction-per-turn invariant** (D-05, single-intent constraint) — `prepare_form_draft` may be called at most once per turn; the hard tool gate makes recursion structurally impossible. Operators do not need to tune iteration caps for Phase 14.

### Cost and Latency Budget

Per-call cost depends on the active `AiParameters` profile model. Reference numbers at the time of writing:

| Component | Default profile (Qwen3.6-35B-A3B via OpenRouter) | Notes |
|-----------|--------------------------------------------------|-------|
| Input — schema instruction (Customer, 3 fields) | ~30 tokens | Bounded by D-03 |
| Input — system prompt + named-intent rule | ~400 tokens | Mostly the rich-tool-description |
| Input — user message (typical) | 50–500 tokens | User-supplied |
| Input — media (per PDF page rendered as image) | ~1024 tokens/page | Vision model overhead — dominant for multi-page PDFs |
| Output — JSON response (3-field Customer) | ~80 tokens | Larger entities scale linearly |
| **Total per extraction (single PDF, Customer)** | ~2K input + ~80 output ≈ **$0.0005/call** at $0.20/M input, $0.40/M output | At Qwen3.6-A3B OpenRouter pricing (May 2026; verify before quoting to ops) |
| **Total per extraction (10-page PDF)** | ~12K input + ~80 output ≈ **$0.0025/call** | PDFs are 3-5x cost increase per page |

Latency: p50 ≈ 2-4s for single-PDF extraction; p95 ≈ 8s on Qwen3.6-A3B via OpenRouter. Vision models on weaker open-weights endpoints can spike to 15s+; p99 alerting threshold should be set per profile in operator monitoring.

**Caching strategy:**
- **Exact-match caching: NOT applicable.** Each extraction is a fresh user prompt over fresh user-attached media. Two users uploading the "same" customer-info PDF will produce different bytes (PDF metadata, scan timestamps); even the same user re-uploading the same file has a fresh `AiTaskFile.id`. No legitimate cache key exists.
- **Semantic caching: NOT applicable.** The whole point of extraction is per-document specificity; semantic equivalence between two customer PDFs is not a property we want to exploit.
- **Prompt prefix caching (provider-side):** the system prompt + named-intent rule + tool description IS a stable prefix. OpenAI-compatible endpoints with prefix-caching (Anthropic, OpenAI ≥1106, some OpenRouter providers) will discount this portion automatically. Phase 14 does not opt-in or out — it just composes the prompt the same way every turn and lets the provider handle it.

**Sub-task model routing: NOT used in v1.1.** Phase 14 runs the entire extraction on a single profile (the active `AiParameters` profile). Trade-offs:
- Pro: simpler audit trail, single model accountability, no fan-out cost on routing logic.
- Con: extraction inherits whatever temperature the profile sets (often tuned for chat, not extraction). Operators can clone the profile for an extraction-tuned variant when this becomes a bottleneck.
- Backlog: per-intent model override on the SPI (`IntentExtractor.profileOverride() : Optional<String>`) — declined for v1.1 to keep the SPI surface minimal.

## 5. Evaluation Strategy

> Every dimension below is grounded in either a Critical Failure Mode (CFM-1..5 from Section 1) or a Section-1b rubric ingredient (Layer-1 user-effort floor / Layer-2 senior-data-steward criteria). Generic AI-eval theory is not the source — Section 1b is.

### Dimensions

| # | Dimension | Grounded in | Rubric (Good vs Bad) | Measurement | Priority |
|---|-----------|-------------|----------------------|-------------|----------|
| E-1 | Field-level extraction accuracy | Layer-2 rubric: "values match the source verbatim where possible" | **Good:** for v1.1 Customer reference fixtures, ≥ 0.9 of fixtures yield Customer.name / email / phone matching ground truth after canonicalisation (case-fold for email, digits-only for phone, trim+collapse-whitespace for name). **Bad:** < 0.75, or any single fixture flips a digit / domain. | Code-eval — string match on canonicalised value vs ground-truth manifest. Host-supplied intents must ship their own labelled fixtures; v1.1 reference covers Customer only. | Critical |
| E-2 | Field-level completeness (recall on required-and-source-present fields) | Layer-1 rubric: "save the user typing" | **Good:** ≥ 0.7 of fields whose value is unambiguously present in the source are populated. **Bad:** < 0.5 or any required-and-clearly-present field is left empty in > 1 fixture. Fields with no source signal must be left empty (an empty field is correct, not a recall miss). | Code-eval — manifest declares per-field `source_present: bool`; recall = populated ∩ source_present / source_present. | High |
| E-3 | Schema discipline | CFM-2 (schema-violation), Layer-2 rubric: "no extra keys, types match" | **Good:** 100% of `MapOutputConverter` outputs parse without `JsonProcessingException`; 0 extra keys; 0 wrong-typed values across the 20-fixture run. **Bad:** any parse failure, any extra key, any field where the LLM emitted `int` for a string-typed attribute. | Code-eval — instrument the converter to record both raw JSON and parsed Map; assert `extra_key_count == 0`, `parse_failures == 0`, `type_mismatch_count == 0`. | Critical |
| E-4 | Source-faithfulness / fabrication rate | Layer-2 rubric: "values match the source verbatim, no invention" + `project_self_hostable_models_only.md` (open-weights models in the 20–35B range are more prone to confabulation than frontier models, so we measure rather than assume) | **Good:** ≥ 0.95 of populated fields have a value that an independent judge can locate in the input source (PDF text, OCR'd image text, or chat message). **Bad:** any fabricated email domain, fabricated phone number, or invented company suffix on the name. | LLM judge calibrated against senior-data-steward labels (target ≥ 0.7 correlation); 100% of fabrication-flagged fixtures escalated to human review. No automated way to detect fabrication on novel sources, so the judge runs only on the labelled reference set + sampled production drafts (Section 7). | High |
| E-5 | Format normalisation observability | Layer-1 rubric: "I shouldn't have to reformat after Save" | **Good:** track per-fixture whether email is lowercase, phone is E.164-or-local-canonical, name is trimmed; record as observation only. **Bad:** N/A for v1.1 — the LLM emits whatever the source said and downstream Jmix `@Email` / Bean Validation catches gross errors. Phase 14 does not prescribe normalisation; the eval surface exists so a future phase can decide whether to normalise upstream (prompt) or downstream (entity setter). | Code-eval — regex-based observers; emits metrics, does not pass/fail the run. | Medium |
| E-6 | Tool-surface integrity | CFM-1 (tool-surface leak), TEST-15 | **Good:** `ToolNavigationLeakScannerTest` finds zero `@Tool` methods that are not on the explicit allow-list; zero `EntityValues.setValue` calls inside `DraftLoader` (extension to the existing scanner). **Bad:** any leak — fail the build. | Code-eval, runs in `./gradlew test` on every CI run. NOT a Phoenix experiment — the "reference dataset" is the source tree itself, the "judge" is the scanner. | Critical |
| E-7 | Cross-tenant draft isolation | CFM-4, REQ-2 | **Good:** multi-user `@UiTest` confirms user A cannot read user B's draft via any chat-button click, any deep-link, or any `DraftLoader` invocation. **Bad:** any path that surfaces another tenant's `payloadJson`. | Code-eval (`@UiTest` from REQ-2). Not an LLM-eval; listed here for completeness because cross-tenant isolation is the highest-stakes Phase 14 invariant. | Critical |
| E-8 | Privilege-escalation guard | CFM-3, REQ-10 | **Good:** `DraftLoaderTest` feeds a `payloadJson` containing a denied attribute; assertion verifies (a) the field is empty in the loaded entity, (b) `setValueIfPermitted` was called rather than `setValue`, (c) the audit row records `deniedAttributes >= 1`. **Bad:** the denied attribute appears on the entity, or the audit row's denied-count is 0. | Code-eval — JUnit. | Critical |
| E-9 | Idempotency under re-click | CFM-5, D-11 | **Good:** `@UiTest` clicks the chat confirm button twice while the draft row exists; both clicks open the same prefilled detail view; no duplicate audit rows beyond the documented two-row append-only pair (D-12). **Bad:** second click opens a stale form, throws, or persists a second tool-call audit row. | Code-eval (`@UiTest`). | High |
| E-10 | User-effort floor | Layer-1 rubric: "the prefill saved time vs typing manually" | **Good:** sampled drafts that the user Saves without editing more than 1 of 3 fields. **Bad:** sustained pattern where users edit ≥ 2 of 3 prefilled fields before Save (the prefill is a net negative). | Human-judge via thumbs-up/thumbs-down on the assistant message bubble. **Phase 15+ candidate** — NOT in scope for Phase 14 implementation, but the Phase 14 audit data model must anticipate it (the `ai_audit_event.outcome` column already supports adding a `user_feedback` follow-up event without schema changes). | Medium |
| E-11 | Multimodal grounding | Layer-2 rubric: "image / PDF content is actually read, not hallucinated from filename" | **Good:** sentinel test images (10 fixtures, controlled content) yield extracted values that match the sentinel content for ≥ 0.9 of fixtures. **Bad:** the LLM returns values that match the filename or surrounding chat text rather than the image bytes — strong signal that Media injection is broken. | Code-eval — sentinels carry unique tokens (e.g. `name = "ZQX-Sentinel-001"`) that cannot appear elsewhere; mismatch ⇒ Media wiring is broken, not a model issue. | High |
| E-12 | PII handling / chat-memory leak | Layer-1 rubric: "my customer data should not turn up in another conversation" + Layer-2 rubric: "no PII leaks into embeddings or audit free-text" | **Good:** (a) `JdbcChatMemoryRepository` rows for conversation X contain no PII from conversation Y; (b) pgvector embeddings table contains no rows tagged with the extracted PII; (c) `ai_audit_event.arguments_json` and `result_summary` truncate per Phase 12 bounds (≤ 8 KB / ≤ 2 KB) and contain no full PDF body. **Bad:** any cross-conversation PII appearance, any embedding row containing a customer email, any audit row exceeding the bounds. | Mix: code-eval (SQL queries + grep over the audit table after the 20-fixture run) + manual review for the embedding table. | High |

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Schema-violation guardrail** (CFM-2) | `MapOutputConverter` throws `JsonProcessingException` on the tool result | **Block** — no draft persisted; audit row written with `outcome=FAILED`, `failureReason=schema_parse`; user-facing notice "Could not extract — try again or fill the form manually". Explicitly NO silent fallback (a partial draft from a parse-failed payload is worse than no draft). |
| **Exposure-rule guardrail** (CFM-3, Phase 10) | The intent's target entity is not exposed to the current user via `EntityExposureService` | **Block** — no extraction call, no LLM round-trip, no draft; audit `outcome=DENIED denialReason=entity_not_exposed`. |
| **Tool-gating guardrail** (D-05) | `intentId` non-null but not present in `IntentRegistry.eligibleFor(currentUser)` | **Block** — audit `outcome=DENIED denialReason=intent_not_eligible`. The eligibility check happens BEFORE the LLM call so a denied intent never reaches the model. |
| **Per-attribute permission guardrail** (REQ-10, CFM-3) | Any `payloadJson` key whose attribute is denied by `AccessManager` for the current user | **Block at apply-time** in `DraftLoader` — `setValueIfPermitted` skips the field, increments `deniedAttributes`. Static-banned: raw `EntityValues.setValue` calls inside `DraftLoader` (extension to `ToolNavigationLeakScannerTest` — recommend filing as part of E-6). |
| **Per-turn invocation cap** (D-05) | LLM attempts a second `prepare_form_draft` call in the same turn | **Block** at framework level — the callback list is single-element per turn, the framework will not surface the second call. No audit row needed; the attempt cannot reach the tool. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|-------------------|-----------------------|
| **Schema-violation rate** per `(active_model, intent_id, week)` | 100 % of `outcome=FAILED, failureReason=schema_parse` audit rows aggregated weekly | If > 5 % for any (model, intent) bucket: page the operator — consider model upgrade, prompt refinement, or upstream document splitting. |
| **Source-faithfulness regression** (E-4) | Monthly LLM-judge re-run on the full 20-fixture labelled set | If average score drops > 0.1 vs prior month: flag for senior-steward review; freeze the active `AiParameters` profile until root cause identified. |
| **Cross-tenant audit-grep** (CFM-4) | Weekly SQL: `SELECT COUNT(*) FROM ai_audit_event WHERE event_name = 'prepare_form_draft' AND user_username <> json_extract(arguments_json, '$.requestedAs')` | Must always be 0. Any non-zero result = page security on-call IMMEDIATELY (see Section 7 alert thresholds). |
| **Stale-draft re-click count** (CFM-5) | Weekly grep for `event_name = 'draft_loader_failed'` AND `failureReason = 'draft_gone'` | Sustained large counts = TTL too short or users routinely returning to old conversations. Tune `ai.intent.draft.ttl` (D-11). |
| **Denied-attribute rate** (REQ-10) | Weekly average of `deniedAttributes` field on successful draft applies | Sustained value > 1 means the intent's schema synthesis is offering fields the user can't modify. Re-scope the intent's column set or split into a viewer-vs-editor variant. |

## 7. Production Monitoring

**Tracing Tool:** **Arize Phoenix** (self-hosted) — same instance as the eval tooling, single OTel exporter target. Phase 12 already enabled `management.tracing` in the chat surface; Phase 14 just needs `spring-ai-observation-*` enabled (verify module ID via Context7 → `/spring-projects/spring-ai`) and the spans tagged with the Phase-14-specific attributes:

| Span Attribute | Source |
|---------------|--------|
| `intent.id` | `IntentRegistry` lookup result |
| `extraction.draft_id` | `AiIntentDraft.id` after persist |
| `extraction.outcome` | `success` / `denied` / `failed_parse` / `fabrication_flag` |
| `extraction.denied_attribute_count` | `DraftLoader` after `setValueIfPermitted` loop |
| `extraction.media_count` | number of attachments injected as `Media` for the turn |

**Key Metrics (5):**

| Metric | Definition | Steady-state Target |
|--------|------------|---------------------|
| `extraction.success.rate{intent_id}` | % of `prepare_form_draft` calls returning a draft (vs DENIED / FAILED) | ≥ 0.92 |
| `extraction.field_completeness{intent_id}` | average ratio populated:source-present per draft | ≥ 0.7 |
| `extraction.tool_call_latency_p95{intent_id}` | p95 wall-clock from tool invocation to draft persistence | ≤ 8 s text/image · ≤ 20 s PDF |
| `extraction.draft_save_rate{intent_id}` | % of drafts that progress to a successful entity Save (vs reaped by TTL) | ≥ 0.5 — low value means prefill is wrong often enough that users abandon |
| `extraction.denied_attribute_count{intent_id}` | average `deniedAttributes` per successful draft | ≤ 1 — high values mean schema synthesis is over-suggesting |

**Alert Thresholds:**

| Condition | Severity | Action |
|-----------|----------|--------|
| Cross-tenant audit-grep count > 0 (any window) | **CRITICAL — zero-tolerance** | Page security on-call IMMEDIATELY; freeze the chat surface for the affected tenant pending investigation. |
| `extraction.success.rate` < 0.85 sustained 1 hour | High | Page on-call engineer; check for upstream provider outage or model swap. |
| `extraction.draft_save_rate` < 0.3 sustained 24 hours | Medium | Email data-steward owner — prefill quality has degraded to net-negative. |
| `extraction.tool_call_latency_p95` exceeds target by > 50 % sustained 1 hour | Medium | Page on-call; usually upstream provider degradation. |
| Schema-violation rate > 5 % per (model, intent) for 1 week | Low (flywheel) | Operator-action ticket — consider model upgrade or prompt refinement. |

**Smart Sampling Strategy:**

| Sampling Class | Rate | Rationale |
|---------------|------|-----------|
| `outcome = DENIED` audit rows | **100 %** | Every denial is a signal — either a misconfigured exposure rule or an attempted privilege escalation. |
| `outcome = FAILED` audit rows | **100 %** | Schema breakage is rare and load-bearing for E-3; never sample-out. |
| Drafts saved-then-immediately-edited (≥ 2 of 3 fields edited within 30 s of Save) | **100 %** | Strong "prefill was wrong" signal; feeds the labelling queue. |
| `outcome = SUCCESS` saved drafts | **5 % random** | Production flywheel — drives the monthly fixture refresh. |
| Conversations with explicit user thumbs-down (Phase 15+ when capability lands) | **100 %** | Direct user-effort-floor signal (E-10). |

The 5 %-random + 100 %-of-concerning sampling shape is asymmetric on purpose: the cheap-to-judge cases get sampled densely, the expensive-to-judge happy path gets sampled lightly.
