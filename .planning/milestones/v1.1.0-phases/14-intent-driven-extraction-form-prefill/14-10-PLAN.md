<objective>
Close the Phase 14 human-UAT gap caused by the old static intent-picker design.

The corrected UX is:

1. Opening chat shows no Customer/entity/action intent card.
2. The user asks for an operation, for example "Create a product".
3. The assistant asks for missing required information first.
4. After enough data exists, the assistant emits a server-validated action proposal.
5. The UI renders action intents for the user to choose, for example "Create now" and "Prefill form".
6. The selected action intent controls the next tool surface:
   - Create now: execute the mutation path under the current user's Jmix security.
   - Prefill form: create a draft and render the existing "Open form to confirm" path; no save happens until the user confirms in the Jmix detail view.

This is the correct agent pattern for side-effecting enterprise actions: gather context, propose choices, wait for explicit user selection, then execute the selected action with a constrained tool surface. It supersedes the Phase 14 static registry picker on chat-ready.
</objective>

<architecture>
## New Terms

- **Entity intent**: the old Phase 14 `IntentExtractor` registry entry, such as "Customer from file". This remains a backend extraction capability, not an initial UI picker.
- **Action intent**: a post-clarification user choice, such as `create-now` or `prefill-form`.
- **Action proposal**: a structured, server-validated payload that says which operation is ready, which entity it targets, which values have been collected, and which action intents are allowed for this user.

## Detection Of "Enough Information"

Do not infer readiness from a visible card row. The assistant must call a safe planning tool, `propose_action_choices`, after it believes the request has enough structured data. The server validates the proposal against Jmix metadata and security:

- target entity exists and is visible to the current user.
- requested operation is supported.
- payload keys are writable attributes for that entity.
- required fields for the selected operation are present or explicitly marked missing.
- create/update action choices are offered only when the user has the required Jmix permissions.
- prefill-form is offered only when a draft can be prepared and the target detail view can be opened by the current user.

If validation reports missing fields, the tool returns a no-choice result that instructs the assistant to ask the user for those fields. The UI renders choices only for a valid `READY` proposal.
</architecture>

<risks>
- If `prepare_form_draft` remains tied only to `IntentExtractor`, `prefill-form` may not be available for entities without a registered extractor. The execution pass must either hide that choice or add a generic proposal-to-draft path.
- Blocking all default mutation tools may affect existing "just create it" chat behavior. This is intentional for create/update side effects under the clarified UAT, but read-only/default informational chat must remain unchanged.
- Action proposals are transient UI state unless persisted. Start with a view/session-scoped proposal store; persist only if UAT requires proposal survival across browser refresh or conversation reload.
</risks>
