### Notes — Intentional ROADMAP Deviation (Security Correctness)

ROADMAP.md SC #6 for Phase 13.1 says: *"Per-turn-all resolver uses `UnconstrainedDataManager` per Phase 13 invariant (`feedback_jmix_unconstrained_for_system_writes`)."*

The actual implementation in `AiTaskFileMediaResolver.java:103, 132` uses `DataManager` (NOT `UnconstrainedDataManager`). This deviation is INTENTIONAL and was locked at SPEC time:

- **SPEC §RES-01:** *"Resolver continues to use `DataManager` (NOT `UnconstrainedDataManager`) so user row-level policy applies."*
- **13.1-02-SUMMARY decisions[2]:** *"Resolver uses DataManager (NOT UnconstrainedDataManager) per threat T-13.1-05 — the AiAgentUserRowLevelRole.taskFile() row-level predicate (userUsername = :current_user_username) MUST apply to keep cross-user attachment leak structurally impossible."*

ROADMAP SC #6 carried over the wording from Phase 13's pattern (where the cleanup job legitimately uses `UnconstrainedDataManager` for system-internal writes), but the chat-turn read path on the user thread MUST honor row-level policy. The SPEC explicitly inverted this for the resolver. This is a security-strengthening change, not a regression. The SPEC is the locked phase contract; ROADMAP SC #6 should be updated post-milestone to reflect the correctness-driven inversion.

No override entry added to frontmatter because this is not a "missed" must-have — the SPEC's correct version IS implemented. Flagging here for transparency at milestone audit time.
