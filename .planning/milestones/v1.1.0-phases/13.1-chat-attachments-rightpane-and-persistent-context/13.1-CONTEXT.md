<decisions>
## Implementation Decisions

### NOTICE row preservation in `ProjectingChatMemoryRepository`

- **D-A1: Modify `saveAll` JPQL to exclude `role='notice'` from the delete pass.**
  - Source file: `ai-agent/ai-agent/src/main/java/com/vn/agent/orchestration/ProjectingChatMemoryRepository.java:85-86`
  - Current: `dataManager.load(AiMessage.class).query("select m from ai_AiMessage m where m.conversation.id = :cid")` then deletes all returned rows.
  - Target: change the JPQL to `select m from ai_AiMessage m where m.conversation.id = :cid and m.role <> :noticeRole`, parameter `noticeRole = AiMessageRole.NOTICE.getId()` (`"notice"`). Re-create logic untouched (already iterates Spring AI's `messages` list, which never contains NOTICE entries because Spring AI's chat-memory table is separate).
  - Rationale: 1-line query change, no schema change, no event subscriber, no race condition. NOTICE rows survive every chat turn projection because they are explicitly excluded from the wipe.
  - Rejected alternatives: (B) separate `AiAttachmentEvent` entity rejected — adds Liquibase 110 + role policy + UI merge logic for marginal isolation; (C) event-subscriber re-insert rejected — race-y and double-source-of-truth.

- **D-A2: NOTICE rows are NEVER fetched by Spring AI's chat-memory path.**
  - `ProjectingChatMemoryRepository.findByConversationId` (line 70-71) delegates to Spring AI's `JdbcChatMemoryRepository`, which reads its own `SPRING_AI_CHAT_MEMORY` table (schema separate from `AI_AGENT_MESSAGE`). NOTICE rows live ONLY in `AI_AGENT_MESSAGE`, so they are structurally invisible to the LLM-prompt path. SPEC REQ-5 "filter NOTICE from LLM prompt path" is therefore satisfied automatically — no explicit filter needed.
  - Acceptance test note for `NoticeFilterTest`: assertion is "Spring AI prompt builder never sees a NOTICE-derived `Message`" — trivially true given the table separation. Test still ships to lock the invariant.

### Card UI fields + actions

- **D-B1: Card content = icon + filename + meta hbox (createdDate + sizeBytes formatted) + 2 actions: open(download) + delete.**
  - Source file to port from: `D:/DTH/jmix-crm/.../ai-attachment-card-fragment.xml` (CRM card structure: `<card>` with `<headerPrefix><icon FILE_O></><header><h5 title/></><headerSuffix><button EXTERNAL_LINK/></><content><hbox><span timestamp/><span | separator/><icon source/><span source/></></content>`).
  - Target: new `ai-task-file-card-fragment.xml` mirrors CRM structure with these adaptations:
    - `<headerPrefix>`: keep generic `FILE_O` icon (or type-specific via simple extension mapping if trivial; defer the per-extension icon table to plan-phase as a nice-to-have).
    - `<header>`: `<h5 dataContainer="taskFileDc" property="filename"/>`.
    - `<headerSuffix>`: TWO buttons in an hbox — `<button id="openButton" icon="DOWNLOAD"/>` (CRM uses `EXTERNAL_LINK` for "open in same tab"; we explicitly use `DOWNLOAD` because Phase 13.1 always downloads, never inline-previews) + `<button id="deleteButton" icon="TRASH" themeNames="tertiary-inline small icon"/>`.
    - `<content><hbox>`: `<span dataContainer="taskFileDc" property="createdDate" classNames="text-secondary text-s"/>` + separator span + `<span id="sizeValue" classNames="text-secondary text-s"/>` populated programmatically with humanized size (`"12.3 KB"` / `"4.5 MB"`).
  - Renderer: new `AiTaskFileCardFragmentRenderer extends FragmentRenderer<JmixCard, AiTaskFile>` with `@RendererItemContainer("taskFileDc")`. Inject `Downloader` for open action; inject `DataManager` (or a thin `AiTaskFileService.delete(id)` wrapper) for delete action. Delete action: `dataManager.remove(row)` then `taskFilesDl.load()` to refresh the grid; `FileStorage.removeFile(row.getStorageRef())` runs synchronously before the row delete.
  - TTL countdown explicitly NOT shown — avoids per-second DOM churn and visual noise; admin/user understands TTL via documentation, not per-card UI.
  - Bilingual button labels: `chatView.attachments.action.download` + `chatView.attachments.action.delete` (both bundles).

- **D-B2: Delete confirmation dialog.**
  - Use Jmix `Dialogs.createOptionDialog()` with WARNING type and message `chatView.attachments.deleteConfirm` ("Remove attachment %s?" / "Xoá tệp đính kèm %s?"). Prevents accidental clicks.

### Empty-state asset

- **D-C1: Vaadin built-in `vaadin:cloud-upload` icon (size XL, `text-tertiary` class) + bilingual text.**
  - Source: `<icon icon="vaadin:cloud-upload" size="XL" classNames="text-tertiary"/>` + `<span text="msg:///chatView.attachments.emptyState"/>`.
  - Wrapper layout: centered vbox with vertical spacing, `visible` bound to `taskFilesDc.getItems().isEmpty()` (programmatic toggle in `ChatPanelFragment.refreshTaskFiles()`).
  - Rejected: copying CRM's Jmix logo SVG (brand mismatch — agent-core is not Jmix-branded); custom hand-drawn SVG (asset maintenance burden for marginal gain).
  - Asset zero-cost: no file added; ships in Lumo theme.

### Budget-exceeded UI feedback

- **D-D1: Toast notification on send when cap is hit, plus the audit row.**
  - Trigger: `AiTaskFileMediaResolver.resolveActive(...)` returns a `Resolved` result with a new boolean field `budgetExceeded` (in addition to `media`). When true, `DefaultChatServiceImpl` (or the surrounding chat-send handler in `ChatPanelFragment`) calls `Notifications.create(messageBundle.getMessage("chatView.attachments.budgetExceeded"), Notifications.Type.WARNING).show()`. Non-blocking, dismissible, default Lumo styling.
  - Bilingual key (mandatory now, was optional in SPEC §9): `chatView.attachments.budgetExceeded` = `Some attachments were not sent to the model (budget exceeded).` / `Một số tệp không được gửi cho mô hình (vượt giới hạn).`
  - Audit row continues exactly as SPEC AUDIT-01 specifies. UI feedback is additive, not a replacement.
  - Rejected: silent (user has no way to know why agent answer is incomplete); persistent banner (panel real-estate cost not justified for a transient event).

### Claude's Discretion

- Per-extension icon table for D-B1 `<headerPrefix>` (e.g. `vaadin:file-pdf`/`file-table`/`file-picture`) — small, reversible, not specified in SPEC. Plan-phase researcher decides whether to ship a simple extension-to-icon map or stick with generic `FILE_O`. If shipped, must be bilingual-key-free (icons only).
- Exact `splitterPosition` numeric value — SPEC REQ-1 says `splitterPosition="68"` (verbatim from CRM). If responsiveness on dialog-narrow needs adjustment, plan-phase may tune to 60–72 with a note in the diff.
- Whether `AiTaskFileService.delete(id)` is a new thin service class or the renderer calls `DataManager.remove` + `FileStorage.removeFile` directly — plan-phase decides based on whether the same delete logic is needed elsewhere.
- Choice of error-handling for `FileStorage.removeFile` failure during card-delete: log-and-continue vs surface to user. Suggested: log-and-continue (orphan blob will eventually be swept by cleanup job).

<code_context>
## Existing Code Insights

### Reusable Assets
- **`Downloader` (Jmix)** — already used by Phase 13's KB upload pattern; renderer's open-action just calls `downloader.download(row.getStorageRef())`.
- **`Notifications` (Jmix)** — for D-D1 budget-exceeded toast; standard Lumo styling, no custom CSS needed.
- **`Dialogs` (Jmix)** — for D-B2 delete-confirmation dialog; `createOptionDialog().withType(WARNING)` standard pattern.
- **`Messages` (Jmix `io.jmix.core.Messages`)** — per memory `feedback_jmix_messages_over_spring`; auto-locale, @NonNull, avoids nullable warnings feeding Notifications.
- **`FragmentRenderer<JmixCard, T>`** — base class for D-B1; `@RendererItemContainer` annotation provides the per-row data binding.
- **`JmixCard` Vaadin component** — supports `<headerPrefix>`, `<header>`, `<headerSuffix>`, `<content>` slots — exactly what CRM card uses; no custom card class needed.

### Established Patterns
- **Phase 13 upload pattern (`UploadHandler.toFile`)** — already wired in `ChatPanelFragment`; Phase 13.1 keeps it (memory `feedback_jmix_upload_receiver_deprecated`). The XML `<upload>` element gets the same Java-side `UploadHandler.toFile(...)` registration in `ChatPanelFragment.onReady`.
- **Phase 13 audit pattern (`AuditWriter.writeToolCall`)** — reused for `task_file_budget_exceeded` event; no new `AuditKind`.
- **Phase 12 fragment-mount pattern (`ChatSurfaceMounter` + `AiUiSettingsService`)** — both surfaces (`ChatView` FULL_ROUTE + `ChatDialogView` HEADER_BUTTON) mount the same `ChatPanelFragment`; one fragment edit lights up both surfaces.
- **`ProjectingChatMemoryRepository.saveAll` delete-recreate pattern** — preserved; D-A1 only adds a predicate to the delete query, doesn't change the recreate logic.
- **`messages.properties` + `messages_vi.properties` parity** — every new key MUST land in both bundles; `LocaleParityTest` enforces.

### Integration Points
- **`taskFilesDc` → grid render** — new collection container loaded by query `select e from ai_AiTaskFile e where e.conversation.id = :conversationId order by e.createdDate desc`. Loader subscribes to `PostLoadEvent` to toggle the empty-state vbox visibility.
- **Upload success → NOTICE insert** — in `ChatPanelFragment` upload handler, after `dataManager.save(taskFile)` succeeds, also create + save an `AiMessage` row with `role=NOTICE` and the bilingual notice text. Both saves in the same logical operation; if NOTICE save fails, log warn and continue (file upload itself is the user-visible event).
- **`DefaultChatServiceImpl.ask/.stream` → `resolveActive`** — replace existing `resolvePending(...)` + `markInjected(...)` calls with single `resolveActive(...)` call. The `Resolved` record's new `budgetExceeded` boolean drives the D-D1 toast trigger.
- **Liquibase 100 → `agentstore-changelog.xml`** — new include line in the root changelog.
- **Card delete → `taskFilesDl.load()`** — after `dataManager.remove(row)` + `FileStorage.removeFile(...)`, reload the loader to refresh the grid + recompute empty-state visibility.
