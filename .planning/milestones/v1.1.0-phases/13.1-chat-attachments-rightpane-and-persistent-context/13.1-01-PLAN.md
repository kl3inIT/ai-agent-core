## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Liquibase boot migration | Schema DDL runs as DB-admin role at boot; user-thread code never executes the drop |
| Spring `@ConfigurationProperties` binding | Operator-supplied property file values bind to `AiTaskFileProperties`; trust depends on filesystem access to `application.properties` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13.1-01 | Tampering | Liquibase 100 changeset content | accept | Liquibase changesets are checksummed by Liquibase itself; running with mismatched checksums fails the boot. Standard Liquibase invariant — no extra mitigation in this phase. |
| T-13.1-02 | Denial of Service | `ttl-seconds=-1` sentinel disables TTL purge → unbounded `AI_TASK_FILE` growth | accept (operator-driven) | Documented in JavaDoc on `AiTaskFileProperties.ttlSeconds`; operator who flips the sentinel acknowledges. FK cascade on conversation-delete still bounds growth. Audit/alerting for table growth is operator responsibility (out-of-scope). |
| T-13.1-03 | Information Disclosure | `AiMessageRole.NOTICE` value reused outside the upload-NOTICE path | mitigate | NOTICE rows are written ONLY by the upload handler (Plan 13.1-04); `ProjectingChatMemoryRepository.saveAll` (Plan 13.1-03) excludes them from the projection wipe so they cannot be smuggled into the LLM prompt. Test gate: `NoticeFilterTest` (Plan 13.1-06). |
| T-13.1-04 | Repudiation | Schema migration leaves no audit trail | accept | Liquibase records every changeset in `DATABASECHANGELOG` table with author/dateExecuted/checksum — already captured. No `AiAuditEvent` row warranted for a one-time DDL. |
</threat_model>
