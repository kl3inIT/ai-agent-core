# Phase 13.1: Code Review Report

## Summary

Reviewed the CRM-style attachment pane, persistent task-file resolver, NOTICE row projection, Liquibase schema cutover, i18n, security roles, and phase tests. The main blocker is the `ttl-seconds=-1` lifecycle contract: it currently disables only the scheduled cleanup job, while uploaded rows still get a normal 24h `expiresAt` and chat turns still invoke direct expired-row deletion.

IDE inspections were run on the high-risk Java/XML files. Context7 Jmix docs were checked for `MessageBundle` lookup behavior; `MessageBundle` infers the fragment package group, which matters for WR-03.

## Critical Issues

### CR-01: `ttl-seconds=-1` still expires and can delete task files

**Severity:** BLOCKER
**Files:**
- `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/ChatPanelFragment.java:877`
- `ai-agent/ai-agent/src/main/java/com/vn/agent/DefaultChatServiceImpl.java:263`
- `ai-agent/ai-agent/src/main/java/com/vn/agent/taskfile/AiTaskFileMediaResolver.java:132`

**Issue:** Phase 13.1 LIFE-01 defines `ai-agent.task-file.ttl-seconds=-1` as "no TTL; only delete on conversation delete". The implementation only applies that sentinel in `AiTaskFileCleanupJob`. Uploads still stamp `expiresAt = now + 86400` when the sentinel is configured, and `resolveActive()` filters on `e.expiresAt > :now`. After 24h, those rows become invisible to the model even though the operator explicitly disabled TTL. Worse, both blocking and streaming chat paths call `taskFileRepository.deleteAllExpired(now)` directly, bypassing the cleanup job's sentinel guard, so old sentinel-mode rows can be deleted on the next chat turn.

**Impact:** The "persistent multi-turn context" contract breaks for long sessions and sentinel-mode deployments. Operators choosing no TTL can still lose attachment context and backing blobs.

**Fix:** Centralize TTL purge gating instead of calling the repository directly from chat paths. In sentinel mode, set upload `expiresAt` to a non-expiring value such as `OffsetDateTime.MAX`, or update the resolver predicate to treat sentinel-mode rows as active. Add a regression that sets `ttl-seconds=-1`, uploads/seeds an old row, invokes `DefaultChatServiceImpl.ask()` or `stream()`, and asserts the row remains and `resolveActive()` still returns it.

## Warnings

### WR-01: Server-side upload size validation trusts upload metadata instead of the staged file

**File:** `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/ChatPanelFragment.java:826`

**Issue:** `handleUploadedFile()` enforces the 100 MB cap using `uploadMetadata.contentLength()` passed into the upload handler. That value is request metadata, not the actual size of the temp file that was streamed to disk. If it is missing, wrong, or bypassed, the "server-side" check can accept an oversized staged file and then persist it with the same unverified `sizeBytes`.

**Impact:** The attachment cap can be bypassed or mis-accounted, which can inflate file storage usage and undercount resolver budget totals.

**Fix:** Measure `Files.size(tempFile)` inside `handleUploadedFile()` and use that value for the cap check and `AiTaskFile.sizeBytes`. Treat negative or unavailable metadata as untrusted.

### WR-02: NOTICE rows drift out of transcript order after later chat turns

**Files:**
- `ai-agent/ai-agent/src/main/java/com/vn/agent/orchestration/ProjectingChatMemoryRepository.java:86`
- `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/ChatPanelFragment.java:378`

**Issue:** `ProjectingChatMemoryRepository.saveAll()` preserves NOTICE rows but deletes and recreates every non-NOTICE message with `createdDate = OffsetDateTime.now()` on every save. `ChatPanelFragment` replays history with `order by m.createdDate asc, m.seq asc`. After a later chat turn, older USER/ASSISTANT messages get fresh timestamps, while the preserved NOTICE keeps its original timestamp, so the notice can move earlier than the messages it was originally between.

**Impact:** The upload ledger no longer renders inline "between message bubbles" after subsequent turns, undermining UX-01 and making the transcript misleading.

**Fix:** Preserve existing projected message timestamps/sequence numbers, or merge NOTICE rows into the projected sequence when recreating memory. Add a test that seeds USER/ASSISTANT, writes a NOTICE, calls `saveAll()` with a longer cumulative chat history, then asserts replay ordering stays USER -> ASSISTANT -> NOTICE -> next USER.

### WR-03: Attachment-card i18n lookup uses the fragment package group, but keys are in the root bundle

**File:** `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/AiTaskFileCardFragmentRenderer.java:78`

**Issue:** The renderer injects `MessageBundle` and calls `messageBundle.getMessage("chatView.attachments.*")`. Jmix `MessageBundle` infers the message group from the view/fragment class package. The actual keys were added to the root `com.vn.agent` bundle (`messages_en.properties:512` etc.), so IDE inspections report every lookup as missing under `com.vn.agent.view.chat.fragment/...`.

**Impact:** Download/delete ARIA labels and delete-confirm dialog text can render raw keys instead of localized text.

**Fix:** Inject `io.jmix.core.Messages` and use the root-group form, for example `messages.getMessage("com.vn.agent", "chatView.attachments.action.download")`, or set an explicit `messagesGroup` for the renderer/descriptor and add coverage that resolves all renderer keys through the same API used at runtime.

### WR-04: Attachment delete removes the DB row before deleting the blob

**File:** `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/AiTaskFileCardFragmentRenderer.java:121`

**Issue:** `performDelete()` calls `dataManager.remove(row)` first, then attempts `storage.removeFile(ref)`. If blob deletion fails, the pointer row is already gone, so `AiTaskFileCleanupJob` cannot discover the orphan later. This is the opposite of `AiTaskFileRepository.deleteRow()`, which intentionally removes the blob before the row to avoid orphaning.

**Impact:** A transient file-storage failure during manual delete can permanently orphan blobs.

**Fix:** Reuse `AiTaskFileRepository.deleteRow()` with a user-authorization check, or mirror its blob-first ordering: delete blob, then remove row; if blob removal fails, keep the row and show a warning so the retry path remains possible.

### WR-05: Attachment delete does not refresh the right-pane collection

**File:** `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/AiTaskFileCardFragmentRenderer.java:139`

**Issue:** The renderer comment says the grid refresh is triggered by `ChatPanelFragment`, but no listener exists. The fragment reloads `taskFilesDl` after upload and on conversation switches only. Deleting an item through the card removes it from the database, but the `taskFilesDc` collection and empty-state toggle are not reloaded.

**Impact:** Users can see stale cards after delete, and the empty state may not appear until a manual navigation/reload.

**Fix:** Emit a fragment/host event after successful delete and have `ChatPanelFragment` reload `taskFilesDl`, or pass a refresh callback into the renderer using an established Jmix renderer pattern. Add a UI/source test covering delete -> loader reload -> empty-state visible when the last row is removed.
