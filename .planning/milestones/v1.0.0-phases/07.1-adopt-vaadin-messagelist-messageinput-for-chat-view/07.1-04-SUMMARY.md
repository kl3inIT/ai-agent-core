# Phase 7.1 Plan 04: Slim ChatView to Route Shell — Summary

One-liner: Trimmed `ChatView.java` from 128 LOC to 89 LOC so it now only owns the `@Route("ai-agent/chat")` shell, `conversationId` query-param binding, and a `Dialogs`-gated New-chat confirm — all transcript/streaming/cancel logic lives in `ChatPanelFragment` (07.1-03); the confirm path calls `startNewChat()` and is gated by `!hasMessages() && !isStreaming()`.

## Fragment Public Methods Consumed

ChatView (Plan 04) calls into `ChatPanelFragment` (Plan 03 Public API) exclusively through:

| Fragment method                        | ChatView caller                                          |
| -------------------------------------- | -------------------------------------------------------- |
| `setConversationId(UUID)`              | beforeEnter — null-path (no query param), invalid-UUID path (error + reset to null), happy-path, ConversationNotFoundException catch (error + reset to null) |
| `hasMessages()`                        | newChat bypass-gate (skip confirm when empty)            |
| `isStreaming()`                        | newChat bypass-gate (skip confirm only when NOT streaming) |
| `startNewChat()`                       | newChat bypass path + confirm YES handler                |

`getConversationId()` is NOT consumed in ChatView (Fragment uses it internally for its own mid-stream swap logic).

## Deviations from Plan

### Rule 1 — Bug / correctness fixes

**1. [Rule 2] Explicit `setConversationId(null)` on the no-param beforeEnter path**

- **Found during:** Task 2 rewrite.
- **Issue:** Plan pseudocode uses early `return` when `idValues.isEmpty()`. The prior ChatView also returned early. But when the user navigates away from a loaded conversation and back to `/ai-agent/chat` (no param), the Fragment retains its prior `conversationId` state, including the loaded transcript. This is a latent correctness bug: the URL no longer has a param but the view still shows the prior conversation.
- **Fix:** Call `chatPanelFragment.setConversationId(null)` before returning on the no-param path so the Fragment clears to an empty chat state matching the URL.
- **Files modified:** ChatView.java (beforeEnter, lines 48–51).
- **Commit:** `ba357f4`.

### Rule 3 — Blocking / scope expansion

**2. [Rule 3] Locale bundles edited despite not being in files_modified frontmatter**

- **Found during:** Task 2 i18n acceptance grep requirements.
- **Issue:** Plan frontmatter `files_modified` lists only `ChatView.java` + `chat-view.xml`, but Task 2 body explicitly scopes `messages_en.properties` + `messages_vi.properties` ("add key-value pairs to BOTH `messages.properties` AND `messages_vi.properties`"). Task 2 acceptance grep requires `^chatView\.newChat\.confirmHeader=` present in both bundles with exactly one hit each. Frontmatter was incomplete.
- **Fix:** Applied the task-body scope (plan body overrides frontmatter when there is an inconsistency, and Rule 3 covers scope expansions needed to complete the current task). 3 new keys added to both bundles in the Task 1 commit for atomicity (keeps Task 2 commit to the one Java file).
