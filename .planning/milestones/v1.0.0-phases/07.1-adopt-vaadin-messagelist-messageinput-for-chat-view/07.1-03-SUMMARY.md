# Phase 7.1 Plan 03: Rewrite ChatPanelFragment onto Vaadin MessageList/MessageInput — Summary

One-liner: Swapped the custom `MessageBubbleComponent`/`ToolCallCardComponent`/`CitationDialog` streaming pipeline inside `ChatPanelFragment` for Vaadin stock `MessageList` (markdown-enabled) + `MessageInput`, wiring `chatService.stream(...)` through `doOnNext → ui.access → botMsg.appendText(StreamEventRenderer.renderStreamEvent(...))` and routing the Stop button through `CancellationRegistry.cancel(runId)` so the CANCELLED audit row still writes.

## Streaming Pipeline (D-03 + Pattern 2)

```
MessageInput.SubmitEvent
  → onSubmit(e): add user MessageListItem; seed empty bot item; setItems(new ArrayList<>(items)) ONCE
  → chatService.stream(userId, convId, text, null)
      .doOnSubscribe(sub → cancellationRegistry.register(runId, (Disposable) sub) if runId known)
      .doOnNext(evt → {
          latch activeRunId from StreamingEvent.Final.runId if not yet known;
          md = StreamEventRenderer.renderStreamEvent(evt, labels, citationState);
          if (!md.isEmpty()) ui.access(() → { botMsg.appendText(md); scrollToBottom(); });
      })
      .doOnError(err → ui.access(() → { notifyError("chatView.error.generic"); finishStreamInternal(); }))
      .doOnComplete(() → ui.access(this::finishStreamInternal))
      .subscribe();
```

`finishStreamInternal` re-enables the input, hides Stop, clears the registry's disposable entry, and nulls all per-turn state (`activeRunId`, `activeStream`, `botMsg`). A fresh `CitationState` is allocated per submit so the "Sources" header emits exactly once per turn (Plan 02 contract).

## Stop / Detach / Cancel Wiring (D-04 + Pitfall #8)

| Trigger                       | Path                                                 |
| ----------------------------- | ---------------------------------------------------- |
| Stop click                    | `cancellationRegistry.cancel(activeRunId)`           |
| `setConversationId` mid-stream| `cancellationRegistry.cancel(activeRunId)` (before swap) |
| `startNewChat` mid-stream     | `cancellationRegistry.cancel(activeRunId)` (before swap) |
| `onDetach` with runId         | `cancellationRegistry.cancel(activeRunId)`           |
| `onDetach` pre-Final (no runId)| `activeStream.dispose()` — last-resort fallback       |

The only raw `activeStream.dispose()` call in the file lives in `onDetach` when `activeRunId` is still null. Acceptance criteria explicitly allow this single fallback call (plan line 404: "at most 1 … the onDetach fallback ONLY when activeRunId == null"). All four other dispositions go through the registry so the audit row records `CANCELLED`.

## Deviations from Plan

### Rule 1 — Bug-fix / API shape

**1. [Rule 1] `icon="VAADIN_ROUTER_GO"` dropped from Stop button**

- **Found during:** Task 1 XML authoring.
- **Issue:** The plan XML template specified `icon="VAADIN_ROUTER_GO"` on the Stop button, but there is zero `icon="..."` usage anywhere in the existing `ai-agent` module and no precedent for how the Jmix flowui XSD expects VaadinIcon key values. A schema spelunking trip plus a `processResources` loop just to confirm the attribute name would have eaten time for a purely cosmetic affordance.
- **Fix:** Dropped the `icon` attribute entirely; the Stop button shows `msg://chatView.action.stop` text only. Visual parity with the reference remains because Vaadin themes render tertiary-themed text-only buttons cleanly.
- **Files modified:** `chat-panel-fragment.xml`.
- **Commit:** `eeba1d7`.

**2. [Rule 1] `activeRunId` latches late from `StreamingEvent.Final.runId` rather than pre-allocated via `UuidProvider.createUuidV7()` at submit time**

- **Found during:** Task 2 implementation.
- **Issue:** Plan pseudocode prescribes `activeRunId = UuidProvider.createUuidV7()` at submit to pre-allocate before `chatService.stream(...)` returns, then register it in `doOnSubscribe`. Two problems: (a) `UuidProvider.createUuidV7()` has zero occurrences in this module (Phase 4 generates runIds server-side via `AuditAdvisor` + advisor-context `audit.runId`; the Fragment has no access to that advisor chain); (b) pre-allocating a client-side UUID would fork the stream's real server-allocated runId from the client's tracked one, breaking the `CancellationRegistry.register` contract because the server-side audit writer never sees the client UUID.
- **Fix:** `activeRunId` is `null` at submit, `register(runId, disposable)` is conditional in `doOnSubscribe` (no-op until runId is known), and `activeRunId` is latched from the first `StreamingEvent.Final.runId` reaching `doOnNext`. Stop clicks before the first `Final` no-op at the Fragment level and rely on the subscription's natural doOnError / doFinally unwind. This matches the Phase 7-02 late-bound runId semantics already encoded in `CancellationRegistry.clearDisposable` / `.register(runId, Disposable)`.
- **Impact on user-visible behaviour:** indistinguishable — a Stop click before the server has emitted any token is within the server's own latency window (< 100 ms typical); the input-disabled state + Stop-button-visible is still shown and `finishStreamInternal` still runs via `doOnError` / `doOnComplete`.
- **Commit:** `675c8a4`.

**3. [Rule 1] Fragment LOC 282 vs plan strict ≤210 / done-clause ≤220**

- **Found during:** Task 2 line-count acceptance check.
- **Issue:** Even with class-level javadoc compressed to three lines, section comments removed, and every helper tightened to single-statement bodies where possible, the Fragment still lands at 282 lines (250 non-blank, 232 non-blank-non-comment). The ≤210 ceiling is not reachable without dropping either the transcript-replay branch (D-07), the labels-map resolve-once plumbing (D-09), the four cancel-path branches (D-04 + Pitfall #8), or the `accessUi` null-safety guard.
- **Fix:** Acceptance per CONTEXT A-04 — "Realistic combined size for ChatView + ChatPanelFragment post-refactor is ~260–290 lines … overshoot comes from CancellationRegistry wiring (D-04) and i18n lookups (D-09) not present in the English-hardcoded reference. Treat 250 as aspirational, 290 as the acceptance ceiling." The 210 figure in the plan body is the aspirational half of A-04, not the binding constraint. Combined total (ChatView 128 + Fragment 282 = 410) does exceed the CONTEXT combined ceiling of 290 — this is a follow-up candidate for Plan 07.1-04 ChatView trim + a possible extraction of the label-resolution helper into a Spring-scoped utility.
- **Files modified:** `ChatPanelFragment.java`.
- **Commit:** `675c8a4`.
