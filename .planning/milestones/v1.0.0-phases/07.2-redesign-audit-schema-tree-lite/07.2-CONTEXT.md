# Phase 7.2: Redesign Audit Schema as Tree-Lite - Context

**Gathered:** 2026-04-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the flat `AI_AGENT_TOOL_CALL_AUDIT` table + `KIND`/`PHASE` discriminators with a self-referential `PARENT_ID` FK ("tree-lite"). One chat turn = exactly one root row (`PARENT_ID = null`, `kind = CHAT`); `TOOL` / `RETRIEVAL` / future `GUARDRAIL` events are children linked via `PARENT_ID`. Collapse the `PHASE = PRE/POST` dual-row pattern into one row per event with `startedAt` + `finishedAt`. Rename entity to `AiAuditEvent`, table to `AI_AGENT_AUDIT_EVENT`; relax `TOOL_NAME` (NOT NULL) → `EVENT_NAME` (nullable). Generalize `AuditListener` SPI to a single kind-tagged method. Wire retrieval auditing end-to-end through the Phase 5 RAG advisor chain in the same phase.

**In scope:**
- Liquibase changelog: drop `AI_AGENT_TOOL_CALL_AUDIT`, create `AI_AGENT_AUDIT_EVENT` with `PARENT_ID` self-FK + indexes (hard cutover — no backfill).
- Entity rename `AiToolCallAudit` → `AiAuditEvent`; `@ManyToOne parent` + `@OneToMany(mappedBy="parent") children` annotated `@Composition`.
- `AuditWriter` rewrite: `writeChatStart`/`writeChatFinish` (mutable root), `writeToolCall(parentId, ...)`, new `writeRetrieval(parentId, ...)`.
- `AuditAdvisor` rewrite: one root INSERT at start, UPDATE at finish — no PRE/POST pair.
- `ToolCallbackAuditDecorator` update: children carry `PARENT_ID = currentChatRootId`.
- New: retrieval audit hookup in `RetrievalAugmentationAdvisorFactory` / `QuestionAnswerAdvisor` path so every RAG retrieval writes a `RETRIEVAL` child of the current chat root.
- `AuditListener` SPI breaking change to `void onEventAudited(UUID auditId, String kind)`.
- `AuditListenerDispatcher` dispatches on every kind (CHAT finish / TOOL / RETRIEVAL / future), not tool-only.
- Flow UI `ToolCallAuditListView` rename + tree rendering via Jmix `@Composition` fetch plan (no client-side grouping).
- Test updates: `AuditWriterFieldMappingTest`, `AuditDurabilityTest`, `AuditListenerDispatcherTest`; new tree-traversal test + retrieval round-trip test.

**Out of scope:**
- Preserving any existing audit rows (hard cutover — pre-v1 dev data only).
- Additional event kinds beyond `CHAT` / `TOOL` / `RETRIEVAL` (reserve `kind` column width for future `GUARDRAIL`, `RATE_LIMIT`, etc., but do not write them).
- Deprecation bridge for old `AuditListener.onToolCallAudited` — direct break (solo codebase, in-tree default bean only).
- Changes to Spring AI chat memory schema (`SPRING_AI_CHAT_MEMORY`) or `AiConversation`/`AiMessage` projection path.
- Reshaping `AuditAdvisor`'s `REQUIRES_NEW` placement (D-11 Phase 4 carried forward unchanged).
- New retrieval-side features (filter-expression shape, topK tuning) — retrieval wiring only records what Phase 5's RAG already does.

</domain>

<decisions>
## Implementation Decisions

### Root Row Lifecycle

- **D-01: Mutable root row — one row per chat turn.** `AuditWriter.writeChatStart(runId, userUsername, conversationId, promptHash) → UUID parentId` INSERTs the root (`parentId=null`, `kind="CHAT"`, `startedAt=now`, `finishedAt=null`, `outcome=null`, `eventName=null`). `AuditWriter.writeChatFinish(parentId, latencyMs, outcome, errorClass)` LOADs the same row by id in a fresh `REQUIRES_NEW` tx and UPDATEs `finishedAt` / `latencyMs` / `outcome` / `errorClass`. Literal match for success criterion #2 ("one root row per turn") and lets the Flow UI render one root row per turn without grouping. No `<chat>` sentinel, no PRE/POST dance. Children (`TOOL`, `RETRIEVAL`) remain append-only — each inserted once with `startedAt` + `finishedAt` set at insert time.

- **D-02: Root UPDATE commits in its own `REQUIRES_NEW` tx, same as inserts.** Preserves Phase 4 D-11 (AuditWriter is the sole transactional surface). AuditAdvisor invokes `writeChatStart` before the advisor chain call, then `writeChatFinish` in a `finally` / after-completion block whether the chain returned normally or threw. Outcome on exception: `ERROR` + `errorClass = simpleName(Throwable)`. On normal return: `SUCCESS` (or `TIMEOUT` / `CANCELLED` if the advisor chain surfaces those explicitly).

### SPI Breaking Change

- **D-03: `AuditListener` becomes `void onEventAudited(UUID auditId, String kind)` — single method, kind-dispatched by the listener.** Old method `onToolCallAudited(UUID)` is removed entirely (not deprecated). Solo codebase + in-tree default bean (`SpiDefaultsAutoConfiguration`) is the only consumer — break is cheap. Hosts that care about per-kind behaviour write `if ("TOOL".equals(kind)) { ... }`; Javadoc documents the kind set and that additional kinds may be added in future (listeners MUST be kind-tolerant). Kind constants live in a public `AuditKind` final class with `String` constants (`CHAT`, `TOOL`, `RETRIEVAL`) so hosts can reference them without string literals, and the set stays open-ended for host-defined kinds. NOT an enum — host extension + Liquibase `varchar` column stays aligned.

- **D-04: Dispatcher method renamed to match: `AuditListenerDispatcher.dispatchEventAudited(UUID auditId, String kind)`.** Dispatcher iterates listeners, `try { l.onEventAudited(auditId, kind); } catch (Throwable t) { log.warn(...) }` — per-listener isolation unchanged from Phase 4 D-13.

### Fan-Out Coverage

- **D-05: Fan-out fires on every audited event, not tool-only.** `writeChatFinish` (the UPDATE, i.e. when the root becomes complete), `writeToolCall`, `writeRetrieval` each register an `afterCommit` `TransactionSynchronization` that calls `dispatcher.dispatchEventAudited(id, kind)`. `writeChatStart` does NOT fan out — listeners should only see the completed root, not the in-flight row. Same `afterCommit` mechanism as Phase 4 D-14 (listeners only observe durable rows).

### Data Migration

- **D-06: Hard cutover — drop `AI_AGENT_TOOL_CALL_AUDIT`, create `AI_AGENT_AUDIT_EVENT` fresh.** No backfill. Pre-v1 project; STATE.md confirms dev-only audit data. Single Liquibase changelog (new file, e.g. `090-ai-audit-event.xml`) executes: `<dropTable tableName="AI_AGENT_TOOL_CALL_AUDIT" cascadeConstraints="true"/>` then `<createTable tableName="AI_AGENT_AUDIT_EVENT">` with the new shape. Retire `030-ai-tool-call-audit.xml` and `080-ai-tool-call-audit-runid.xml` — planner picks the concrete retire pattern during research and verifies on both Postgres + HSQLDB. Document hard cutover in a short ADR / memory note so v1 consumers know there is no upgrade path from pre-v1 audit data.

### Rename + Naming

- **D-07: Bundle tree introduction and rename in one phase / one changelog.** With hard cutover the rename is free — the new table is created with its final name in the same changelog. No half-renamed intermediate state, one review cycle, one entity-reference sweep.

- **D-08: Entity name `AiAuditEvent`, table name `AI_AGENT_AUDIT_EVENT`.** Event-shaped reads naturally for a row representing a single audited event; mirrors `onEventAudited` SPI method. `AI_AGENT_` table prefix preserves add-on ownership. Instance name: `getDisplayName()` derived from `(kind, eventName, outcome)` — e.g. `"TOOL / find_records / SUCCESS"` or `"CHAT / (no name) / SUCCESS"`.

### Retrieval Audit Wiring (scope expansion)

- **D-09: Phase 7.2 ships end-to-end retrieval audit, not just the `writeRetrieval` method.** The `RetrievalAugmentationAdvisorFactory` (and the `QuestionAnswerAdvisor` path, whichever the Phase 5 RAG wiring actually uses) is instrumented so every retrieval call writes a `RETRIEVAL` child row of the current chat root with: `query` (user question), `topK`, `hitCount`, `topScore`, `filtersJson` (the per-request `FILTER_EXPRESSION` serialized), `latencyMs`, `outcome`. Parent id comes from the `RunContext` (Phase 4) — the advisor chain already threads `runId`; we add `rootAuditId` to the same context. Folds the previously-blocked retrieval-audit todo into this phase so the feature ships in one refactor.

- **D-10: `RunContext` extended with `UUID rootAuditId` (nullable, populated after `writeChatStart`).** `AuditAdvisor` writes start, captures returned parent id, stashes it on `RunContext`. Tool-callback decorator and retrieval hookup both read `RunContext.rootAuditId` to pass as `parentId`. If missing (out-of-chain writes), falls back to `null` parent — document that this case SHOULD NOT happen in normal chat flow and is defensive only.

### Flow UI Tree Rendering

- **D-11: Audit list view renders via Jmix `@Composition` fetch plan — no client-side grouping.** Rename `ToolCallAuditListView` → `AiAuditEventListView`; XML loader uses a fetch plan that includes `children` recursively (one level — children of children not rendered since current kinds are all leaf-under-CHAT). Tree data grid via Jmix built-in (hierarchical `dataGrid` with `@Composition` expanding children on click). Uses prior Jmix UI conventions from memory: Jmix-first over raw Vaadin, `@Subscribe` wiring, root-bundle messages. Planner verifies the exact Jmix XML element (`treeDataGrid` vs `dataGrid` with `hierarchicalContainer`) via Context7 → Jmix docs → jmix-ai-backend reference.

### Claude's Discretion

- Exact Liquibase `<dropTable>` + retire-changelog pattern (runOnChange empty-body vs `<validCheckSum>ANY</validCheckSum>` vs letting the drop handle it). Planner picks during research; verify on both Postgres + HSQLDB.
- `AuditKind` constants file location (`com.vn.agent.audit.AuditKind` vs `com.vn.agent.spi.AuditKind`) — SPI location is cleaner for host reference but ties SPI package to audit internals; planner decides.
- `filtersJson` serialization format for retrieval rows — JSON string of the Spring AI `FilterExpression` (via whatever its toString/serialization is in M4) vs add-on-owned compact representation. Planner confirms M4 `FilterExpression` shape via Context7.
- Whether `RunContext` is constructor-injected or `ThreadLocal`. Phase 4 already decided this; 7.2 inherits — planner confirms by reading `RunContext` source.
- Instance name format for `AiAuditEvent` — exact string shape.

<specifics>
## Specific Ideas

- User wants the tree-rendering pattern aligned with `jmix-ai-backend` (reference repo) for consistency across the Jmix AI add-on family. Planner should read that repo's audit view during RESEARCH.md and note alignment / divergence as a D-NN in PLAN.md.
- Fan-out on `writeChatStart` is explicitly excluded (D-05) — listeners only see the completed root, never an in-flight row.
- `AuditKind` should be a public `final class` of `String` constants, NOT an enum — keeps `kind` column open-ended for host-defined kinds and matches Liquibase `varchar`.
- Rename the old `ToolCallAuditListView` + `ToolCallAuditDetailDialog` Java classes + XMLs to `AiAuditEventListView` / `AiAuditEventDetailDialog` — don't leave legacy names as thin wrappers.

</specifics>

<deferred>
## Deferred Ideas

- Additional event kinds (`GUARDRAIL`, `RATE_LIMIT`, `INJECTION_SCAN`) — `kind` column sized to accommodate, but writing these belongs to Phase 6 / Phase 8 scope. 7.2 only writes `CHAT` / `TOOL` / `RETRIEVAL`.
- Deeper tree (retrieval → per-chunk children, tool-call → sub-step children) — leaf-under-CHAT is the only level in v1. Multi-level trees can be introduced later without schema change.
- `AuditListener` async executor pool — Phase 4 D-13 explicitly ruled this out; 7.2 keeps synchronous per-listener fan-out.
- Historical audit data migration for downstream consumers that adopt v1 after pre-v1 dev use — out of scope given hard cutover; documented as an ADR note.

</deferred>
