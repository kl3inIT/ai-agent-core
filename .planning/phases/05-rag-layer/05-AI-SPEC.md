## 1. System Classification

**System Type:** RAG

**Description:**
Phase 5 lands the knowledge-base ingestion + pgvector retrieval path of the `ai-agent-core` Jmix add-on. Admins of a host Jmix application upload business documents (PDF / MD / TXT / HTML) tagged with `allowedRoles`; the add-on chunks them with `TokenTextSplitter`, embeds with OpenAI `text-embedding-3-small` via OpenRouter (dim=1536), and persists vectors to `AI_AGENT_KB_VECTOR_STORE` (pgvector) in the host's own Postgres. At chat time, `RetrievalAugmentationAdvisor` sits in the Phase 4 advisor chain between `MessageChatMemoryAdvisor` and `ToolCallAdvisor`; a per-request `FILTER_EXPRESSION` built by `RetrievalFilterBuilder` from `CurrentAuthentication.getAuthorities()` constrains retrieval to chunks whose `allowedRoles` intersect the caller's Jmix roles AND whose `embeddingModel` matches the currently-configured model. "Good" means: (a) uploaded docs reach `READY` with every chunk carrying the contract metadata, (b) a user with role R only retrieves chunks explicitly shared with R or broader, (c) `AiAgentAdminRole` bypasses the filter (explicit, configurable), (d) delete-document atomically purges both the entity row and every vector chunk in one transaction, (e) the path fails closed — any chunk missing `allowedRoles` or carrying a stale `embeddingModel` tag is invisible to non-admin callers. Consumers are host Jmix application developers (integrating the add-on) and the admins/end-users of those host apps (uploading docs and asking grounded questions).

**Critical Failure Modes:**
1. **Cross-role document leak.** A user with only `AiAgentUserRole` retrieves a chunk whose `allowedRoles` is `[AiAgentAdminRole]`, or a chunk missing `allowedRoles` entirely, because the pgvector JSON-array `IN` pitfall (Section 3 pitfall #1) silently returns the wrong shape, or because a race between upload and ingest persisted an untagged chunk. This is the hard contract — ROADMAP success criterion #3.
2. **Orphaned vector chunks after delete.** `DataManager.remove(doc)` succeeds but `VectorStore.delete(Filter.Expression documentId==X)` silently partial-fails (pgvector transaction not bound to the same `PlatformTransactionManager`, or JSON key mismatch), leaving embeddings retrievable against a deleted document — a compliance-visible ghost in the KB. ROADMAP success criterion #4.
3. **Silent ingestion corruption.** Upload reports `READY` but the worker dropped chunks mid-stream — a transient OpenRouter 429 was swallowed instead of retried, or `@Async` + `@Transactional` footgun (Section 3 pitfall #7) committed partial state. Admin trusts the KB; users get thin or missing retrievals with no signal. RAG-03 / D-14.
4. **Stale-model retrieval pollution.** After a host swaps `EmbeddingModel` (e.g. to `text-embedding-3-large`), old chunks embedded under the prior model remain in the store and get mixed into retrievals despite living in a different semantic space — answers degrade silently with no admin warning. D-03 pins `embeddingModel` in metadata precisely to filter these out; failure here means the filter clause is missing or misspelled.
5. **Fail-open on missing `allowedRoles`.** A `CustomIngester` returns docs with an empty `allowedRoles` list; the filter builder treats "empty list" as "match anyone" rather than "admin-only", violating fail-closed posture (D-05). Regression is invisible to functional tests that only assert the positive case.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / enterprise knowledge retrieval — this is a horizontal Jmix add-on (a reusable component embedded into vertical-specific host apps), not itself a vertical product. Host apps may be healthcare / legal / finance, but the add-on's own eval criteria are framed around enterprise knowledge retrieval with a security-critical authorization contract.

**User Population:**
- **Primary (runtime):** end-users of host Jmix applications asking grounded questions; they never see pgvector directly — they see chat answers with citations.
- **Primary (admin):** host-app administrators uploading docs, tagging `allowedRoles`, triggering reingest/delete.
- **Primary (integrator):** host-app developers embedding `ai-agent-starter` into their Jmix app, configuring the embedding provider, implementing `CustomIngester` for their KB sources.
- **Secondary:** SRE/platform engineers operating the host app in production — responsible for ingest throughput, orphaned-row audits, cost budgets.

**Stakes Level:** High — the role-scoped filter is a parallel authorization channel to Jmix `AccessManager`. A silent leak from the vector store is a direct confidentiality incident for the host application; an orphaned-chunk residue after delete is a compliance-visible bug. Stakes are not "critical" (no life-safety, no medical/legal advice issued directly) but one tier below — a failure causes host-app customers to lose trust in the add-on and potentially triggers host-side data-protection reporting.

**Output Consequence:** Chat answers grounded in retrieved chunks are surfaced to end-users of the host app, frequently with citation links into the source document. Downstream: the answer may be copied into email, pasted into tickets, or acted on as if authoritative. The retrieval step is upstream of the LLM's grounding — an unauthorized chunk reaching the prompt context is a leak regardless of whether the LLM quotes it verbatim.

### What Domain Experts Evaluate Against

```
Dimension: Authorization-channel correctness (role-scoped retrieval)
Good: For a user holding exactly role set R, every chunk returned by retrieval has an allowedRoles list intersecting R (or the caller holds AiAgentAdminRole with bypass enabled). Fail-closed on empty/missing allowedRoles for non-admin callers. Filter also pins to the currently-configured embeddingModel so stale-model chunks are invisible.
Bad: Any chunk whose allowedRoles is disjoint from R appears in retrieved context for a non-admin caller; or an untagged chunk appears for a non-admin caller; or a chunk embedded with a previous model appears after a model swap.
Stakes: Critical (for this add-on)
Source: Enterprise security practice — parallel authorization channels must each enforce independently (defence in depth; RAG auth cannot rely on the LLM refusing to quote). ROADMAP success criterion #3.
```

```
Dimension: Atomic delete / orphan-freedom
Good: Deleting a document removes the AiKnowledgeDocument row AND every vector chunk with metadata.documentId == X in a single transaction bound to the same PlatformTransactionManager; rollback of either step rolls back both. COUNT(*) WHERE metadata->>'documentId'='X' returns 0 the instant the delete commits.
Bad: The entity row is gone but chunks remain retrievable; or chunks are gone but the row lingers with status=READY; or partial deletion under transient failure leaves the KB in a state no admin action can reach.
Stakes: Critical
Source: SRE / data-governance practice — orphaned rows are compliance artefacts (e.g. right-to-erasure requests fail if vectors persist). ROADMAP success criterion #4.
```

```
Dimension: Ingestion reliability and observability
Good: Upload → PENDING → PROCESSING → READY lifecycle completes for every accepted doc, with every chunk carrying the full metadata contract {source, documentId, embeddingModel, allowedRoles}. Transient provider errors (OpenRouter 429/503) are retried with bounded exponential backoff; retry exhaustion transitions the doc to FAILED with a captured errorMessage, never a misleading READY. No partial persistence — a half-indexed doc is impossible.
Bad: Upload reports READY but chunk count is lower than expected; FAILED status with an empty errorMessage; a transient provider hiccup corrupts status to FAILED without retry; the worker silently drops chunks on a 429 and the admin never sees the loss.
Stakes: High
Source: Technical-writer / KB-admin practice — admins cannot trust a KB whose completeness they cannot verify. RAG-03, D-14, D-16.
```

```
Dimension: Metadata contract stability (ingest-time flatness to filter-time correctness)
Good: Every chunk written to the store carries the contract keys verbatim (source, documentId, embeddingModel, allowedRoles) with the agreed JSON shape. Renames, type shifts (string → array), or casing drift are breaking changes requiring a full reingest. The filter builder's expected keys and the writer's emitted keys share a single source of truth (constants or a shared contract class).
Bad: Writer emits allowedRoles as a comma-joined string; filter builder queries it as a JSON array — zero chunks match, retrieval falls silent (a failure mode indistinguishable from an empty KB). Or writer emits EmbeddingModel (PascalCase); filter queries embeddingModel — same silent failure.
Stakes: High
Source: Data-pipeline / IR practice — ingest and retrieval are two systems on one schema; the schema contract is the single point of coupling, and silent mismatches are the most common retrieval outage.
```

```
Dimension: Fail-closed posture on edge input
Good: Untagged chunks (allowedRoles empty or missing) are invisible to non-admin callers. Service never synthesises a default allowedRoles at ingest; if the upload form omitted roles, the service either rejects the upload or tags the chunk admin-only. CustomIngester SPI outputs that omit allowedRoles are treated identically. Admin-bypass is a single explicit flag, defaulted on but toggleable to off for stricter hosts.
Bad: A code path treats "empty allowedRoles" as "accessible to all roles" because a defensive default was applied at the wrong layer; or CustomIngester output bypasses the role-validation check that the upload-service path runs; or admin-bypass is hard-coded on with no flag.
Stakes: Critical
Source: Security engineering — the default posture under ambiguous input is the most consequential design decision in an auth channel. D-05, D-07.
```

### Known Failure Modes in This Domain

- **JSON-array membership silently returns zero rows.** Spring AI's pgvector `FilterExpressionConverter` emits `metadata->>'allowedRoles' IN (...)` which text-casts a JSON array and never matches a scalar. Symptom: role-scoped retrieval returns an empty list for every non-admin user, indistinguishable from "no docs match". Referenced in Section 3 pitfall #1 and spring-projects/spring-ai#1179.
- **`@Async` + `@Transactional` on the same method opens a transaction in the wrong thread.** The async proxy wraps outside transactional; the caller never participates, exceptions cross thread boundaries, partial state persists. Section 3 pitfall #7.
- **Model drift without reingest.** Host swaps embedding model; old vectors remain geometrically valid but semantically misaligned; retrieval quality degrades silently (no error, just worse answers). D-03 mitigation = pin `embeddingModel` per chunk and filter.
- **Bean-collision on embedding starter.** Transitive `spring-ai-starter-model-ollama` or similar pulls a second `EmbeddingModel` bean; `NoUniqueBeanDefinitionException` at context refresh. `@ConditionalOnMissingBean` does not defend against this (it only gates the add-on's own bean). Section 3 pitfall #4.
- **Delete across two stores without a shared PTM.** If pgvector ran on a separate datasource from the host entity store, `VectorStore.delete(...)` and `DataManager.remove(...)` would need XA or a saga; in this add-on they share the host Postgres, so a single `@Transactional(REQUIRED)` suffices — but if a host ever points pgvector at a different datasource, atomicity breaks silently.
- **Ingestion queue saturation under bulk reingest.** `SimpleAsyncTaskExecutor` (Spring default) spawns a thread per call, defeats HTTP-client connection pooling, and under a "reingest all 500 docs" click can OOM the host. D-12 mandates a bounded `ThreadPoolTaskExecutor` with MDC propagation.
- **Orphaned vector rows after failed `CustomIngester` re-run.** SPI-derived synthetic doc IDs (D-19) must be stable UUIDv5 hashes; if the hash scheme drifts between runs, a re-run inserts new chunks without deleting the old, and the KB accumulates ghosts.

### Regulatory / Compliance Context

None specific to this horizontal add-on. Downstream hosts may process PII/PHI/financial data under GDPR, HIPAA, FCA, or similar frameworks — this add-on's contract to those hosts is:

- The role-scoped filter (D-09/D-11) and fail-closed posture (D-05) are the minimum posture required for a host to layer its own compliance (consent scoping, data-minimisation, right-to-erasure via the atomic-delete path in D-21) on top.
- No PII redaction, no content-level ACLs beyond role tagging, no retention policies — these are explicitly out of scope for v1 and a host needing them must build on the SPI surface.
- The add-on does not phone home; all data stays in the host's Postgres and the host-configured OpenRouter / embedding provider. Hosts with regulatory constraints on outbound model calls must swap `EmbeddingModel` and `ChatModel` beans to on-prem equivalents — both are `@ConditionalOnMissingBean`.

## 2. Framework Decision

**Selected Framework:** Spring AI (RetrievalAugmentationAdvisor + PgVectorStore + OpenAiEmbeddingModel via OpenRouter)

**Version:** 1.1.4 (pinned in `PROJECT.md` via `spring-ai-bom:1.1.4`)

**Rationale:**
Spring AI 1.1.4 is already load-bearing in this codebase: Phase 4's advisor chain reserves a RAG slot between `MessageChatMemoryAdvisor` and `ToolCallAdvisor` (Phase 4 D-02); Phase 2 pgvector DDL pins `vector(1536)` to match OpenAI `text-embedding-3-small`; the OpenRouter base-url pattern from Phase 4 D-03 is reused verbatim for the embedding endpoint. Phase 5 is strictly additive — new `@Bean`s in `AIAutoConfiguration` for `EmbeddingModel`, `VectorStore`, `RetrievalAugmentationAdvisor`, and `RetrievalFilterBuilder`. Spring AI's `Filter.Expression` DSL cleanly expresses the role-intersection + embedding-model-drift filter required for success criteria #2 and #3, and `PgVectorStore.delete(Filter.Expression)` under a single `@Transactional(REQUIRED)` satisfies success criterion #4's atomic delete contract.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain4j 0.35+ (`langchain4j-pgvector` + `langchain4j-open-ai`) | Does not integrate with Spring AI's advisor chain already built in Phase 4; swapping would force rewriting `ChatClientFactory`, `MessageChatMemoryAdvisor`, `AuditAdvisor`, and `ToolCallAdvisor` wiring, and break the Spring-Boot auto-configuration contract PKG-02 depends on. |
| Raw JDBC + manual embedding calls | Throws away Spring AI's advisor composition, filter DSL portability, and `TikaDocumentReader` / `TokenTextSplitter` wiring — every feature would need a bespoke reimplementation. |

**Vendor Lock-In Accepted:** Partial — locked into Spring AI's advisor + `VectorStore` abstractions (already accepted in Phase 4); model and embedding provider stay swappable via `EmbeddingModel` bean (D-02) and OpenAI-compatible base-url (D-01).

### Entry Point Pattern

The advisor is a `@Bean` wired into `ChatClient.defaultAdvisors(...)` with a permissive static retriever (Phase 4 slot), then the per-request filter is injected by `ChatService` via `.advisors(a -> a.param(...))` each call. This keeps the advisor reusable and the security-critical filter build co-located with `CurrentAuthentication`.

```java
// AIAutoConfiguration.java (Phase 5 additions)
@Bean
@ConditionalOnMissingBean
VectorStore vectorStore(JdbcTemplate jdbc, EmbeddingModel embeddingModel,
                        AiAgentProperties props) {
    return PgVectorStore.builder(jdbc, embeddingModel)
            .vectorTableName("AI_AGENT_KB_VECTOR_STORE")  // Phase 2 DDL table name
            .initializeSchema(false)                      // Liquibase owns schema (Phase 2 changelog 070)
            .dimensions(1536)                             // pinned to text-embedding-3-small
            .build();
}

@Bean
@ConditionalOnMissingBean
RetrievalAugmentationAdvisor retrievalAugmentationAdvisor(VectorStore vectorStore,
                                                          AiAgentProperties props) {
    // Retriever built without a static filter — runtime filter supplied via FILTER_EXPRESSION param.
    VectorStoreDocumentRetriever retriever = VectorStoreDocumentRetriever.builder()
            .vectorStore(vectorStore)
            .similarityThreshold(props.getRag().getSimilarityThreshold())  // e.g. 0.50
            .topK(props.getRag().getTopK())                                // e.g. 5
            .build();

    return RetrievalAugmentationAdvisor.builder()
            .documentRetriever(retriever)
            // Optional: .queryTransformers(RewriteQueryTransformer.builder()...build())
            // Optional: .documentJoiner(new ConcatenationDocumentJoiner())
            .build();
}

// ChatService.ask(...) — per-request filter injection (filter is security-critical, built from CurrentAuthentication)
public String ask(String userMessage) {
    Filter.Expression filter = retrievalFilterBuilder.buildFor(currentAuthentication);
    return chatClient.prompt()
            .advisors(a -> {
                if (filter != null) {
                    a.param(VectorStoreDocumentRetriever.FILTER_EXPRESSION, filter);
                }
                // admin bypass (D-06): filter == null means no param set => retriever-level filter is empty
            })
            .user(userMessage)
            .call()
            .content();
}
```

### Common Pitfalls

1. **`FilterExpressionBuilder.in("allowedRoles", "role_a", "role_b")` does NOT mean "list metadata value intersects constant list".** Spring AI's pgvector `FilterExpressionConverter` emits `metadata->>'allowedRoles' IN ('role_a','role_b')` — the `->>` operator casts the JSON value to text, which succeeds only when `allowedRoles` is stored as a scalar string. If the chunk stores `allowedRoles` as a JSON **array** (the D-10 contract), the text-cast yields the array's JSON literal (e.g. `["admin","user"]`), which never equals any single role code — the filter silently returns zero rows. **Mitigation (planner's call):** either (a) override `PgVectorFilterExpressionConverter` to emit `metadata->'allowedRoles' ?| array[...]` (pgvector JSONB `?|` = "any-of" membership), or (b) flatten the tag at ingest time to N boolean metadata keys (`role_admin=true`, `role_user=true`) and filter via OR-of-`eq`. Option (b) is portable across `VectorStore` implementations; option (a) keeps one metadata key but ties to pgvector. Verified against [spring-projects/spring-ai#1179](https://github.com/spring-projects/spring-ai/issues/1179) which documents the parallel `IN`-on-JSON issue.

2. **`initializeSchema(true)` silently conflicts with Liquibase.** The Phase 2 changelog (`070-ai-kb-vector-store.xml`) owns the `AI_AGENT_KB_VECTOR_STORE` DDL and the HNSW index. If `PgVectorStore.builder(...).initializeSchema(true)` is set, Spring AI will try to `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX` on startup — harmless on Postgres (both guard on IF NOT EXISTS) but it violates the "Liquibase is the single DDL owner" contract and will blow up on schema drift detection in CI. Always `initializeSchema(false)` in this add-on.

3. **`FILTER_EXPRESSION` advisor param replaces the retriever's static filter, it does not AND with it.** If the retriever is built with `.filterExpression(staticExpr)` and the request also passes the `FILTER_EXPRESSION` param, the runtime param wins outright — the static expression is not merged. Consequence: never put the security filter in the retriever builder (someone could forget to pass the runtime param and retrieval would fall back to "no filter"). Build the retriever with no filter at all; make `ChatService` unconditionally set the param; and write a test that asserts the retriever's internal filter is null.

4. **Shared `EmbeddingModel` bean collision on starter ordering.** Both `spring-ai-starter-model-openai` and any transitively-pulled embedding starter (`spring-ai-starter-model-ollama`, etc., if a host adds one) declare an `EmbeddingModel` bean. Spring Boot resolves the duplicate at context refresh with a `NoUniqueBeanDefinitionException`. The `@ConditionalOnMissingBean EmbeddingModel` pattern in `AIAutoConfiguration` does NOT defend against this — it only prevents our bean from registering when one exists; it does not deduplicate starters. Defence: an `AIConfigurationValidator` `@PostConstruct` assertion (bean-collision test, per D-02) counting beans of type `EmbeddingModel` and failing fast with a diagnostic.

5. **`TokenTextSplitter` has no `chunkOverlap` parameter.** CONTEXT.md D-13 lists `chunk-overlap` default 350 — that figure actually maps to `minChunkSizeChars` (the splitter's minimum chunk size in characters, which effectively acts as the lower bound when merging short trailing fragments). The splitter does NOT produce overlapping windows like a naive character splitter; it splits on token count with sentence-boundary awareness. `@ConfigurationProperties` key `jmix.ai-agent.rag.splitter.min-chunk-size-chars` (default 350) is the honest name; deprecate the `chunk-overlap` alias or document it as a semantic alias.

6. **`PgVectorStore.delete(Filter.Expression)` inherits the same pgvector JSON pitfall.** The document-delete path filters on `metadata->>'documentId' == '<uuid>'`. `documentId` is a scalar string in metadata — this works correctly. But if the planner ever tries to delete by `allowedRoles`, the same pitfall as #1 applies. Keep delete keyed on `documentId` only.

7. **`@Async` on `IngesterManager.runAll()` with `@Transactional` on the same method is a footgun.** Spring's `@Async` proxy wraps BEFORE `@Transactional` — the async call returns immediately, the transaction opens in the worker thread, and any exception crosses thread boundaries asynchronously. Worse, if the worker uses `DataManager` inside the outer `@Transactional`, the caller's transaction is not propagated. Per D-14, keep the async method transaction-free; have it call `IngestionStatusWriter.markFailed(...)` (annotated `@Transactional(REQUIRES_NEW)`) for status persistence, mirroring Phase 4's `AuditWriter`.

**Core Pattern:**

Two halves — (a) ingestion write-path, (b) retrieval read-path. Both converge on the same `VectorStore` bean.

```java
// (a) IngestionWorker.java — @Async write path
@Component
@Slf4j
public class IngestionWorker {

    private final TokenTextSplitter splitter;           // new TokenTextSplitter(chunkSize, minChunkSizeChars, 5, 10000, true)
    private final VectorStore vectorStore;
    private final EmbeddingModel embeddingModel;        // used only for model-name tagging
    private final IngestionStatusWriter statusWriter;   // @Transactional(REQUIRES_NEW)
    private final AiAgentRagProperties props;

    @Async("aiAgentIngestExecutor")   // D-12: dedicated bounded executor
    @Retryable(                       // D-16: retry only on transient provider errors
        retryFor = { TransientAiException.class, ResourceAccessException.class },
        maxAttemptsExpression = "#{@aiAgentRagProperties.embedRetry.maxAttempts}",
        backoff = @Backoff(
            delayExpression = "#{@aiAgentRagProperties.embedRetry.initialInterval.toMillis()}",
            multiplierExpression = "#{@aiAgentRagProperties.embedRetry.multiplier}"))
    public void ingest(UUID documentId, Resource source,
                       List<String> allowedRoles, String sourceLabel) {
        try {
            // 1. Read (Tika) -> raw Document list (usually 1)
            List<Document> raw = new TikaDocumentReader(source).read();

            // 2. Split -> chunk Documents
            List<Document> chunks = splitter.apply(raw);

            // 3. Attach metadata to every chunk (D-10 contract)
            String modelName = resolveEmbeddingModelName();  // e.g. "openai/text-embedding-3-small"
            for (Document chunk : chunks) {
                chunk.getMetadata().put("source", sourceLabel);
                chunk.getMetadata().put("documentId", documentId.toString());
                chunk.getMetadata().put("embeddingModel", modelName);
                chunk.getMetadata().put("allowedRoles", allowedRoles);
                // See pitfall #1: planner may flatten this to per-role booleans.
            }

            // 4. VectorStore.add(...) embeds + writes all chunks.
            //    D-14: no partial persistence — if this throws AFTER retries, caller's
            //    outer transaction (wrapping this call) rolls back the whole set.
            vectorStore.add(chunks);

            statusWriter.markReady(documentId);
        } catch (Exception ex) {
            log.error("Ingest failed for document {}", documentId, ex);
            statusWriter.markFailed(documentId, ex.getMessage());  // REQUIRES_NEW so this survives rollback
            throw ex;   // let the async boundary record it; no partial state persists
        }
    }
}
```

```java
// (b) RetrievalFilterBuilder.java — pure Authentication -> Filter.Expression
@Component
public class RetrievalFilterBuilder {

    private static final String ROLE_ADMIN = "AiAgentAdminRole";
    private final AiAgentRagProperties props;
    private final String currentEmbeddingModel;   // resolved at construction

    /**
     * D-11 contract. Null return means "admin bypass" — ChatService must not set FILTER_EXPRESSION param.
     */
    public Filter.Expression buildFor(Authentication auth) {
        Set<String> roles = auth.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .collect(Collectors.toSet());

        if (props.isAdminBypass() && roles.contains(ROLE_ADMIN)) {
            return null;   // D-06
        }

        FilterExpressionBuilder b = new FilterExpressionBuilder();

        // D-03: pin to current embedding model — stale chunks invisible.
        Filter.Expression modelPin = b.eq("embeddingModel", currentEmbeddingModel).build();

        // D-09 role intersection. See Section 3 pitfall #1 — literal shape TBD by planner:
        //   Option A (portable, flattened-role-keys):
        //     OR over b.eq("role_" + r, true) for r in user roles
        //   Option B (pgvector-specific, override converter):
        //     b.in("allowedRoles", roles.toArray()) + custom FilterExpressionConverter
        // Shown here: Option A because it is portable and survives a VectorStore swap.
        Filter.Expression[] roleOrs = roles.stream()
                .map(r -> b.eq("role_" + r.toLowerCase(Locale.ROOT), true).build())
                .toArray(Filter.Expression[]::new);
        Filter.Expression roleOverlap = (roleOrs.length == 1)
                ? roleOrs[0]
                : b.or(roleOrs[0], Arrays.stream(roleOrs).skip(1)
                        .reduce(roleOrs[0], (a2, c) -> b.or(a2, c).build())).build();

        return b.and(modelPin, roleOverlap).build();
    }
}
```

The atomic delete (D-21, success criterion #4) binds `VectorStore.delete(Filter.Expression)` and `DataManager.remove(doc)` to the same `PlatformTransactionManager` because the pgvector table is in the host Postgres:

```java
@Transactional   // REQUIRED — shared JDBC PTM
public void delete(UUID documentId) {
    cancellationRegistry.markCancelled(documentId);   // D-20
    Filter.Expression byDocId = new FilterExpressionBuilder()
            .eq("documentId", documentId.toString()).build();
    vectorStore.delete(byDocId);                      // pgvector DELETE ... WHERE metadata->>'documentId'=?
    AiKnowledgeDocument doc = dataManager.load(AiKnowledgeDocument.class).id(documentId).one();
    dataManager.remove(doc);
    // Rollback of either step rolls back both.
}
```

**Context Window Strategy:**
- `topK` = 5 and `similarityThreshold` = 0.50 as defaults — conservative; tune per eval feedback.
- Hard cap on retrieved-document total tokens: at 800 tokens/chunk × 5 chunks = 4000 tokens of context injected, leaving generous room in a 128k window.
- The advisor concatenates retrieved documents into the system-context section of the prompt — no per-turn summarisation needed at Phase 5 scope. If context overruns are observed in eval, the remediation is to (a) lower `topK`, (b) raise `similarityThreshold`, or (c) add a `RewriteQueryTransformer` — all advisor-builder-level knobs, no code path change.
- `MessageChatMemoryAdvisor`'s own window limit (configured in Phase 4) runs first, so the combined {history + retrieved docs} stays bounded before the model sees it.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Jackson records + `BeanOutputConverter`

> This is a Java/Spring codebase — Pydantic does not apply. The equivalent is a Jackson-mapped Java record validated by Spring AI's `BeanOutputConverter<T>` or the shorthand `.entity(Class)` on `ChatClient`.

RAG answers are not pure generation — they cite sources. The answer payload is a structured object: `{answer, citations[{documentId, source, snippet}]}`. The LLM must emit valid JSON or retry; we never trust free-form "Source: foo.pdf" text parsing.

```java
// Output contract — a record is sufficient; Spring AI derives the JSON schema via Jackson reflection.
public record RagAnswer(
        String answer,
        List<Citation> citations
) {
    public record Citation(
            String documentId,    // from chunk metadata.documentId (Phase 5 contract)
            String source,        // from chunk metadata.source
            String snippet        // short quote — at most ~200 chars
    ) {}
}
```

Two integration shapes — pick based on whether you want the advisor chain to remain engaged:

```java
// (a) Shorthand — best for single-turn RAG Q&A. ChatClient uses BeanOutputConverter internally;
//     the format instruction is appended to the prompt automatically.
RagAnswer result = chatClient.prompt()
        .advisors(a -> a.param(VectorStoreDocumentRetriever.FILTER_EXPRESSION, filter))
        .user(question)
        .call()
        .entity(RagAnswer.class);     // throws on parse failure

// (b) Explicit converter — when you need the raw String response for auditing,
//     or want to customise the JSON schema prompt.
BeanOutputConverter<RagAnswer> converter = new BeanOutputConverter<>(RagAnswer.class);
String raw = chatClient.prompt()
        .user(u -> u.text(question).param("format", converter.getFormat()))
        .call().content();
RagAnswer result = converter.convert(raw);
```

**Retry on validation failure (Phase 6 territory but establish the contract now):** wrap `.entity(RagAnswer.class)` in a `RetryTemplate` with **2 attempts** (one retry). On first failure, log `{conversationId, rawOutput, parseErrorMessage}` at WARN. On exhaustion, surface a typed `RagAnswerParseException` to the caller — do **not** return a synthetic fallback answer: a malformed structured output is a signal that the model misunderstood the prompt, not a transient fault. Phase 6's `StructuredOutputValidationAdvisor` (existence in 1.1.4 to be verified) will formalise this; Phase 5 ships the record contract so Phase 6 has something to wrap.

### Async-First Design

Spring AI's imperative APIs (`.call()`, `.similaritySearch(...)`, `VectorStore.add(...)`) are blocking. Spring AI also exposes reactive APIs (`.stream().content()` returns `Flux<String>`), but Phase 5's scope is ingestion + one-shot retrieval — no streaming — so the pattern is Spring's standard `@Async`:

- Ingestion runs on a **dedicated bounded executor** (`aiAgentIngestExecutor`, D-12). Do NOT reuse `Executors.newCachedThreadPool()` or Spring's default `SimpleAsyncTaskExecutor` — the former is unbounded (OOM risk on a bulk reingest), the latter spawns a new thread per call (defeats connection pooling on the embedding HTTP client).
- Propagate MDC into the worker so `runId` / user context survives the thread hop. Use `TaskDecorator` on the executor builder (`ThreadPoolTaskExecutor.setTaskDecorator(...)`) — this is the one common mistake: forgetting the decorator means audit logs in the worker are orphaned and troubleshooting a failed ingest becomes impossible.
- **`@Async` + `@Transactional` on the same method is a trap** (see Section 3 pitfall #7). The async proxy wraps outside the transactional proxy; the outer caller never sees the transaction boundary. In Phase 5, the async ingestion method stays **transaction-free** at the method level; it calls `IngestionStatusWriter.markReady(...)` / `markFailed(...)` which are `@Transactional(REQUIRES_NEW)`, mirroring Phase 4 `AuditWriter`.
- **Stream vs. await:** Phase 5 only does `.call()` (await). Streaming for end-user chat UX lands in Phase 7. The structured-output path (`RagAnswer` record) MUST be `.call()` — streaming + structured output do not mix in Spring AI 1.1.4, because the JSON-schema-aware parser needs the whole response before it can validate.

### Prompt Engineering Discipline

- **System vs. user prompt separation.** The RAG system prompt (grounding instructions, citation discipline, "say 'I don't know' if context insufficient") lives in a classpath-packaged template and is set once via `ChatClient.Builder.defaultSystem(...)` in `AIAutoConfiguration`. The user prompt is the end-user's question only — never concatenate retrieved documents into the user message. `RetrievalAugmentationAdvisor` inserts retrieved context into the system-message slot via a configurable template; override that template instead of concatenating manually.
- **Few-shot.** RAG Q&A with citations benefits from 2-3 inline gold examples of the expected `RagAnswer` shape, especially on smaller chat models. Store them in the system-prompt template (`classpath:/prompts/rag-system.st` using Spring AI's `PromptTemplate`). Do NOT retrieve few-shot examples dynamically in v1 — adds a second vector store, a second failure mode, and yields marginal accuracy wins on the Phase 5 use case.
- **`maxTokens` MUST be set.** Phase 4 sets `ChatOptions.maxTokens` per call. RAG answers are bounded — a citation-heavy reply rarely exceeds 800 tokens. Set `maxTokens=800` for the RAG path; fail-fast rather than generate a 4k-token essay. Never leave unbounded in production — runaway generation on an adversarial prompt is both a cost bomb and a latency tail.
- **Embedding-call inputs are NOT prompts.** Do not prefix chunk text with instructions before embedding. The embedding model has no system prompt; any extra tokens degrade retrieval by shifting the vector away from the content's natural semantics.

### Context Window Management

RAG-specific:

- **Retrieve, then truncate.** `topK=5` @ 800 tokens/chunk = 4000 tokens injected. Safe for a 128k-window chat model; watchful for an 8k-window model. If the host swaps to an 8k model, lower `topK` to 3 via `jmix.ai-agent.rag.top-k=3` — no code change.
- **No reranker in v1.** Spring AI 1.1 supports `DocumentPostProcessor` (e.g., `Reranker`) in the `RetrievalAugmentationAdvisor` builder chain, but adding one is Phase 6 territory. Gate: if retrieval accuracy eval (Section 5) shows consistent misranking at `topK=5`, add a cross-encoder reranker; keep `topK=5` and let the reranker pick the top 3 injected chunks.
- **Stale-chunk silent filter-out (D-03).** The `embeddingModel == current` filter clause is a context-management feature as much as a correctness feature — it stops the advisor from injecting chunks whose vectors do not share the current model's semantic space, which would otherwise surface as low-quality retrievals within budget.
- **Conversation memory + retrieval interaction.** `MessageChatMemoryAdvisor` runs BEFORE `RetrievalAugmentationAdvisor` (Phase 4 D-02 order), so the retrieval query is the already-rewritten message including memory context. No summarisation is needed; memory window is bounded upstream.

### Cost and Latency Budget

Per-call cost estimate at expected volume (OpenRouter pass-through pricing, April 2026):

| Path | Model | Tokens (est) | Unit cost | Per-call |
|------|-------|--------------|-----------|----------|
| Ingestion (per 1000-token chunk) | `text-embedding-3-small` | 1000 in | $0.02 / 1M in | $0.00002 |
| Retrieval (embed query) | `text-embedding-3-small` | ~30 in | $0.02 / 1M in | negligible |
| Chat turn (RAG-augmented) | `gpt-4o-mini` via OpenRouter | ~4000 in (sys+retrieved+history) + 600 out | $0.15 in / $0.60 out per 1M | ~$0.0010 |

Indicative at a modest pilot volume (1k conversations/day × 4 turns): ~$4/day chat + one-off ingestion cost on KB size. Fits a dev-sandbox budget; set a host-level per-day spend alert at 3× the expected baseline.

**Caching:**
- **Exact-match embedding cache** (high value, trivial to add): the same user question embedded repeatedly is a common pattern (health checks, canned demos). Cache `query-text → float[1536]` in a Caffeine `@Cacheable` layer in front of `EmbeddingModel.embed(query)`. Eviction: LRU, 10k entries, TTL 24h. Caveat: cache key must include the embedding model name (D-03) — a model swap invalidates the cache semantically.
- **Exact-match retrieval cache** — tempting, but risky under per-request `FILTER_EXPRESSION`. The cache key must include a canonical hash of the filter tree, not just the query text; otherwise a user with narrower roles could see a chunk hit cached from an admin request. Skip in v1.
- **Semantic caching** (returning an answer for a "close enough" prior question) — deferred. Phase 5's correctness contract is role-scoped retrieval; a semantic cache would require proving the cached answer is also accessible to the current user's role set, which adds a whole second authorization path.

**Sub-task model routing:** not relevant at Phase 5 scope — only one chat-path task (answer from context). The ingestion path has no LLM call at all apart from embedding. If Phase 6 adds a "classify this query: is it KB-answerable vs tool-callable" router, that is the right spot to drop to a cheaper model (`gpt-4o-mini` is already the cheap tier here; `gpt-4o-mini` for classification, `gpt-4o` only if high-stakes reasoning surfaces).

## 6. Guardrails

> The Phase 5 guardrail surface is small on purpose. Retrieval is an **internal** call downstream of Jmix's authenticated session — there is no user-facing input surface here (the user's question is already authenticated-and-authorized by Jmix). The `FILTER_EXPRESSION` itself **is** the guardrail: role-scoping, model-drift filtering, and fail-closed posture live inside it. Output-side guardrails belong to Phase 6 (structured-output validation, `ToolGuard`). Input-side prompt-injection scrubbing belongs to Phase 6 (GUARD-05). Phase 5 ships the ingestion-side validations and the runtime invariants, nothing more.

### Online (Real-Time)

| # | Guardrail | Trigger | Intervention | Measurement |
|---|-----------|---------|--------------|-------------|
| G-1 | **Role-filter construction is mandatory on every non-admin call.** | Every `ChatService.ask(...)` invocation: `RetrievalFilterBuilder.buildFor(auth)` runs; if the caller is non-admin, the advisor param `VectorStoreDocumentRetriever.FILTER_EXPRESSION` MUST be set before `.call()` executes. | **Block.** `ChatService` is structured so the only path that reaches `.call()` is one that already set the param (or deliberately skipped it for admin-bypass). A `ChatServiceFilterParamContractTest` asserts that the retriever's static filter is null (pitfall #3) and that every non-admin path sets the runtime param. | Integration test; no runtime counter needed — structural invariant. |
| G-2 | **Embedding-model drift clause always present for non-admin callers.** | Every non-admin `FILTER_EXPRESSION` built by `RetrievalFilterBuilder` includes `eq("embeddingModel", currentEmbeddingModel)` as a conjunction. | **Block.** Unit-tested (`RetrievalFilterBuilderTest`, Dimension #2) with every fixture role set — absence of the clause fails the test. At runtime, no affirmative action; the invariant is enforced by construction. | Unit test (Dimension #2) + structural review. |
| G-3 | **Fail-closed on empty/missing `allowedRoles`.** | Ingestion time: `KnowledgeDocumentUploadService` rejects an upload whose submitted `allowedRoles` list is empty AFTER role-code validation (D-07); `CustomIngester` output with empty `allowedRoles` is forced to admin-only before persist (D-05). Retrieval time: untagged chunks that somehow exist in the store are invisible to non-admin callers because the role-overlap clause cannot match them. | **Block** (ingestion rejects the upload with a typed exception). **Filter** (retrieval silently excludes untagged chunks from non-admin view). | `UploadServiceRoleValidationTest` + `FailClosedPostureIntegrationTest` (Dimension #7). |
| G-4 | **Role-code validation against `RoleRepository`.** | Every submitted `allowedRoles` code on upload is checked against `io.jmix.security.role.RoleRepository` before the doc row is persisted. | **Block.** Unknown role codes raise a typed `UnknownRoleCodeException`; the upload is rejected, no `AiKnowledgeDocument` row is written. | `UploadServiceRoleValidationTest` (Dimension #7b). |
| G-5 | **Ingestion document-size + chunk-count sanity limits.** | Pre-split: reject a raw `TikaDocumentReader` output whose total character count exceeds `jmix.ai-agent.rag.ingest.max-document-chars` (default 5 MB / ~1.25M chars). Post-split: reject if chunk count exceeds `TokenTextSplitter.maxNumChunks` (default 10000) — the splitter already caps this, but surface the rejection as a typed exception rather than silent truncation. | **Block.** Document is marked FAILED with `errorMessage = "Document exceeds size limit"`; no embed calls are made. Protects against a cost-runaway on an adversarial upload and against the async executor queue backing up on a genuinely huge doc. | Integration test on a synthetic oversized input. |
| G-6 | **Bounded ingest executor.** | `aiAgentIngestExecutor` is a `ThreadPoolTaskExecutor` with `queue-capacity=100` (D-12, configurable). A 101st upload while all threads are busy hits the reject policy. | **Escalate.** Reject with `CallerRunsPolicy` (runs on caller thread, making upload synchronous and slowing the submitter) — this is a back-pressure signal, not a data loss. Admin sees a slower UX under bulk-upload bursts rather than an OOM. Alternative `AbortPolicy` surfaces the rejection as a `TaskRejectedException` logged at WARN. Planner picks; CallerRuns is the safer default. | Metric `aiagent.ingest.executor.queue.size` + alert (Section 7). |

### Offline (Flywheel)

| # | Metric | Sampling Strategy | Action on Degradation |
|---|--------|-------------------|----------------------|
| F-1 | **Orphaned chunks per documentId** — `SELECT metadata->>'documentId', COUNT(*) FROM AI_AGENT_KB_VECTOR_STORE WHERE metadata->>'documentId' NOT IN (SELECT id::text FROM AI_KNOWLEDGE_DOCUMENT)` | Scheduled `@Scheduled(cron = "0 0 3 * * *")` admin-triggered job (or manual SQL on demand — Phase 5 ships the query, Phase 7 surfaces the UI). | Non-zero count is a regression of Dimension #4 (atomic delete). Alert admin; open a ticket with the documentId(s). Retrieval is NOT automatically purged — admin decides whether to re-run the delete path or investigate. |
| F-2 | **Chunks tagged with a stale `embeddingModel` value** — `SELECT metadata->>'embeddingModel', COUNT(*) FROM AI_AGENT_KB_VECTOR_STORE WHERE metadata->>'embeddingModel' != ?` (param = currently-configured model). | Same scheduled job or admin-on-demand. | Non-zero count surfaces the "reingest required after model swap" signal that D-03 anticipates. Admin action: bulk-reingest via `KnowledgeDocumentService.reingest(...)` (D-15) per doc. Phase 7 UI can surface as a banner. |
| F-3 | **Per-document chunk-count drift** — record `chunks_written` on `AiKnowledgeDocument` at ingest completion; periodically re-count `AI_AGENT_KB_VECTOR_STORE WHERE metadata->>'documentId'=X`. Mismatch > 0 indicates silent loss. | On-reingest (compare pre vs post) + nightly batch sample. | Mismatch alerts admin; opens a reingest recommendation. | F-4 | **Ingestion failure rate by error type** — Micrometer counter `aiagent.ingest.failed{errorType}` (e.g. `TransientAiException`, `TikaParseException`, `UnknownRoleCodeException`). | Continuous (counter). Aggregate weekly. | Trends surface the top failure classes for admin triage. Rising transient-error rate signals an OpenRouter health problem; rising TikaParse signals malformed inputs and may motivate file-type restrictions. |
| F-5 | **Zero-retrieval rate** — `aiagent.retrieval.result_count == 0` fraction of total retrieval calls (Section 7 metric). | Continuous; weekly review. | Sustained > 20% over a week triggers "is the filter wrong / is the KB wrong / did someone swap the embedding model?" investigation checklist. Often the earliest signal that D-03 model-drift is biting. |

## 7. Production Monitoring

> Phase 5's production telemetry is **Micrometer counters + structured JSON logs**, not a managed tracing platform. This is the honest default for a Jmix add-on: the host already has Spring Boot Actuator; Micrometer ships with it; no new service dependency is mandated. Hosts that want a richer surface wire Phoenix / Langfuse / their existing APM via the OTel bridge — documented as an extension point, not a baseline.

**Tracing Tool:**

- **Default: Micrometer metrics + structured JSON logs.** All instrumentation lives inside the add-on as `MeterRegistry` counters / timers + `org.slf4j.Logger` events with MDC-propagated fields (`conversationId`, `userId`, `documentId` where applicable).
- **Optional: Arize Phoenix (or any OTel-compatible APM).** Hosts enable via Spring Boot Actuator's OTel exporter (`management.otlp.metrics.export.*` + `management.otlp.tracing.export.*`) pointing at a Phoenix / OTel collector endpoint. The add-on does not ship a Phoenix client, does not launch a Phoenix process, and does not mandate this integration. Documented in a `docs/observability.md` page in Phase 7.
- **Not used:** Langfuse, LangSmith, Braintrust, RAGAS — these are either LLM-judge-driven (out of scope for v1) or platform-account-dependent (does not fit a Jmix add-on's distribution shape).

**Key Metrics to Track:**

Every RAG retrieval call emits:

| Metric name | Type | Tags | Source |
|-------------|------|------|--------|
| `aiagent.retrieval.calls` | Counter | `userRoles` (pipe-delimited sorted), `filterHash` (sha256 of the canonical `Filter.Expression` string — **NOT** raw role names; avoids role-name PII in metrics), `adminBypass` (bool) | Incremented in `ChatService.ask(...)` after the filter is built, before `.call()`. |
| `aiagent.retrieval.result_count` | DistributionSummary | `filterHash`, `adminBypass` | Number of `Document`s returned by `VectorStoreDocumentRetriever` — captured in a wrapping advisor or by reading the advisor's response context. |
| `aiagent.retrieval.latency` | Timer | `filterHash` | Wall-clock from filter-built to retrieved-docs-attached-to-prompt. |
| `aiagent.retrieval.embedding_model` | Gauge | `model` | Current value of `spring.ai.openai.embedding.options.model` — lets dashboards correlate retrieval metrics with the configured model and spot a recent swap. |
| `aiagent.retrieval.similarity_threshold_hit_rate` | DistributionSummary | — | `(docs_returned) / topK` — dashboards whether retrieval is mostly filling the budget or mostly falling short (early signal for KB coverage gaps). |

Every ingestion event emits:

| Metric name | Type | Tags | Source |
|-------------|------|------|--------|
| `aiagent.ingest.started` / `aiagent.ingest.ready` / `aiagent.ingest.failed` | Counter | `errorType` on `.failed` only | `IngestionStatusWriter` transitions. |
| `aiagent.ingest.embed_retry_count` | DistributionSummary | `errorType` | Per-document total retries consumed; surfaces OpenRouter health. |
| `aiagent.ingest.duration` | Timer | `fileType` (`md` / `pdf` / `txt` / `html`) | Per-document ingest wall-clock. |
| `aiagent.ingest.executor.queue.size` | Gauge | — | `ThreadPoolTaskExecutor.getThreadPoolExecutor().getQueue().size()` — back-pressure signal. |
| `aiagent.ingest.chunks_written` | DistributionSummary | — | Per-document chunk count at ingest completion. |

Every atomic-delete emits:

| Metric name | Type | Tags | Source |
|-------------|------|------|--------|
| `aiagent.delete.calls` | Counter | `outcome` (`success` / `rolled_back`) | `KnowledgeDocumentService.delete(...)`. |
| `aiagent.delete.chunks_removed` | DistributionSummary | — | Rows affected by `VectorStore.delete(Filter.Expression)`. |

**Structured log events (JSON, via SLF4J + Logstash encoder):**

- `rag.retrieval.completed` — `{conversationId, userId, userRoleCount, filterHash, adminBypass, resultCount, embeddingModel, similarityThreshold, latencyMs}`
- `rag.ingest.started` — `{documentId, source, fileType, sizeBytes, submittedBy, allowedRolesCount}`
- `rag.ingest.completed` — `{documentId, status (READY|FAILED), chunksWritten, retryCount, durationMs, errorType?}`
- `rag.delete.completed` — `{documentId, chunksRemoved, outcome, latencyMs}`

**Role names are NEVER logged raw.** Only `userRoleCount` (cardinality) and `filterHash` (irreversible digest) — role codes are treated as identifying data per defence-in-depth practice, and a `filterHash` is enough to correlate a suspicious retrieval result with the filter shape that produced it. If incident response needs the actual filter, it is reconstructible from `userId` + the current role assignment at incident time.

**Alert Thresholds:**

| Alert | Condition | Priority | Response |
|-------|-----------|----------|----------|
| Ingestion failure rate high | `rate(aiagent.ingest.failed[1h]) > 0.05 * rate(aiagent.ingest.started[1h])` | High (page on-call) | Check OpenRouter status + recent uploads; likely transient provider issue or malformed file-type surge. |
| Retrieval zero-result rate high | `rate(aiagent.retrieval.result_count == 0[1h]) / rate(aiagent.retrieval.calls[1h]) > 0.20` | High (page on-call) | Most likely causes: (a) embedding-model drift (check `aiagent.retrieval.embedding_model` changed recently), (b) metadata-contract mismatch after a code change, (c) genuinely empty KB. Run flywheel metric F-2 to confirm or rule out (a). |
| Atomic-delete rollback | `rate(aiagent.delete.calls{outcome="rolled_back"}[15m]) > 0` | Critical (page immediately) | Indicates pgvector ↔ entity datasource transaction boundary broken. Run `AtomicDeleteRollbackIntegrationTest` locally; inspect recent config changes to datasource / PTM. Non-zero rollback is a compliance-visible regression. |
| Ingest executor queue saturation | `aiagent.ingest.executor.queue.size > 80` for 10 min | Medium (alert) | Back-pressure is functioning but approaching caller-runs fallback. Consider raising `queue-capacity` or adding worker threads; investigate whether a bulk reingest is under way. |
| Embedding model changed unexpectedly | `aiagent.retrieval.embedding_model` gauge value differs from last deploy's recorded value | Medium (alert) | Cross-check with an intentional config change; if unintentional, roll back and trigger F-2 flywheel metric. |
| Orphan chunks detected | Flywheel F-1 nightly job returns count > 0 | Medium (alert) | Correlates with atomic-delete regressions or manual DB tampering. Open a ticket with the offending documentId(s). |

**Smart Sampling Strategy:**

- **Every retrieval call is counted** (Micrometer counters are cheap); latency / result_count distributions sample at Micrometer's default.
- **Structured log events are emitted at INFO for `rag.retrieval.completed` / `rag.ingest.completed` / `rag.delete.completed` by default** — hosts with high volume can downgrade `rag.retrieval.completed` to DEBUG and still retain metrics for post-hoc analysis.
- **Signal-based human-review queue (if a host adopts one):**
  - `resultCount == 0` AND `userRoleCount > 0` AND `adminBypass == false` — "user with roles got nothing" is the single highest-value signal; sample 100% into the review queue.
  - `resultCount == topK` AND query text is very short (< 15 chars) — over-broad match candidates; sample 10%.
  - Any `rag.ingest.completed` with `status=FAILED` — 100% into the review queue with the full `errorMessage`.
- **No LLM-judge sampling in v1.** A host that wants answer-quality sampling wires it outside the add-on using the `AuditListener` SPI (Phase 4).
- **PII posture:** the sampling signals above operate on `filterHash`, `userRoleCount`, and result-shape metadata — not on raw queries or raw role names. Hosts with stricter posture can disable the `rag.retrieval.completed` INFO log entirely via the standard `logging.level.*` surface.
