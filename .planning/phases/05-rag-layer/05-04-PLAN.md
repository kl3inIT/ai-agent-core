  <behavior>
    - `@Service @Transactional` class. Constructor inject: DataManager, VectorStore, CancellationRegistry, AsyncIngestionWorker, IngestionStatusWriter.
    - `delete(UUID documentId)`:
      1. Load document (throw DocumentNotFoundException if absent).
      2. cancellationRegistry.cancel(documentId) — signals any in-flight worker to stop between batches.
      3. vectorStore.delete(FilterExpressionBuilder.eq(ChunkMetadata.DOCUMENT_ID, documentId.toString()).build()).
      4. dataManager.remove(document).
      5. Everything inside steps 2–4 runs in the caller's @Transactional(REQUIRED). If step 3 throws, Spring rolls back step 4 → entity remains → admin sees status unchanged → can retry. If step 4 throws, Spring rolls back but step 3 already sent delete to pgvector — document this limitation in a javadoc: "pgvector delete is not transactional with JPA. On entity-remove failure the vectors are already gone; operator must retry delete to clean up the entity." (This is acceptable per D-06 because the dangerous failure mode — orphaned vectors visible to retrieval — cannot occur.)
    - `reingest(UUID documentId)`:
      1. Load document (throw DocumentNotFoundException if absent).
      2. cancellationRegistry.cancel(documentId); cancellationRegistry.clear(documentId) (reset any stale flag).
      3. vectorStore.delete(FilterExpressionBuilder.eq(DOCUMENT_ID, documentId.toString()).build()) — purge old chunks.
      4. ingestionStatusWriter.markProcessing(documentId) — flips status back to PROCESSING even if caller rolls back.
      5. After caller commit: asyncIngestionWorker.ingest(documentId) (use afterCommit synchronization).
    - Reingest purposely does NOT dataManager.save the document — IngestionStatusWriter owns status transitions.

    Test cases:
    - delete happy path: loads, cancels, vectorStore.delete called with documentId filter, dataManager.remove called, no exceptions
    - delete when document is missing → DocumentNotFoundException, no vectorStore or cancellationRegistry calls
    - delete when vectorStore.delete throws → exception propagates, dataManager.remove NOT called (verifies rollback ordering)
    - delete invokes cancellationRegistry.cancel BEFORE vectorStore.delete (argument ordering verified via InOrder)
    - reingest happy path: cancels, clears, vector-delete, markProcessing, scheduler fires afterCommit
    - reingest when document missing → DocumentNotFoundException
    - reingest cancels+clears even when vectorStore.delete throws (cancellation state must not leak across re-ingests)
  </behavior>

@Component
public class IngesterManager {
    private static final Logger log = LoggerFactory.getLogger(IngesterManager.class);
    private final List<CustomIngester> ingesters;
    private final KnowledgeDocumentUploadService uploadService;

    public IngesterManager(List<CustomIngester> ingesters, KnowledgeDocumentUploadService uploadService) {
        this.ingesters = ingesters; this.uploadService = uploadService;
    }

    public void runAll() {
        for (CustomIngester ingester : ingesters) {
            try {
                List<Document> docs = ingester.read();
                for (Document d : docs) {
                    try {
                        String source = String.valueOf(d.getMetadata().getOrDefault("source", d.getId()));
                        uploadService.upload("ingester://" + ingester.getId() + "/" + source, "CUSTOM_INGESTER", List.of());
                    } catch (Exception perDoc) {
                        log.error("Ingester {} failed on document {}: {}", ingester.getId(), d.getId(), perDoc.getMessage());
                        // continue to next document? no — break to next ingester to bound blast radius
                        break;
                    }
                }
            } catch (Exception perIngester) {
                log.error("Ingester {} failed: {}", ingester.getId(), perIngester.getMessage(), perIngester);
            }
        }
    }
}
