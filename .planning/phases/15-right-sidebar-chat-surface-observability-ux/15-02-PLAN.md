<objective>
Add the additive `StreamingEvent.Activity(ActivityKind kind)` variant (closed enum `{CHAT, TOOL, RETRIEVAL}`) per decision D-05, and emit it from the orchestration edge — `AuditingDocumentRetriever.retrieve(...)` emits `Activity(RETRIEVAL)` at retrieval start; `ToolCallbackAuditDecorator` emits `Activity(TOOL)` alongside its existing `ToolCall` emit; `DefaultChatServiceImpl` emits `Activity(CHAT)` before the model stream (decide explicitly vs. UI-derived per Claude's Discretion). Add the compiler-forced no-op `Activity` arm to every exhaustive `switch` over `StreamingEvent` (currently only `StreamEventRenderer.renderStreamEventDetails`). All emit sites are best-effort (swallow `RuntimeException` — observability must never break a turn).

Purpose: This variant is the KIND source for Plan 04's ephemeral streaming-status line. The no-leak guarantee is structural — only a closed enum constant ever crosses to the UI; the fragment maps it to a `msg://` string and never touches `toolName`/`argsJson`. Plan 04 (the fragment consumer) and Plan 03 (the surface) both depend on or sit alongside this; landing it in Wave 1 unblocks them.

Output: `StreamingEvent.Activity` + `ActivityKind`; emit calls in the retriever, tool decorator, and chat impl; the `RetrievalAugmentationAdvisorFactory` constructor-arg wiring; updated `StreamEventRenderer`; extended `RenderStreamEventTest`; new `StreamingActivityEventTest`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| orchestration edge (retriever / tool decorator / chat impl) → streaming sink → UI | The new `Activity(ActivityKind)` event crosses to the browser via the existing `StreamingEvent` flux; only a closed enum constant ever crosses — no `toolName`, no `argsJson`, no entity name |
| RAG retrieval / tool callback → observability emit | A best-effort side-effect; a failure here must not affect the security-critical retrieval/tool path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-B1 | Information disclosure | `StreamingEvent.Activity` payload reaching the UI | mitigate | `ActivityKind` is a closed enum `{CHAT, TOOL, RETRIEVAL}` — structurally cannot carry a `@Tool` method name or entity name. The emit sites pass only the enum constant, never `toolName`/`argsJson`/`resultSummary`. TEST-19 (Plan 05) enforces the rendered text never matches the Phase 9 leak regexes. |
| T-15-B2 | Denial of service | observability emit failing inside `retrieve(...)` or a tool callback | mitigate | Every `tryEmitNext(new StreamingEvent.Activity(...))` is wrapped in `try { } catch (RuntimeException ignored) { }` (mirrors the existing `ToolCallbackAuditDecorator.emitToolEvent` and the retriever's audit-write-never-rethrows convention); `streamingSinkHolder` is null-guarded. Tested in `StreamingActivityEventTest`. |
| T-15-B3 | Tampering | persisted `AiAuditEvent` shape / the advisor chain | mitigate (avoid) | The emit sites are deliberately OUTSIDE `ChatService`-proper, the advisor chain, and the audit-write path — no new audit row, no changed row shape, no advisor-chain behavior change beyond the factory injecting one extra `@Component`. Verified by `git diff` (no `AiAuditEvent.java` change) and the unchanged audit-row tests. |
| T-15-B4 | Spoofing | `Activity(RETRIEVAL)` emitted with the wrong `runId` so it lands on another run's sink | mitigate | `runId` resolved exactly as the existing retriever code does (`RunContext.get()` then `query.context().get("audit.runId")`); `streamingSinkHolder.currentOrForRun(runId)` (prefers `forRun(runId)`, falls back to `current()`) — same lookup `ToolCallbackAuditDecorator` already trusts. Worst case on mismatch: the status line silently doesn't show — no cross-user leak (the sink is per-run, registered by `DefaultChatServiceImpl.stream`). |
</threat_model>
