## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host shell (AppLayout / StandardMainView) ↔ ChatSurfaceMounter | The mounter walks the UI tree to find the AppLayout; degrades gracefully (warn-once, skip) if absent — no throw |
| browser DOM (the fixed-position panel Div, the push class) ↔ server-side Flow component tree | The panel Div + push class are server-managed Flow elements; the only "client input" is the toggle click event |
| user ↔ SIDEBAR surface visibility | A user without chat-view permission must not get the panel or the toggle |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-C1 | Broken access control | the side-panel Div + navbar toggle mounted for a user without chat permission | mitigate | Gate the SIDEBAR mount/show on the same `isDialogViewPermitted()` (`UiShowViewContext` + `accessManager.applyRegisteredConstraints`) check the HEADER_BUTTON dialog uses, AND on `AiUiSettings.getEnabledSurfaceSet().contains(AiChatSurface.SIDEBAR)`. Tested: not-permitted ⇒ neither mounted. |
| T-15-C2 | Information disclosure | (none new) — the panel hosts the existing shared `ChatPanelFragment`; no new data path | accept | No new data crosses to the UI here; the fragment's existing security posture is unchanged. The observability text (status line / disclosure) is added in Plan 04 with its own threat model + TEST-19. |
| T-15-C3 | Tampering / XSS | the in-panel close button / panel header text | mitigate | All button labels via `msg://` keys + `Element.setText(...)` (HTML-escaped) — no `innerHTML`, no user free-text. The panel header carries only the close button (icon + aria-label from `msg://`). |
| T-15-C4 | Denial of service | the panel Div torn down / re-created racing the framework on every navigation | mitigate | Attach the Div to `UI.getCurrent().getElement()` (not the AppLayout content slot, which `setContent()`-replaces on navigation); on `AfterNavigationEvent` re-assert attachment idempotently (re-append only if detached) — mirrors the existing `attachDialogWindowToUi` pattern for the modeless dialog. Tested: panel persists across two route changes. |
| T-15-C5 | Session-scope leak | sidebar open-state / panel handle stored at too-broad a scope | mitigate | Store the sidebar `panelDiv` / `toggleButton` / `sidebarOpen` on the per-UI `MountedChatSurfaceState` (`ComponentUtil.getData(ui, ...)`) or the `@UIScope` `AiChatUIState` — both correctly per-UI, never `AiChatSessionState` (which stays at `currentConversationId` + listeners — that's Plan 04/OBS-04's concern, but respected here too). |
