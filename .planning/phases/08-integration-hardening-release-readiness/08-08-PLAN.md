## Why all three RED tests share one classpath root cause

### The Jmix authorization contract

Jmix 2.8 separates authorization into two layers:

1. **Decision layer** — `AccessManager.applyRegisteredConstraints(AccessContext)` walks `AccessConstraintsRegistry.getConstraints()` and invokes `constraint.applyTo(context)` for each registered constraint matching the context type. The decision is then read off the populated context (`crudEntityContext.isReadPermitted()`, etc.). If NO matching constraint is registered, the context's default state is preserved — and `CrudEntityContext` defaults to PERMIT-ALL.

2. **Registration layer** — Spring beans annotated with `@PostConstruct registerConstraints()` push individual constraints into the registry at startup. `jmix-security-2.8.0` ships `SecurityConstraintsRegistration` (registers `ExportImportEntityConstraint`, `SpecificConstraintImpl`, `EntityAttributeConstraint`). `jmix-security-data-2.8.1` ships `SecurityDataConstraintsRegistration` (registers `CrudEntityConstraint`, `ReadEntityQueryConstraint`, `InMemoryCrudEntityConstraint`, `LoadValuesConstraint`).

### Why each RED test is RED

- **RED-1** `carol_filteredSchema_excludesDenied_andDeniedAttributes`: `CurrentUserSchemaAccess.canReadEntity` calls `accessManager.applyRegisteredConstraints(crudEntityContext)` then `crudEntityContext.isReadPermitted()`. Without `jmix-security-data-starter`, `CrudEntityConstraint` is NOT in the registry; the call is a no-op; `isReadPermitted()` returns `true` by default. Carol therefore sees ALL entities, including `ai_AiAuditEvent`.
- **RED-2** `carol_findRecordsDeniedEntity_returnsAccessDeniedJson`: `BuiltInDataTools.resolveReadableEntityOrThrow` calls `currentUserSchemaAccess.canReadEntity(metaClass)`. Same root cause as RED-1 — returns `true` for carol; the `access_denied` envelope is never thrown.
- **RED-3** `userB_listingConversations_doesNotIncludeUserA_agentStoreScoped`: `dataManager.load(AiConversation.class).all().list()` does NOT route through `CurrentUserSchemaAccess`. Row-level enforcement at the JPA layer is performed by `ReadEntityQueryConstraint` (also registered by `SecurityDataConstraintsRegistration`), which intercepts query transformation and appends the `@JpqlRowLevelPolicy where {E}.createdBy = :current_user_username` clause. Without the dep, the query runs unfiltered and bob sees alice's row.

### Why misread of the executor's escalation does NOT change the architectural fix

Investigation #2's executor framed the failure as "`UnconstrainedDataManager` does NOT bypass `DataStoreCrudListener`". That framing is incorrect — the cited stack passed through `UnconstrainedDataManagerImpl` only as internal class delegation from constrained `DataManagerImpl`, which sets `SaveContext.authorizationRequired=true` first; `UnconstrainedDataManager` called directly DOES set `authorizationRequired=false` and DOES bypass the listener. The Jmix Context7 docs and project memory `feedback_jmix_unconstrained_for_system_writes` are correct and applicable. The executor's misread does not invalidate the architectural pattern; it only means the pattern needs to be applied to `ProjectingChatMemoryRepository` (the actual stack-trace origin) instead of being abandoned.

### Architectural fix (validated against Jmix 2.8 docs)

Per Jmix Context7 docs (`/jmix-framework/jmix-context7` → `data-access/data-manager.html`):

> The `UnconstrainedDataManager` interface provides the same methods as `DataManager` but bypasses all security policy checks. It can be used to override security constraints when necessary in your application code.

Use case match: audit log writes AND chat-memory pruning are system-internal persistence that must succeed regardless of caller authentication. `UnconstrainedDataManager` declares this intent at the type level, is the canonical Jmix pattern (also recommended for Quartz jobs and unauthenticated contexts per the same doc), and avoids the role-grant brittleness of `runWithSystem`. Project memory `feedback_jmix_unconstrained_for_system_writes` confirms this is the project standard.

### Why this is one cohesive plan

- **Single classpath fix** (gradle dep) registers BOTH `CrudEntityConstraint` (RED-1, RED-2) AND `ReadEntityQueryConstraint` (RED-3) via the same `SecurityDataConstraintsRegistration` bean.
- **Single architectural pattern** (`UnconstrainedDataManager` for system-internal persistence) covers AuditWriter (audit pipeline), ProjectingChatMemoryRepository (chat-memory pruning), and the test fixtures that exercise these paths under `runWithSystem`.
- **Symmetric write/read application:** any system-internal entity (`ai_AiAuditEvent`, `ai_AiMessage`, `ai_AiConversation`, `ai_AiParameters`, `ai_AiKnowledgeDocument`) accessed under `runWithSystem` or arbitrary user auth needs `.unconstrained()` for both write paths AND verification-read paths.

All five edits are coordinated; landing any subset leaves a regression hole.
