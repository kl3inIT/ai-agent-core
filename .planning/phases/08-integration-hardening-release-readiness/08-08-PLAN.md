## Why all three RED tests share one root cause

The executor MUST NOT skip this section — it explains why a one-line gradle change is the entire fix and what to verify.

### The Jmix authorization contract

Jmix 2.8 separates authorization into two layers:

1. **Decision layer** — `AccessManager.applyRegisteredConstraints(AccessContext)` walks `AccessConstraintsRegistry.getConstraints()` and invokes `constraint.applyTo(context)` for each registered constraint matching the context type. The decision is then read off the populated context (`crudEntityContext.isReadPermitted()`, etc.). If NO matching constraint is registered, the context's default state is preserved — and `CrudEntityContext` defaults to PERMIT-ALL for every operation.

2. **Registration layer** — Spring beans annotated with `@PostConstruct registerConstraints()` push individual constraints into the registry at startup. `jmix-security-2.8.0` ships `SecurityConstraintsRegistration` (registers `ExportImportEntityConstraint`, `SpecificConstraintImpl`, `EntityAttributeConstraint`). `jmix-security-data-2.8.1` ships `SecurityDataConstraintsRegistration` (registers `CrudEntityConstraint`, `ReadEntityQueryConstraint`, `InMemoryCrudEntityConstraint`, `LoadValuesConstraint`).

### Why each RED test is RED

**RED-1** `carol_filteredSchema_excludesDenied_andDeniedAttributes`:
`CurrentUserSchemaAccess.canReadEntity(MetaClass)` at line 75-79 calls `accessManager.applyRegisteredConstraints(crudEntityContext)` then `crudEntityContext.isReadPermitted()`. Without `jmix-security-data-starter`, `CrudEntityConstraint` (the bean that calls `secureOperations.isEntityReadPermitted(metaClass, policyStore)` and only sets `setReadDenied()` when there's no ALLOW policy) is NOT in the registry. So `applyRegisteredConstraints` is a no-op for `CrudEntityContext`, and `isReadPermitted()` returns its default of `true`. Carol therefore sees ALL entities, including `ai_AiAuditEvent`.

**RED-2** `carol_findRecordsDeniedEntity_returnsAccessDeniedJson`:
`BuiltInDataTools.resolveReadableEntityOrThrow` line 279 calls `currentUserSchemaAccess.canReadEntity(metaClass)`. SAME root cause as RED-1 — returns `true` for carol on `ai_AiAuditEvent`, so the `access_denied` envelope at line 280 is never thrown. Instead, the query proceeds with empty result rows.

**RED-3** `userB_listingConversations_doesNotIncludeUserA_agentStoreScoped`:
`dataManager.load(AiConversation.class).all().list()` does NOT route through `CurrentUserSchemaAccess` — instead it goes through Jmix's `LocalDataManager` → EclipseLink session. Row-level policy enforcement at the JPA layer is performed by `ReadEntityQueryConstraint` (in `jmix-security-data` package `io.jmix.securitydata.constraint`), which intercepts query transformation and appends the `@JpqlRowLevelPolicy where` clause (`{E}.createdBy = :current_user_username` from `AiAgentUserRowLevelRole.conversation()`). Without `jmix-security-data-starter`, `ReadEntityQueryConstraint` is also not in the registry, so the query runs unfiltered. Bob sees alice's row.

### Why this is one fix

A SINGLE class — `io.jmix.securitydata.impl.constraint.SecurityDataConstraintsRegistration`, packaged in `jmix-security-data-2.8.1.jar` — registers BOTH `CrudEntityConstraint` (fixes RED-1, RED-2) AND `ReadEntityQueryConstraint` (fixes RED-3) into the `AccessConstraintsRegistry` at `@PostConstruct`. Adding `jmix-security-data-starter` to ai-agent.gradle pulls the autoconfig that wires this bean. ONE dependency line. ONE classpath addition. THREE tests flip GREEN.

### Why the existing 9 GREEN tests in com.vn.agent.security stay green

- `AdminViewAccessTest` (5 tests) uses `UiShowViewContext`, registered by `jmix-security-flowui` — unaffected by adding `jmix-security-data`.
- `RagRoleFilterNegativeTest` (2 tests) calls `RetrievalFilterBuilder.buildFor(Authentication)`, an in-house bean that reads roles directly from authentication — does not use `AccessManager` or `DataManager` at all.
- `CrossUserConversationAccessTest.userB_replayingUserAConversation_throwsSameTypeAndCodeAsRandomUuid` (1 test) goes through `ChatService.ask` → `ConversationGateway.loadOrCreate` which uses an EXPLICIT `createdBy = :owner` JPQL predicate — works regardless of constraint registry contents.
- `FilteredSchemaAndExecutionDenialTest.dave_filteredSchema_includesEntity_butExcludesProtectedAttributes` (1 test) — currently passes because dave has BOTH the entity-level READ AND the attribute-level VIEW grants. With `CrudEntityConstraint` newly active, the entity will still be readable for dave (he has explicit ALLOW), and `EntityAttributeConstraint` (already in registry from `jmix-security-starter`) keeps filtering protected attributes. Stays green.

### Phase 2 forensics observation about HSQLDB metadata

`FoundationsBootSmokeTest.java` lines 198-209 documents:
> "ReadEntityQueryConstraint (the JPA-layer enforcement bean) lives in jmix-security-data... Pulling it in as a test-only dep breaks the metadata wiring on HSQLDB (AccessDenied under runWithSystem + EclipseLink 'not a known Entity type' on persist — the securitydata module reshapes the persistence unit)."

This was a Phase 2 observation when `jmix-security-data-starter` was attempted as a TEST-only dep. Two reasons it should not recur in this plan:

1. **Production scope, not test scope:** We're adding it as `implementation` (production dep), not `testImplementation`. This matches `jmix-app/build.gradle:49` which is the canonical Jmix application shape. `jmix-app` boots cleanly on HSQLDB+Postgres with this exact config.

2. **The Phase 2 break was about persistence-unit reshaping caused by additional securitydata-owned entities (`RowLevelPolicyEntity`, `ResourcePolicyEntity` in `io.jmix.securitydata.entity` package).** Those entities are storage for the optional Jmix-UI-managed roles feature. The ai-agent module uses ONLY annotation-based roles (`@ResourceRole` interfaces in `com.vn.agent.security`), so those entities are not persisted, but they ARE present in the metamodel. EclipseLink may try to map them.
   - **Mitigation:** `runWithSystem` in `FoundationsBootSmokeTest.all_five_entities_round_trip` performs writes; if EclipseLink chokes on the new entities, the test fails. Task 3 below explicitly re-runs this test as a regression gate. If it fails, the plan addresses it via the standard Jmix `jmix.core.entity-name-prefix` / `Stores` partitioning — both `RowLevelPolicyEntity` and `ResourcePolicyEntity` are in the `main` store (different from the ai-agent's `agentstore`), so they should not collide with `agentstore`-owned tables.

### Architectural impact (informational)

This change makes the ai-agent module's security posture self-contained: a host consuming `ai-agent-starter` will get correctly-enforced entity-policy + row-level-policy without needing to add `jmix-security-data-starter` themselves. This is the correct shape for a security-sensitive add-on.
