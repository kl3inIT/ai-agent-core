# Phase 13.1 Plan 05: ChatPanelFragment Java rewire — right-pane attachments + NOTICE rendering + budget toast Summary

Wave-4 controller-side plug into the stable Phase 13.1-04 XML/CSS surface. Single-file rewrite of `ChatPanelFragment.java` that retires the Phase 13 chip-strip + MessageList substrate, programmatically binds the `taskFilesDl` data loader to the active conversation, dispatches history replay by role into mixed bubble/notice substrate (Pitfall 7 Option A), persists a NOTICE `AiMessage` on every successful upload + appends a `<vaadin-message class="attachment-event">` divider in the message list, and surfaces the budget-exceeded toast from `ChatResponseDto.budgetExceeded()` / `StreamingEvent.Final.budgetExceeded()` via a single `ui.access`-routed helper. Phase 12 contract files have ZERO diff.

## New Private Helpers

| Helper                                            | Role |
|---------------------------------------------------|------|
| `refreshTaskFiles()`                              | empty-state toggle: shows `attachmentsEmptyState` when `taskFilesDc` is empty, otherwise shows `attachmentsGridLayout`. |
| `appendBubble(MessageBubbleComponent.Role, String)` | constructs a `MessageBubbleComponent` (USER or ASSISTANT) and appends to `messageListSlot`; returns the bubble for streaming-append. |
| `appendNoticeRow(String)`                         | builds a raw `<vaadin-message class="attachment-event">` element via Vaadin Element API and appends to `messageListSlot.getElement()`. T-13.1-17: `setProperty("text", ...)` HTML-escapes by default. |
| `clearMessageList()`                              | wipes `messageListSlot.removeAll()` (Components) + `messageListSlot.getElement().removeAllChildren()` (raw vaadin-message rows) and resets `botBubble = null` + `messageCount = 0`. |
| `nextSeq(UUID conversationId)`                    | `select max(m.seq) from ai_AiMessage m where m.conversation.id = :cid` via `DataManager.loadValue(...).store("agentstore")` (memory `feedback_jmix_loadvalue_store`); returns `maxSeq + 1`, defaulting to `0` for empty conversations. |
| `showBudgetExceededToast()`                       | `ui.access`-routed `notifications.create(messages.getMessage("chatView.attachments.budgetExceeded")).withThemeVariant(LUMO_WARNING).show()`. |
| `onBlockingResponse(ChatResponseDto)`             | package-private blocking-path consumer surface — invokes `showBudgetExceededToast()` when `response.budgetExceeded()` is true. Currently called by tests + future hosts; the live `.stream()` subscriber wires the toast directly inside `doOnNext` for `StreamingEvent.Final`. |

## Conversation-Lifecycle Wiring

| Site                                  | Action |
|---------------------------------------|--------|
| `onReady()`                           | If `conversationId != null`, prime `taskFilesDl.setParameter("conversationId", id)` + `load()`; call `refreshTaskFiles()` for the initial empty-state state. |
| `setConversationIdInternal(UUID cid)` | After `clearMessageList()`: if `cid == null`, clear loader parameter, set `taskFilesDc.setItems(List.of())`, `refreshTaskFiles()`. If `cid != null`, set parameter + `load()`, then dispatch history replay by role into `appendBubble` / `appendNoticeRow`. |
| `ensureConversationIdForSubmit(...)`  | After conversation is created/resolved, set loader parameter + `load()` so the right-pane reflects task files for the new conversation thread. |
| `ensureConversationIdForUpload()`     | Same as above for the upload-before-first-message path. |
| `handleUploadedFile(...)`             | After `dataManager.save(row)`: persist `AiMessage(role=NOTICE)` attributed to the uploading user (log-and-continue on failure), `appendNoticeRow` under `accessUi`, then `taskFilesDl.load()` under `accessUi` so the empty-state toggle re-fires. |

## Budget-Exceeded Toast Wiring

| Path        | Site                                                                        | Accessor                              |
|-------------|-----------------------------------------------------------------------------|---------------------------------------|
| Streaming   | `onSubmit` `.doOnNext(evt -> { ... if (evt instanceof StreamingEvent.Final f) { ... if (f.budgetExceeded()) showBudgetExceededToast(); } })` | `StreamingEvent.Final.budgetExceeded()` |
| Blocking    | `onBlockingResponse(ChatResponseDto response)` package-private hook         | `ChatResponseDto.budgetExceeded()`    |

The streaming consumer is the live UI path. `onBlockingResponse` is the test/host surface that consumes the same flag from `.ask`-style callers; the streaming-fallback inside `DefaultChatServiceImpl.stream()` (Plan 13.1-03) routes through the same `Final` event with the budget flag propagated, so the streaming consumer also covers the streaming-fallback case.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Compile / verify-gate compatibility] Bundle-key resolution form**

- **Found during:** Implementation of `showBudgetExceededToast` and the NOTICE row content formatter.
- **Issue:** The plan listed `messages.getMessage(ChatPanelFragment.class, "chatView.attachments.budgetExceeded")` and `messages.formatMessage(ChatPanelFragment.class, "chatView.attachments.notice", ...)`. The class-scoped `Messages.getMessage` form derives the message group from the caller's package (`com.vn.agent.view.chat.fragment`), but per project memory `feedback_jmix_messages_over_spring`, all `chatView.attachments.*` keys live in the root `com.vn.agent` bundle (`messages.properties` / `messages_vi.properties`). The class-scoped form would miss the entries at runtime.
- **Fix:** Switched `showBudgetExceededToast` to the bare `messages.getMessage(key)` form (default group resolution falls back to the root bundle). Switched the NOTICE content formatter to the explicit-group `messages.formatMessage("com.vn.agent", key, params)` form. Both forms hit the root bundle. Verify counts unaffected (the literal `chatView.attachments.budgetExceeded` and `chatView.attachments.notice` still appear in code exactly once each).
- **Files modified:** `ai-agent/ai-agent/src/main/java/com/vn/agent/view/chat/fragment/ChatPanelFragment.java` (no separate commit — the fix landed before the single Task 1+2+3 commit).
- **Commit:** `38940f8` (rolled into the main commit).

**2. [Rule 3 — Compile / verify-gate compatibility] Comment phrasing in field-list block**

- **Found during:** Verify regex `MessageListItem` returned 1 match (in a comment) instead of 0.
- **Issue:** A documentation comment in the field-block read "message-count tracker replaces the old MessageListItem buffer" — the verify regex scans both code and comments, so the literal token tripped the gate.
- **Fix:** Rewrote the comment to "message-count tracker replaces the old item buffer" — same historical narrative, no gate token.
- **Files modified:** Same file.
- **Commit:** `38940f8` (rolled into the main commit).

### Plan-vs-Implementation Note: Single Commit for All 3 Tasks

The plan defines 3 sequential tasks all targeting the same file (`ChatPanelFragment.java`). The plan itself acknowledges in each task's `<done>` block that "Compile may still be red until Tasks 2 + 3 land — full library compile is asserted at end of Task 3." Per the executor's `task_commit_protocol`, atomic per-task commits would be intermediate non-compiling states. Pragmatic resolution: the rewrite landed as a single coherent commit `38940f8` covering all three task deliverables (field/loader rewire + NOTICE substrate migration + budget toast + Phase 12 zero-diff guard). This matches the spirit of "one self-contained logical change per commit"; the alternative — three commits, each leaving the build red — would violate the `compile-on-every-commit` invariant of CI hooks.
