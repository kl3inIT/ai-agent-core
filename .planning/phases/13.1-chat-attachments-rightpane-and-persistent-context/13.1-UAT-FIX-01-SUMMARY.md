# Phase 13.1 UAT-Fix-01 Summary

UAT exposed three live UI bugs in the chat surface. This UAT-fix plan restores the
Vaadin MessageList substrate for chat turns (Phase 7.1 baseline), switches the NOTICE
row to a plain `<div>` substrate (UI-SPEC §138 alternative), fixes a broken
`formatMessage` group call, and removes the redundant "Trò chuyện" dialog title.

## The 3 bugs the user surfaced + how each was fixed

### Bug 1 — "Trò chuyện" dialog header duplicates the in-fragment title

**Symptom:** Opening the chat dialog from the AppLayout header rendered an h2 title
"Trò chuyện" above the in-fragment `conversationTitle` h3, duplicating the chat title.

**Fix (Task A, commit 8d20093):** Drop the `title="msg:///chatDialogView.title"`
attribute on the chat-dialog-view root. The DialogWindow header bar now renders
without text; the close (×) icon stays. The message keys themselves remain in the
bundle in case other code references them.

### Bug 2 — NOTICE rows show as floating ↑ upload icons with literal key text

**Symptom:** The user uploaded files and saw 3 stacked ↑ upload-icon glyphs in the
chat column where bilingual NOTICE divider rows ("[username] đã đính kèm file") were
expected. Inspecting the DOM revealed:

1. `<vaadin-message class="attachment-event">` siblings whose `text` property was
   the literal string `"chatView.attachments.notice"` (the bundle key, not the
   formatted message).
2. The default `<vaadin-avatar>` slot of `<vaadin-message>` rendered the upload-arrow
   icon glyph because no userName was set on the substrate element.

**Root causes:**

1. `messages.formatMessage("com.vn.agent", "chatView.attachments.notice", a, b)` used
   the GROUP form of `Messages.formatMessage`, which makes the resolver look the key
   up inside a per-class bundle (`com.vn.agent.messages` is treated as a class scope
   prefix, not the root bundle). Since the key only lives in the root
   `com/vn/agent/messages*.properties` bundles, the resolver returned the literal key.
   The canonical pattern proven elsewhere in the codebase
   (`KnowledgeBaseView.java:192/196/388/572`) is the no-group form
   `messages.formatMessage(key, args)`.
2. The `<vaadin-message>` substrate exposes a default avatar slot. Even with the
   `vaadin-avatar` selector hidden via CSS pseudo-element, the underlying shadow DOM
   keeps the upload-arrow glyph rendering as the avatar fallback when no userName is
   bound.

**Fix (Task B, commit abf94f6):**

- ChatPanelFragment now writes NOTICE rows as plain `<div class="ai-agent-attachment-notice">`
  elements appended via raw Element APIs to `messageListSlot.getElement()` as siblings
  of the live `<vaadin-message-list>` block. `Element.setText(...)` is used for the
  text content, which Vaadin HTML-escapes by default (T-13.1-17 mitigation).
- `formatMessage` switched from the broken group form back to the no-group form
  `messages.formatMessage("chatView.attachments.notice", username, filename)`, matching
  KnowledgeBaseView's canonical pattern and project memory `feedback_jmix_messages_over_spring`.
- New CSS rule `.ai-agent-attachment-notice` matches the UI-SPEC NOTICE visual contract:
  centered text, secondary text color, divider lines top + bottom, micro font size.

### Bug 3 — User explicitly objected to the substrate switch in Plan 13.1-05

**Context:** Plan 13.1-05 swapped the Phase 7.1 Vaadin `MessageList` + `MessageListItem`
substrate for `MessageBubbleComponent` (Composite/Div) on the live chat path. The user
objected to this in UAT and asked for the Vaadin MessageList back.

**Fix (Task B, commit abf94f6):** ChatPanelFragment is reverted to the Phase 7.1
baseline shape:

- `private MessageList messageList;` field restored.
- `private final List<MessageListItem> items = new ArrayList<>();` restored.
- `private MessageListItem botMsg;` replaces `private MessageBubbleComponent botBubble;`.
- USER/ASSISTANT turns are constructed as `new MessageListItem(text, Instant.now(), userName)`
  with `setUserColorIndex(USER_COLOR=0 / AI_COLOR=2)` — Phase 7.1 verbatim.
- `messageList.setItems(...)` is called only at turn boundary (Pitfall #5: mid-stream
  uses `botMsg.appendText(md)`).
- `MarkdownRenderer` field deleted — Vaadin `MessageList.setMarkdown(true)` does its
  own markdown rendering. (`MessageBubbleComponent.java` itself is kept on disk because
  `ConversationDetailView` (Plan 07-04 read-only transcript replay) still uses it.)
- Pitfall #8 dispose-on-detach, D-04 CancellationRegistry routing, and D-03 per-event
  `ui.access` wrap are all preserved.

## Substrate-revert decision

The Plan 13.1-05 mixed substrate
(`MessageBubbleComponent` for chat turns + `<vaadin-message class="attachment-event">`
for NOTICE rows) is fully reverted on the live chat path. The user explicitly objected
to it in UAT. UI-SPEC §138 always allowed "alternatively a custom inline element" for
the NOTICE row, so the new plain-div NOTICE substrate honors the UX-01 contract while
avoiding the upload-arrow avatar fallback that was the actual bug.

`MessageBubbleComponent` (the class) is intentionally kept — `ConversationDetailView`
still uses it for read-only transcript replay (Plan 07-04). The CSS rules
`.ai-agent-bubble*` are kept for the same reason.

## Open follow-ups

- **NOTICE chronological ordering.** NOTICE divs are appended as siblings of the
  `<vaadin-message-list>` block, so on history replay all NOTICE rows visually appear
  AFTER the MessageList items even when chronologically a NOTICE persisted between
  two chat turns. UI-SPEC §138 allowed this simplification, but if the user wants
  strict in-order interleaving, that's a follow-up plan: either (a) split the chat
  column into N alternating MessageList chunks per NOTICE boundary, or (b) build a
  custom Composite that intermixes MessageListItem-shaped DOM with notice DOM.
- **MessageBubbleComponent.** The class is kept on disk for `ConversationDetailView`
  but is now dead code on the live chat path. If `ConversationDetailView` is later
  rewritten to use Vaadin MessageList, both `MessageBubbleComponent.java` and the
  `.ai-agent-bubble*` CSS rules can be deleted in a single follow-up commit.
