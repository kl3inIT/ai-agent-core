# Phase 13.1: Chat Attachments — CRM-Style Right-Pane + Persistent Multi-Turn Context — Specification

**Created:** 2026-05-06
**Ambiguity score:** 0.127
**Requirements:** 9 locked
**Parent phase:** 13 (completed 2026-05-06) — see `../13-chat-task-input-stt-task-scoped-file/13-SPEC.md`

## Goal

Replace Phase 13's chip-strip-above-MessageInput attach affordance with a verbatim port of the `D:/DTH/jmix-crm` right-pane Attachments panel (`<split>` + `<gridLayout>` of cards + drop-zone) AND change `AiTaskFileMediaResolver` from single-turn injection (`injectedAt IS NULL` predicate) to per-turn-all injection of every non-expired `AiTaskFile` row in the conversation, gated by a token-budget cap. Default `AiTaskFile` lifetime extends from 1h to 24h (configurable, with `-1` sentinel meaning "no TTL"). Each upload also persists an inline `AiMessageRole.NOTICE` row that renders between message bubbles and is filtered out of the LLM prompt.

## Background

Phase 13 shipped 2026-05-06 with a working attach-then-LLM-reads pipeline but two design choices that post-ship UX review found wrong against the verbatim `D:/DTH/jmix-crm` reference:

**Wrong layout (current code):** `chat-panel-fragment.xml:52-81` declares `<vbox attachmentsPanel visible="false">` between `messageListSlot` and `messageInputSlot`, plus a separate `<hbox attachRow>` with a `📎` button + `<upload>` inline. `ChatPanelFragment.java:97` declares `attachmentsPanel` as `VerticalLayout` (chip strip). 0px footprint when empty → undiscoverable. No drop-zone, no per-file metadata, no empty-state affordance.

**Wrong resolver semantics (current code):** `AiTaskFileMediaResolver.resolvePending(UUID)` returns rows where `injectedAt IS NULL AND expiresAt > :now` (file:106-119). After send, `AiTaskFileRepository.markInjected(ids)` writes `injectedAt = now()` so subsequent resolves return nothing. This breaks "AI agent thực thụ" multi-turn workflow: turn 1 attach xlsx → turn 1 sees `Media`; turn 2 asks "phân tích cột B" → empty `Media`, model sees only its own prior text response and cannot re-inspect bytes.

**Wrong default TTL (current code):** `application.properties` ships `ai-agent.task-file.ttl-seconds=3600` (1h). Multi-turn analysis sessions easily exceed 1h.

**CRM reference (`D:/DTH/jmix-crm/.../ai-conversation-detail-view.xml`):** `<split orientation="HORIZONTAL" splitterPosition="68">` with chat left + Attachments right (`<vbox attachmentsPanel>` containing `<h3 attachmentsTitle>` + `<gridLayout attachmentsGridLayout>` + `<fragmentRenderer>` from `AiAttachmentCardFragmentRenderer` + `<upload classNames="attachments-dropzone" dropAllowed="true" dropLabel>`). CRM's `AiAttachmentMediaResolver` is single-shot like Phase 13's (CRM use case is single-shot Q&A over a doc), but Phase 13.1's per-turn-all resolver is required for the agent-core "agent thực thụ" workflow.

Phase 13 schema (`090-ai-task-file.xml`): `AI_TASK_FILE` has `MESSAGE_ID` (nullable, FK with `onDelete=SET NULL`) + `INJECTED_AT` (nullable, single-turn marker). `CONVERSATION_ID` already has `deleteCascade="true"` — assumption A2 from CONTEXT.md verified ✓. Per-turn-all + persistent-context lifecycle eliminates both the `MESSAGE_ID` and `INJECTED_AT` columns; Phase 13.1 ships a Liquibase 100 to drop them.

`AiMessageRole` enum (`AiMessage.java:57-58`) is stored as `varchar(16)` `ROLE_` column. Adding a `NOTICE` value is a +1 enum entry with no schema change.

2. **Per-turn-all `Media` resolver (RES-01)**: `AiTaskFileMediaResolver` returns ALL non-expired `AiTaskFile` rows for the conversation on every turn (not just rows with `injectedAt IS NULL`).
   - Current: `AiTaskFileMediaResolver.resolvePending(UUID)` (file:101-119) loads `where e.conversation.id = :cid and e.injectedAt is null and e.expiresAt > :now order by e.createdDate asc`. `DefaultChatServiceImpl` calls `resolvePending(...)` then after persisting the user message calls `AiTaskFileRepository.markInjected(ids)` to set `injectedAt = now()`.

3. **Token-budget cap with LRU eviction + audit (AUDIT-01)**: Per-turn-all resolver applies a configurable cap; over-cap drops oldest rows and emits an audit event.
   - Current: No cap exists (Phase 13's single-turn resolver was naturally bounded by per-turn upload count).
   - Target: New `AiTaskFileProperties` fields `perTurnMaxFiles` (default 10) and `perTurnMaxTotalBytes` (default 52428800 = 50 MB), config keys `ai-agent.task-file.per-turn-max-files` and `ai-agent.task-file.per-turn-max-total-bytes`. Sentinel value `-1` on either field disables that cap independently. `AiTaskFileMediaResolver.resolveActive(...)`: after loading rows ordered `createdDate DESC` (most-recent first), iterates and includes rows while accumulated `count <= perTurnMaxFiles AND accumulated bytes <= perTurnMaxTotalBytes`; rows beyond the cap are dropped (oldest dropped first because the load is DESC). When at least one row is dropped, resolver emits one `AuditWriter.writeToolCall(eventName="task_file_budget_exceeded", outcome=SUCCESS, argumentsJson={conversationId, totalRows, totalBytes, keptRows, keptBytes, droppedRows, droppedBytes, perTurnMaxFiles, perTurnMaxTotalBytes})` per turn. NO new `AuditKind`.
   - Acceptance: `@SpringBootTest BudgetCapTest` attaches 11 small files (each 1KB) to a conversation, calls `resolveActive(convId)`, asserts returned `Media` list has 10 entries (most recent 10), asserts exactly one `AiAuditEvent` row exists with `eventName=task_file_budget_exceeded` whose `argumentsJson` parses to `{totalRows: 11, keptRows: 10, droppedRows: 1, ...}`; second test attaches 6 files of 10MB each, asserts `keptRows: 5, keptBytes: 52428800` (5 × 10MB); third test sets `per-turn-max-files=-1` and `per-turn-max-total-bytes=-1`, attaches 11 files, asserts `Media` list size = 11 and zero `task_file_budget_exceeded` rows.

4. **Lifecycle change — default TTL 24h + `-1` sentinel (LIFE-01)**: `AiTaskFile` default lifetime is 24 hours (was 1 hour). Operators can set `-1` for "no TTL — only delete on conversation delete via FK cascade".

Per-turn cap default of 50 MB chosen because base64-encoded multimodal payload is ~33% larger than raw bytes (~67 MB encoded), which empirically fits in Qwen3.6-VL's context window for typical xlsx/pdf workloads while leaving headroom for chat history + tool definitions; operators with smaller context windows MUST tune down via `per-turn-max-total-bytes`.
- **Destructive Liquibase migration**: `100-ai-task-file-drop-dead-columns.xml` runs on a table that shipped 1 day prior. Spec-phase locked this choice over the conservative "keep nullable, deprecate" alternative because the column is dead-on-arrival in 13.1 and v1.1 is still pre-release. Discuss-phase verifies no production deployments exist before plan-phase commits this.
- **NOTICE row prompt filter**: filter MUST happen at the chat-memory boundary (`JdbcChatMemoryRepository` query OR explicit `DefaultChatServiceImpl` filter step) — implementation locus is a discuss-phase decision; correctness is a SPEC requirement.
- **Servlet multipart**: `spring.servlet.multipart.max-file-size=100MB` and `max-request-size=110MB` from Phase 13 already accommodate per-file 100 MB uploads; no `application.properties` multipart changes.
