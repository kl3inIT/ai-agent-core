## `LiquibaseSchemaTest` Dialect-Detection Branch

The plan's interfaces section called for runtime JDBC catalog queries with PostgreSQL → H2 fallback. The boot regression (deferred-items.md) blocks every `@SpringBootTest` on this module, so the test ships as a pure XML parse against the source changelog instead. The dialect-detection branch is therefore **N/A by design** — the assertion targets are the deletion-target set the JDBC query would observe post-migration:

| Assertion | XML check (this test) | Equivalent JDBC catalog query (future port) |
|-----------|------------------------|---------------------------------------------|
| FK_AI_TASK_FILE__ON_MESSAGE absent | exactly one `<dropForeignKeyConstraint constraintName="FK_AI_TASK_FILE__ON_MESSAGE"/>` in 100 changelog | `select constraint_name from information_schema.referential_constraints where table_name='AI_TASK_FILE'` returns no row matching |
| IDX_AI_TASK_FILE__ON_MESSAGE absent | `<dropIndex indexName="IDX_AI_TASK_FILE__ON_MESSAGE" tableName="AI_TASK_FILE"/>` present in 100 | `select index_name from information_schema.statistics where table_name='AI_TASK_FILE'` returns no row matching |
| IDX_AI_TASK_FILE__INJECTED_AT absent | `<dropIndex indexName="IDX_AI_TASK_FILE__INJECTED_AT" tableName="AI_TASK_FILE"/>` present in 100 | same query, no row matching |
| MESSAGE_ID column absent | `<dropColumn columnName="MESSAGE_ID" tableName="AI_TASK_FILE"/>` present in 100 | `select column_name from information_schema.columns where table_name='AI_TASK_FILE'` returns no row matching |
| INJECTED_AT column absent | `<dropColumn columnName="INJECTED_AT" tableName="AI_TASK_FILE"/>` present in 100 | same query, no row matching |
| FK_AI_TASK_FILE__ON_CONVERSATION present (Pitfall 10) | inline `<constraints foreignKeyName="FK_AI_TASK_FILE__ON_CONVERSATION" deleteCascade="true"/>` on the `CONVERSATION_ID` column in 090 | `select constraint_name, delete_rule from information_schema.referential_constraints` returns CASCADE row |
| FK-drop precedes column-drop in changeSet order | `changeSetIndexContaining(FK_DROP) <= changeSetIndexContaining(MESSAGE_ID_DROP)` | order-invariant at runtime, but the XML order is the source of truth |

When the upstream boot regression clears, a follow-up plan can port LiquibaseSchemaTest to a `@SpringBootTest + JdbcTemplate` shape with no semantic loss — the assertion targets are identical.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — assertion mismatch] Conversation FK is declared INLINE on the column, not via `<addForeignKeyConstraint>`**

- **Found during:** Task 2 first verify run — `conversationCascadeFkSurvivesInTheCreateChangelog` failed at `LiquibaseSchemaTest.java:147` with `<addForeignKeyConstraint>` returning no `FK_AI_TASK_FILE__ON_CONVERSATION` entry.
- **Issue:** The plan's `<read_first>` cited 13.1-RESEARCH Pitfall 10 ("`FK_AI_TASK_FILE__ON_CONVERSATION` survives; assertion on `referential_constraints`") but the 090 changelog actually declares the conversation FK INLINE on the `CONVERSATION_ID` column via `<constraints foreignKeyName="FK_AI_TASK_FILE__ON_CONVERSATION" deleteCascade="true"/>` (Phase 13 D-03 design). The separate `<addForeignKeyConstraint>` at id="3" is reserved for `FK_AI_TASK_FILE__ON_MESSAGE` (which has explicit `onDelete="SET NULL"` per REVIEWS HIGH-2). My initial assertion shape assumed both FKs were declared the same way and tripped on the empty `<addForeignKeyConstraint>` lookup.
- **Fix:** Rewrote `conversationCascadeFkSurvivesInTheCreateChangelog` to (a) locate the `CONVERSATION_ID` `<column>`, (b) read its inline `<constraints>` child, (c) assert `foreignKeyName="FK_AI_TASK_FILE__ON_CONVERSATION"` + `deleteCascade="true"`, and (d) defensively assert that no `<addForeignKeyConstraint>` ever names the conversation FK (would imply duplicate declaration). Same Pitfall 10 invariant pinned, correct XML shape.
- **Files modified:** `ai-agent/ai-agent/src/test/java/com/vn/agent/liquibase/LiquibaseSchemaTest.java`
- **Commit:** `62165ba` (rolled into Task 2 — fix landed before commit so the test stayed green at HEAD).

**2. [Rule 4 architectural exception → autonomous] UI tests ship as XML/source-scan, not @UiTest**

The plan's interfaces section called for `@UiTest` Vaadin TestBench / Karibu DOM assertion. Plan 13.1-06 confirmed (and documented) that the module-level Spring-context boot regression at `.planning/phases/13-chat-task-input-stt-task-scoped-file/deferred-items.md` blocks runtime of every `@SpringBootTest` on this module — including `@UiTest`, which extends `@SpringBootTest`. The plan author also explicitly anticipated the deferred boot blocker in the project context preamble: *"If that blocker affects @SpringBootTest in this plan, mirror Plan-06's stance: pin assertions correctly + document the inheritance + still run the source-scanner / locale-parity / XML-schema tests that don't need a live context."*

Per that explicit directive, this plan ships UI tests as XML-descriptor parse + source-scan against the same contract surfaces (Vaadin element ids in `chat-panel-fragment.xml`, the `appendNoticeRow` / `clearMessageList` helpers in `ChatPanelFragment.java`, both surface descriptors mounting the same fragment FQN). Mirrors the precedent shipped under Plan 12-04: `ChatDialogViewTest.descriptorComposesChatPanelFragmentWithoutCustomChrome` (XML parse) + `ChatSurfaceMounterTest.mounterUsesVaadinServiceInitAndRequiredRuntimeGates` (source string assertion). When the upstream boot regression clears, a follow-up plan can port these to live `@UiTest` without semantic loss — the assertion targets are identical.

This is documented as an autonomous Rule-4 deviation (architectural change to test substrate) explicitly authorized by the plan's `<project_context>` preamble, not a checkpoint return.
