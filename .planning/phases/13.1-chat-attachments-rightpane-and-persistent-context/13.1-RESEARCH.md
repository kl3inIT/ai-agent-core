## Summary

Phase 13.1 is a UX + lifecycle reshape of an already-shipped Phase 13. The locked CONTEXT.md (D-A1, D-A2, D-B1, D-B2, D-C1, D-D1) and UI-SPEC already resolve the high-risk decisions: NOTICE preservation is a 1-line JPQL change in `ProjectingChatMemoryRepository.saveAll`; layout port is verbatim XML from `D:/DTH/jmix-crm/.../ai-conversation-detail-view.xml`; card renderer is verbatim `FragmentRenderer<JmixCard, AiTaskFile>` plus an `EXTERNAL_LINK→DOWNLOAD` icon swap and a `TRASH` delete button; budget-exceeded is a `Resolved.budgetExceeded` boolean → `Notifications.WARNING` toast paired with an `AuditWriter.writeToolCall("task_file_budget_exceeded", ...)` row; per-extension card icon table (csv/xlsx → TABLE, pdf/html/htm/md/txt → FILE_TEXT_O, png/jpg/jpeg/gif/webp → FILE_PICTURE, default → FILE_O) is shipped because the CRM analog already provides it (see `D:/DTH/jmix-crm/.../AiAttachmentCardFragmentRenderer.java:108-115`).

The biggest landmine the planner must absorb is **the SPEC-vs-current property naming drift**. SPEC §4 and §6 specify `ai-agent.task-file.ttl-seconds=86400` with `-1` sentinel; the existing `AiTaskFileProperties.java` (`ttl: Duration = PT1H`) and `application.properties` (`ai-agent.task-file.ttl=PT1H`) use Spring `Duration` not seconds. A long-running test (`AiTaskFileCleanupJobTest`, `AiTaskFileMediaResolverIntegrationTest`, `AiTaskFileNoVectorStoreInvocationTest`) already pin the `ttl=PT1H` Duration form. The planner has two options: (A) keep `Duration` and use `Duration.ofSeconds(-1)` / `Duration.ofDays(1)` defaults with a custom `-1` sentinel detection, OR (B) flip the property to `ttl-seconds=86400` (long, with `-1` sentinel detection trivial) and update the 3 tests. **Recommendation: Option B** — the SPEC explicitly names `ttl-seconds=-1` as the sentinel, which is more idiomatic for a sentinel-bearing knob than `Duration.ofSeconds(-1)`. This is a `[CITED: 13.1-SPEC.md REQ-4]` hard requirement, not a discretionary stylistic choice.

The second landmine is the **`AiInternalEntityNames` mismatch** with the new NOTICE row inserts. `AiInternalEntityNames` (`D:/DTH/ai-agent-core/ai-agent/ai-agent/src/main/java/com/vn/agent/exposure/AiInternalEntityNames.java:11-20`) gates entities from LLM tool exposure but does NOT currently include `ai_AiTaskFile` (Phase 13 left it off — task files are user-scoped data, not LLM-tool surface). NOTICE `AiMessage` rows pose no new exposure surface because `ai_AiMessage` is already on the list (line 14). No `AiInternalEntityNames` change is needed for Phase 13.1.

**Primary recommendation:** Plan 6 waves (TASK-06 layout reshape; TASK-07 resolver per-turn-all + budget cap; TASK-08 lifecycle 24h + sentinel; TASK-09 NOTICE row + render + filter; SCHEMA-01 Liquibase 100; TEST-18 multi-turn integration) with TASK-06 and TASK-07 fully parallelizable after a Wave-0 schema change locks the entity shape.

```java
public Resolved resolveActive(UUID conversationId) {
    if (conversationId == null) {
        return Resolved.empty();
    }
    List<AiTaskFile> rows = dataManager.load(AiTaskFile.class)
            .query("select e from ai_AiTaskFile e " +
                    "where e.conversation.id = :cid and e.expiresAt > :now " +
                    "order by e.createdDate desc")
            .parameter("cid", conversationId)
            .parameter("now", OffsetDateTime.now())
            .list();
    if (rows.isEmpty()) {
        return Resolved.empty();
    }

    int maxFiles = taskFileProperties.getPerTurnMaxFiles();          // -1 disables file cap
    long maxBytes = taskFileProperties.getPerTurnMaxTotalBytes();    // -1 disables byte cap

    List<AiTaskFile> kept = new ArrayList<>();
    long keptBytes = 0;
    int droppedRows = 0;
    long droppedBytes = 0;
    long totalBytes = 0;
    for (AiTaskFile row : rows) {
        long size = row.getSizeBytes() == null ? 0L : row.getSizeBytes();
        totalBytes += size;
        boolean fileCapHit = (maxFiles >= 0) && (kept.size() >= maxFiles);
        boolean byteCapHit = (maxBytes >= 0) && (keptBytes + size > maxBytes);
        if (fileCapHit || byteCapHit) {
            droppedRows++;
            droppedBytes += size;
            continue;
        }
        kept.add(row);
        keptBytes += size;
    }

    boolean budgetExceeded = droppedRows > 0;
    if (budgetExceeded) {
        try {
            String argumentsJson = buildBudgetArguments(conversationId,
                    rows.size(), totalBytes, kept.size(), keptBytes,
                    droppedRows, droppedBytes, maxFiles, maxBytes);
            auditWriter.writeToolCall(
                    /*parentId*/ null,
                    /*runId*/ runContextRunIdOrNew(),
                    /*userUsername*/ currentUsername(),
                    /*conversationId*/ conversationId,
                    /*toolName*/ "task_file_budget_exceeded",
                    argumentsJson,
                    /*resultSummary*/ null,
                    /*latencyMs*/ 0L,
                    AiToolCallOutcome.SUCCESS,
                    /*denialReason*/ null,
                    /*errorClass*/ null);
        } catch (RuntimeException auditEx) {
            log.warn("Failed to write task_file_budget_exceeded audit row for conv={}", conversationId, auditEx);
        }
    }

    List<Media> media = kept.stream().map(this::buildMedia).toList();
    return new Resolved(media, budgetExceeded);
}

public record Resolved(List<Media> media, boolean budgetExceeded) {
    public static Resolved empty() { return new Resolved(List.of(), false); }
    public boolean isEmpty() { return media.isEmpty(); }
}
```

## Common Pitfalls

### Pitfall 1: SPEC says `ttl-seconds` but existing code uses `Duration ttl`
**What goes wrong:** Plan writes `ai-agent.task-file.ttl-seconds=86400` to `application.properties`, but `AiTaskFileProperties.java` binds `Duration ttl` to `ai-agent.task-file.ttl`. Boot fails (unbound property warning) AND the new key is silently ignored. Tests that already use `ai-agent.task-file.ttl=PT1H` pass while production behavior is broken.

**Why it happens:** SPEC was written without re-reading existing properties; the Phase 13 build pivoted from `ttl-seconds` (SPEC) to `ttl=PT1H` (Duration) per `13-REVIEWS.md` MEDIUM line 180.

**How to avoid:**
- **Recommended:** Plan-phase locks `AiTaskFileProperties.ttlSeconds : long` with `-1` sentinel (matches SPEC exactly). Update `application.properties` (`ttl=PT1H` → `ttl-seconds=86400`). Update 3 test files (`AiTaskFileCleanupJobTest`, `AiTaskFileMediaResolverIntegrationTest`, `AiTaskFileNoVectorStoreInvocationTest`) to use the new key.
- **Alternative:** Keep `Duration ttl` and add `boolean ttlDisabled` derived field; `application.properties` sets `ai-agent.task-file.ttl=PT24H`; sentinel becomes `ttl=PT0S` or `ttl=-PT1S` (unintuitive). Discouraged.

**Warning signs:** `application.properties` has `ai-agent.task-file.ttl=...` but `taskFileProperties.getTtlSeconds()` is what the code reads.

### Pitfall 2: NOTICE row inserted before `AiConversation` exists
**What goes wrong:** User uploads a file before typing first message → `ChatPanelFragment.handleUploadedFile` calls `ensureConversationIdForUpload` which creates a conversation; THEN the AiTaskFile insert succeeds; THEN the NOTICE `AiMessage` insert needs `conversation`. If the NOTICE insert reuses a stale `AiConversation` reference loaded BEFORE `ensureConversationIdForUpload`, the FK is null.

**Why it happens:** The Phase 13 upload handler at line 769 reloads `conversation` after the `ensureConversationIdForUpload` call returns. NOTICE insert must do the same.

**How to avoid:** In the new NOTICE insert block, reuse the same `conversation` variable that was loaded right above the AiTaskFile insert (`ChatPanelFragment.java:769`). Do NOT re-load — the loaded reference is fresh.

### Pitfall 3: Budget-exceeded audit lacks runId/userUsername
**What goes wrong:** `AuditWriter.writeToolCall` (`AuditWriter.java:148`) requires `runId` (non-null), `userUsername`, and `conversationId`. The resolver runs INSIDE a chat turn so `RunContext.get()` returns the runId — but the resolver may also be called from tests or admin flows where `RunContext` is unset.

**Why it happens:** `RunContext` is a ThreadLocal set by `DefaultChatServiceImpl.ask`/`stream` (line 195 + 440). Tests calling `resolveActive` directly bypass this.

**How to avoid:**
- In `resolveActive`, fall back to `UUID.randomUUID()` if `RunContext.get()` returns null (mirrors `AuditWriter.findChatRootId(null)` defensive pattern at line 246).
- Resolve `userUsername` via `currentAuthentication.getUser().getUsername()`. Fall back to `"system"` if anonymous (matches `BaselineContextProvider#safeGetUser` pattern referenced in `DefaultChatServiceImpl.java:805-809`).
- The audit row's `parent_id` is null (no chat root in this context) — `AuditWriter.findChatRootId` will look it up via runId; if not found, the row is orphaned but persisted (line 169 of `AuditWriter.java` warn-and-continue).

### Pitfall 4: Vaadin `<gridLayout>` `gap=` attribute
**What goes wrong:** XML schema may reject inline `gap="var(--lumo-space-xs)"`.

**Why it happens:** Jmix Flow UI 2.8 schema may only accept enum values (`small`/`medium`/`large`) for `gap`.

**How to avoid:** If `gap=` rejects the CSS-var syntax, drop the attribute and add `vaadin-grid-layout { gap: var(--lumo-space-xs); }` to the CSS append. Fallback works because `<gridLayout>` renders as `<vaadin-grid-layout>`. Plan-phase verifies via Context7 lookup `mcp__context7__get-library-docs` against `jmix-framework/jmix-context7` for "gridLayout gap".

### Pitfall 5: `taskFilesDl` parameter binding

**Why it happens:** Jmix data-load coordinators auto-bind from view query parameters but a `Fragment` has no query params; the parent view must seed.

**How to avoid:** In `ChatPanelFragment.setConversationIdInternal` (line 347), after setting `this.conversationId`, call:
