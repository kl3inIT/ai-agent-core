## NOTICE row preservation in `ProjectingChatMemoryRepository`

| Option | Description | Selected |
|--------|-------------|----------|
| A. Delete query exclude `role='notice'` | 1-line JPQL change in `saveAll`: add `and m.role <> :noticeRole` predicate. NOTICE rows survive every projection | ✓ |
| B. NOTICE in separate `AiAttachmentEvent` entity | New entity + Liquibase 110 + role policy + UI merge logic; clean schema isolation but heavy | |
| C. saveAll subscribe AiTaskFile event + re-insert | Event-subscriber re-inserts NOTICE rows after each delete-recreate; race-y, double source of truth | |

**User's choice:** A
**Notes:** Critical scout finding upstream: `ProjectingChatMemoryRepository.findByConversationId` delegates to Spring AI's `JdbcChatMemoryRepository` (separate `SPRING_AI_CHAT_MEMORY` table). NOTICE rows live ONLY in `AI_AGENT_MESSAGE`, so they are structurally invisible to the LLM-prompt path — SPEC REQ-5 "filter at chat-memory boundary" is satisfied automatically. The real engineering work is preserving NOTICE rows during `saveAll`'s delete-recreate cycle, hence Option A.

## Card UI fields + actions

| Option | Description | Selected |
|--------|-------------|----------|
| Mirror CRM + add Delete button | icon + filename + meta (createdDate + sizeBytes formatted) + 2 actions: open=download + delete=remove file. Confirmation dialog on delete | ✓ |
| Mirror CRM exactly (open only, no delete) | Verbatim CRM port: open button only. User must wait TTL to clear unwanted file | |
| Full meta + TTL countdown + delete | Adds per-card TTL countdown ("expires in 23h 14m") | |

**User's choice:** Mirror CRM + Delete
**Notes:** Delete button gives user control over what's in agent context (e.g., clear stale xlsx before asking unrelated question). TTL countdown rejected to avoid per-second DOM churn and visual noise. Open action explicitly = download (not inline preview) for v1.1; preview deferred.
