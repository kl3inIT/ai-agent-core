# Phase 13.1 Context — Pre-Spec Working Doc

**Purpose of this doc:** capture the post-Phase-13 UX review decision and the locked design intent BEFORE running `/gsd-spec-phase 13.1`. The spec phase will turn this into REQ-IDs with ambiguity scores.

**Authoritative parent:** `../13-chat-task-input-stt-task-scoped-file/13-SPEC.md` — Phase 13 SPEC. All Phase 13 invariants (TEST-16, MIME allowlist, role policies, FileStorage code path, audit shape, Liquibase 090) carry over unchanged unless overridden below.

## 1. Why this phase exists

Phase 13 shipped a working "attach a file → LLM reads it" pipeline, but two design choices proved wrong in post-ship UX review against the verbatim `D:/DTH/jmix-crm` reference:

### Wrong choice #1 — Chip-strip layout above MessageInput

**Phase 13 picked:** `<vbox attachmentsPanel visible="false">` between `messageListSlot` and `messageInputSlot`, plus an `<hbox attachRow>` with `📎` button + `<upload>` inline. Visible only when chips exist; 0px footprint when empty.

**CRM picked:** Right-pane Attachments panel — `<vbox>` taking ~30% horizontal width, header `Attachments`, body `<gridLayout>` of `<card>` fragments (icon + filename + timestamp + uploader + open button), footer `<upload>` with prominent drop-zone + Upload button. Empty state: Jmix logo + `There's nothing here yet...`.

**Side-by-side from screenshots (CRM dialog + CRM detail view + agent-core dialog):**

| Tiêu chí | CRM right-pane | Phase 13 chip-strip |
|---|---|---|
| Discoverability | high — panel always visible | low — paperclip nhỏ, panel ẩn khi rỗng |
| Empty state affordance | "There's nothing here yet..." + drop-zone | none |
| Drop-zone | yes (kéo-thả vùng lớn) | no (phải click) |
| Per-file metadata | filename + timestamp + uploader + open | filename only |
| Inline ledger ("[user] added X") | yes, in message stream | no |
| Footprint when empty | ~30% chiều ngang | 0px |
| Enterprise feel | đậm (Slack/Teams pattern) | mỏng (ChatGPT pattern) |

**Original Phase 13 rationale that didn't hold:**
- "ChatDialogView dialog hẹp không vừa right-pane" — **falsified** by `D:/DTH/jmix-crm` `CRM AI` dialog screenshot (provided 2026-05-06): the CRM dialog uses the same right-pane layout and dialog renders cleanly.
- "v1.1 không có nội dung right-pane khác" — true, but Attachments IS the right-pane content; argument was circular.
- "MessageInput không có prefix/suffix slot" — true, but irrelevant to right-pane decision (right-pane lives outside the input row).

### Wrong choice #2 — Single-turn `Media` injection (Phase 13 REQ-4)

**Phase 13 picked:** `AiTaskFileMediaResolver` returns ONLY rows where `messageId IS NULL`. After send, two-phase write `UPDATE AiTaskFile SET messageId = newMessageId`. Subsequent turns receive empty `Media`. Rationale: Spring AI `JdbcChatMemoryRepository` text-only persistence; jmix-crm `AiAttachmentMediaResolver` does the same.

**Why it's wrong for "AI agent thực thụ":**
- Phase 13 SPEC line 19 host requirement: "bulk-import là *capability* của một 'AI agent thực thụ'".
- Real workflow: user uploads xlsx → asks `phân tích cột A` (turn 1, sees Media) → asks `đếm số dòng valid` (turn 2, **empty Media** — model sees only its own prior text response, can't recompute against the file) → asks `bulk_save_records cho 50 dòng đầu` (turn 3, **empty Media** — model can't read the file to extract the records).
- Workaround "model remembers from text history" is brittle: text response summarizes the file at low fidelity, and the model can't re-inspect bytes.
- Counter-claim "jmix-crm does the same" is true but CRM's use case is single-shot Q&A over an attached doc, NOT multi-turn agentic workflow with tool use.

**Phase 13.1 picks:** per-turn-all `Media` injection with token-budget cap. Resolver returns ALL non-expired rows for the conversation. Cap (`per-turn-max-files=10`, `per-turn-max-total-bytes=52428800` default 50 MB) MUST be present to avoid context blow-up; over-cap → keep N most-recent files (LRU by `createdAt DESC`) and audit `task_file_budget_exceeded`. `messageId` two-phase write is removed.

### Wrong choice #3 (consequence) — TTL 1h

Phase 13 default `ttl-seconds=3600` (1h) was chosen for "transient file" semantics. With per-turn-all + multi-turn agent workflow, 1h is too short — a long debugging session over an xlsx easily exceeds 1h. Phase 13.1 raises default to `86400` (24h) and adds `-1` sentinel for "no TTL, only delete on conversation delete" (Liquibase 090 already has FK `ON DELETE CASCADE` on `conversationId` — verify in spec-phase).

## 2. Locked design intent (input to spec-phase)

### D-01 — UI layout port from jmix-crm (verbatim)

**Source:** `D:/DTH/jmix-crm/src/main/resources/com/company/crm/ai/view/aiconversation/`
- `ai-conversation-detail-view.xml` (right-pane `<vbox attachmentsPanel>`, lines ~41–60 from earlier grep)
- `ai-attachment-card-fragment.xml` (card layout: icon prefix, h5 title, open button suffix, meta hbox with timestamp + source)
- `AiAttachmentCardFragmentRenderer.java` (`@Component` renderer wired to `<gridLayout>`)

**Port to:** `chat-panel-fragment.xml` + new `ai-task-file-card-fragment.xml` + new `AiTaskFileCardFragmentRenderer.java`. Reuse the CRM CSS class names (`attachments-dropzone`, `attachment-card-meta`, `attachment-card-source-icon`, `attachment-card-source-text`) — copy any associated styles from CRM into the agent-core stylesheet.

**Layout shape change:** `chat-panel-fragment.xml` rootLayout becomes a 2-column `<hbox>` (chat column ~70% + attachments column ~30%). Phase 13 chip-strip vbox + `<hbox attachRow>` are removed. `attachmentsPanel` slot identifier is preserved for Phase 12 fragment-contract continuity but its position + content changes.

**Both surfaces:** `ChatView` (FULL_ROUTE) + `ChatDialogView` (HEADER_BUTTON dialog) both render the new layout. Verify `D:/DTH/jmix-crm` has BOTH a detail view AND a dialog opener for `AiConversation` — if only the detail view exists, derive the dialog layout from the detail layout with width adjustments (no functional change).

### D-02 — Per-turn-all `Media` resolver with token-budget cap

**Resolver change:**
```java
// Phase 13 (current):
public ResolvedMedia resolvePending(UUID conversationId) {
    // returns rows WHERE messageId IS NULL
}

// Phase 13.1 (target):
public ResolvedMedia resolveActive(UUID conversationId) {
    // returns ALL non-expired rows for conversationId
    // applies budget cap (max files + max total bytes)
    // returns trimmed list + emits audit event if cap hit
}
```

**`DefaultChatServiceImpl` change:** call `resolveActive(convId)` on every turn, inject `Media` whenever non-empty. Remove the `markSent(...)` call entirely. `JdbcChatMemoryRepository` text-only persistence remains as-is (chat memory still stores text only — the resolver re-attaches `Media` from `AiTaskFile` rows on every turn).

**Budget config (new):**
```properties
ai-agent.task-file.per-turn-max-files=10
ai-agent.task-file.per-turn-max-total-bytes=52428800
```

**Over-cap behavior:** keep N most-recent rows (LRU `createdAt DESC`), drop the oldest, emit `AuditWriter.writeToolCall(eventName="task_file_budget_exceeded", arguments={conversationId, totalFiles, totalBytes, keptFiles, keptBytes})`. NO new `AuditKind`.

### D-03 — Lifecycle change: conversation-scoped, default TTL 24h

**Default config change:**
```properties
ai-agent.task-file.ttl-seconds=86400  # was 3600
```

**New sentinel:** `ttl-seconds=-1` → no TTL; rows persist until conversation deleted (FK cascade) or operator runs manual cleanup.

**`AiTaskFileCleanupJob` change:** if `ttlSeconds == -1`, skip TTL purge — only the FK cascade handles deletion. Otherwise existing hourly purge logic runs unchanged with the new default.

**Opportunistic purge in `DefaultChatServiceImpl`:** unchanged logic, but with the new default it fires far less often (rows only expire after 24h).

### D-04 — Inline attachment ledger row in message stream

**CRM precedent:** the CRM dialog screenshot shows a horizontal divider with text `[admin] added attachment "RDS Document (1).docx"` between message bubbles.

**Implementation options (decide in spec-phase):**
- **Option A:** insert a `MessageType=SYSTEM_NOTICE` row into `AiMessage` on every successful upload. Pros: persistent, replays on reload. Cons: changes `MessageType` enum + `JdbcChatMemoryRepository.findByConversationId` must filter `SYSTEM_NOTICE` out of the LLM prompt assembly path.
- **Option B:** render the notice as a non-persistent UI-only div in `MessageListSlot` driven by a client-side observer of `AiTaskFile` insert events. Pros: no DB schema change. Cons: lost on reload; harder to test.
- **Recommendation for spec:** Option A — persistent ledger matches CRM behavior and gives audit-style provenance. Option B is a fallback if the `MessageType` enum extension is rejected.

**Filtering constraint:** notice rows MUST NOT be sent to the LLM as user/assistant messages. Filter at `JdbcChatMemoryRepository` boundary or in `DefaultChatServiceImpl` before `chatClient.prompt()` chain.

**Bilingual messages:** `[%s] added attachment "%s"` (en) + `[%s] đã đính kèm "%s"` (vi).

### D-05 — Two-phase `markSent` write removal

The `messageId` UPDATE step from Phase 13 13-04-PLAN is removed. The `AiTaskFile.messageId` column itself is decided in spec-phase:
- **Option A:** keep column NULLABLE, mark deprecated in JavaDoc, never written.
- **Option B:** drop via Liquibase 100 cleanup changelog (`<dropColumn>`).
- **Recommendation:** Option A for v1.1; defer column drop to v1.2 cleanup phase. Avoids a destructive migration on a fresh-shipped table.

## 4. Risks and assumptions

| ID | Assumption | Risk if wrong | Mitigation |
|---|---|---|---|
| A1 | jmix-crm has both detail view AND dialog opener for `AiConversation` with the same right-pane layout | Spec-phase derives dialog layout from detail layout instead of porting verbatim | Verify in spec-phase by reading `AiConversationListView.java` for lookup-action / dialog-window invocations |
| A2 | Liquibase 090 has FK `ON DELETE CASCADE` on `AiTaskFile.conversationId` | "Conversation deleted → orphan rows + orphan blobs" bug | Spec-phase reads the changelog; if not cascade, add Liquibase 100 to fix |
| A3 | Qwen3.6-VL 262K context can absorb 50 MB total file payload across multi-turn conversation without truncation | Token-budget cap default of 50 MB is too high; turns get truncated | Spec-phase computes a realistic per-turn token cost from sample xlsx/pdf and recommends a safer default |
| A4 | Phase 12 `ChatSurfaceMounter` contract has no special handling for `attachmentsPanel` slot position (only its presence) | Layout reshape breaks one of the surfaces | Spec-phase reads `ChatSurfaceMounter` + both view XMLs to confirm |
| A5 | `MessageType` enum extension to add `SYSTEM_NOTICE` does not regress Phase 12 message rendering | Notice rows render as user/assistant bubbles by mistake | Spec-phase decides Option A vs B; if A, add explicit unit test for renderer dispatch |
| A6 | Per-turn-all resolver does NOT regress Phase 13 TEST-16 (no `IngesterManager` / `VectorStore` touch) | Re-implementing the resolver leaks a RAG dependency | Port the static-analysis test verbatim; CI catches regression |
| A7 | jmix-flowui 2.8 `<gridLayout>` + `fragmentRenderer` API is unchanged from Phase 13 ship date | Card grid doesn't render or renders incorrectly | Context7 lookup `jmix-framework/jmix-context7` for `gridLayout fragmentRenderer` before locking spec |
