### Locked Decisions

- **D-01** Mutable root row — one row per chat turn. `writeChatStart(runId, userUsername, conversationId, promptHash) -> UUID` INSERTs root (`parentId=null`, `kind=CHAT`, `startedAt=now`, finishedAt/outcome/eventName null). `writeChatFinish(parentId, latencyMs, outcome, errorClass)` LOADs same row in fresh `REQUIRES_NEW` tx and UPDATEs. ## Summary

Phase 7.2 rewrites the audit ledger into a self-referential tree using Jmir `@Composition` on a single entity, collapses the PRE/POST two-row chat pattern into a mutable root row, and wires end-to-end retrieval audit through the Spring AI `RetrievalAugmentationAdvisor` pipeline already in the repo. Transactional model from Phase 4 (`AuditWriter` as sole `REQUIRES_NEW` surface; `afterCommit` fan-out) is preserved verbatim; only the row shape, SPI method signature, and UI rendering change.

The single highest-risk mechanical item is the mutable-root UPDATE path: Jmix `@Composition` will cascade on `DataManager.save(root)`, so `writeChatFinish` MUST reload the root row inside its own `REQUIRES_NEW` tx and save it WITHOUT populating the `children` collection — otherwise child rows written earlier by tool/retrieval hooks could be re-saved or orphan-removed. A fresh load + null-children + save is the safe pattern and matches how Jmix `AiConversation` parent-only UPDATEs are already handled elsewhere in the repo.

Liquibase retire-and-cutover on an already-initialised dev DB is straightforward on Postgres + HSQLDB (`<dropTable cascadeConstraints="true">` works on both, and HSQLDB honours its default synonyms for `cascade`). The safest retire pattern for the two legacy changelogs is to leave them in place and add a new `090-ai-audit-event.xml` that unconditionally drops the old table first, then creates the new one — Liquibase will still see `030`/`080` as executed on the DEV_CHANGELOG and skip them; no `<validCheckSum>` or `preConditions` gymnastics needed since the drop + create in `090` puts the DB in the final target state regardless of what `030`/`080` did earlier.

**Primary recommendation:** Implement in this order — (1) new Liquibase changelog `090-ai-audit-event.xml` with `dropTable` + `createTable` + indexes; (2) `AiAuditEvent` entity (replace `AiToolCallAudit`, add `@ManyToOne parent` + `@OneToMany children` with `@Composition`); (3) `AuditKind` constants + `AuditListener` / dispatcher SPI rename; (4) `AuditWriter` rewrite (`writeChatStart`/`writeChatFinish`/`writeToolCall`/`writeRetrieval`); (5) `AuditAdvisor` + `ToolCallbackAuditDecorator` + `RunContext.rootAuditId`; (6) `RetrievalAugmentationAdvisorFactory` retrieval-audit hook (custom `DocumentRetriever` wrapper); (7) `SpiDefaultsAutoConfiguration` no-op update; (8) UI rename + tree rendering; (9) i18n drop + re-add; (10) tests.

### Pattern 1: Self-Referential `@Composition` Entity

**What:** One JPA entity with `@ManyToOne parent` + `@OneToMany(mappedBy="parent") children`, both flagged with Jmix `@Composition` (on the children collection), so the Flow UI's list view can render a hierarchy via the Jmix fetch plan and so cascade operations follow parent ownership semantics.

**When to use:** Any time a single row has both a "root" and a "sub-event" shape and the UI needs to render them in a parent-expands-to-children tree.

**Confidence:** HIGH for the pattern itself (mirrors `AiConversation` -> `AiMessage` `@Composition` already in repo at `AiConversation.java:50-53`). MEDIUM on the specific annotation combination when `mappedBy` points to the same class — this is less common than cross-entity `@Composition`; Jmix docs are the authority.

**Example (derived from existing `AiConversation` + canonical self-ref JPA):**

```java
// Source: adapted from AiConversation.java:50-53 + standard JPA self-ref
@Store(name = "agentstore")
@JmixEntity
@Entity(name = "ai_AiAuditEvent")
@Table(name = "AI_AGENT_AUDIT_EVENT", indexes = {
        @Index(name = "IDX_AI_AGENT_AUDIT_EVENT__ON_PARENT", columnList = "PARENT_ID"),
        @Index(name = "IDX_AI_AGENT_AUDIT_EVENT__ON_CONVERSATION", columnList = "CONVERSATION_ID"),
        @Index(name = "IDX_AI_AGENT_AUDIT_EVENT__ON_STARTED_AT", columnList = "STARTED_AT"),
        @Index(name = "IDX_AI_AGENT_AUDIT_EVENT__ON_RUN_ID", columnList = "RUN_ID")
})
public class AiAuditEvent {

    @Id @Column(name = "ID", nullable = false) @JmixGeneratedValue
    private UUID id;

    @Version @Column(name = "VERSION", nullable = false)
    private Integer version;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "PARENT_ID")
    private AiAuditEvent parent;

    @Composition
    @OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<AiAuditEvent> children;

    @NotNull @Column(name = "KIND", nullable = false, length = 16)
    private String kind;                        // CHAT / TOOL / RETRIEVAL (open-ended)

    @Column(name = "EVENT_NAME", length = 128)  // nullable — CHAT root has no event name
    private String eventName;

    // ... other columns: conversation FK, userUsername, runId,
    //     argumentsJson/resultSummary (TOOL), query/topK/hitCount/topScore/filtersJson (RETRIEVAL),
    //     promptHash (CHAT), outcome (nullable until CHAT finish),
    //     denialReason, errorClass, latencyMs, startedAt, finishedAt

    @InstanceName
    @DependsOnProperties({"kind", "eventName", "outcome"})
    public String getDisplayName() {
        String name = eventName == null ? "-" : eventName;
        String oc = outcome == null ? "..." : outcome;
        return kind + " / " + name + " / " + oc;
    }
}
```

Key points:
- `@Composition` goes on the CHILDREN side only (same as `AiConversation.messages`).
- `@OnDelete(DeletePolicy.CASCADE)` optional — not used on self-ref in this phase since roots are never deleted via UI in v1; revisit only if a "delete audit row" action lands.
- Fetch plan for list view: `_base` + explicit `children` include one level deep. Do not include grand-children — all current kinds are leaf under CHAT.

### Pattern 2: Mutable Root Row — UPDATE Path in Its Own `REQUIRES_NEW` Tx

**What:** `writeChatFinish(UUID rootId, long latencyMs, String outcome, String errorClass)` runs in `@Transactional(propagation = REQUIRES_NEW)`, loads the root row freshly, mutates only scalar fields, and saves without touching the `children` collection.

**Why this specific shape:** If `writeChatFinish` loaded the root WITH a populated `children` list and then called `DataManager.save(root)`, Jmix `@Composition` + `cascade = CascadeType.ALL` + `orphanRemoval = true` would trigger a re-save of every child and (worse) orphan-remove any child that was null-loaded. Loading with a fetch plan that omits `children` prevents the cascade from touching them.

**Example:**

```java
// Source: synthesized — follows existing AuditWriter.java REQUIRES_NEW pattern,
//         applied to the UPDATE case with a no-children fetch plan.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeChatFinish(UUID rootId, long latencyMs, String outcome, String errorClass) {
    AiAuditEvent root = dataManager.load(AiAuditEvent.class)
            .id(rootId)
            .fetchPlan(fp -> fp.addProperty("kind")
                    .addProperty("outcome")
                    .addProperty("latencyMs")
                    .addProperty("finishedAt")
                    .addProperty("errorClass")
                    .addProperty("startedAt"))  // do NOT include "children"
            .optional()
            .orElse(null);
    if (root == null) {
        log.warn("writeChatFinish: root {} not found; lost", rootId);
        return;
    }
    root.setFinishedAt(OffsetDateTime.now());
    root.setLatencyMs(latencyMs);
    root.setOutcome(outcome);
    root.setErrorClass(errorClass);
    dataManager.save(root);

    // D-05 fan-out: CHAT becomes durable only on finish.
    registerAfterCommit(rootId, AuditKind.CHAT);
}

private void registerAfterCommit(UUID auditId, String kind) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() {
                dispatcher.dispatchEventAudited(auditId, kind);
            }
        });
    } else {
        dispatcher.dispatchEventAudited(auditId, kind);
    }
}
```

### Pattern 3: Retrieval Audit via `DocumentRetriever` Wrapper

**What:** Wrap the `VectorStoreDocumentRetriever` produced by `RetrievalAugmentationAdvisorFactory` with an `AuditingDocumentRetriever` that calls the delegate and then writes an audit row on the way out.

**Why a wrapper (not a custom advisor):** The Spring AI RAG advisor builder accepts `.documentRetriever(DocumentRetriever)`. Substituting a decorator is the least-invasive hook: no fork of `RetrievalAugmentationAdvisor`, no advisor-ordering rework. [ASSUMED: `DocumentRetriever` is a single-method functional interface with `List<Document> retrieve(Query query)` in M4 — verify via IDE / `javap`.]

**Example:**

```java
// Source: new file; shape inferred from DocumentRetriever SPI usage in RetrievalAugmentationAdvisorFactory.java
public class AuditingDocumentRetriever implements DocumentRetriever {
    private final DocumentRetriever delegate;
    private final AuditWriter auditWriter;
    // ... + CurrentAuthentication for user, etc.

    @Override
    public List<Document> retrieve(Query query) {
        UUID parentId = RunContext.getRootAuditId();   // may be null outside chat flow
        long start = System.nanoTime();
        List<Document> docs = null;
        String outcome = "SUCCESS";
        String errorClass = null;
        try {
            docs = delegate.retrieve(query);
            return docs;
        } catch (Throwable t) {
            outcome = "ERROR";
            errorClass = t.getClass().getName();
            throw t;
        } finally {
            long latencyMs = (System.nanoTime() - start) / 1_000_000L;
            try {
                String filtersJson = RunContext.getRetrievalFiltersJson();   // NEW helper
                Integer topK = RunContext.getRetrievalTopK();                // NEW helper
                Double topScore = (docs == null || docs.isEmpty()) ? null
                        : docs.get(0).getScore();       // [ASSUMED: Document.getScore() exists in M4]
                auditWriter.writeRetrieval(parentId,
                        query.text(),                    // [ASSUMED: Query record exposes text()]
                        topK,
                        docs == null ? 0 : docs.size(),
                        topScore,
                        filtersJson,
                        latencyMs,
                        outcome,
                        errorClass);
            } catch (Throwable t2) {
                log.warn("Retrieval audit write failed for parentId={}", parentId, t2);
            }
        }
    }
}
```

**Caveat:** `topK` and `FILTER_EXPRESSION` are supplied as advisor params by `DefaultChatServiceImpl.java:218`, not via `Query`. Two options for the planner:
1. Read them from the advisor context via a `RequestContext` — likely not reachable from inside `DocumentRetriever.retrieve` since that SPI runs below the advisor layer.
2. Capture them via a ThreadLocal set by the service layer on entry — mirrors `RunContext` exactly. **Recommended.**

See §Open Questions for resolution.

### Anti-Patterns to Avoid

- **Loading root WITH children collection before UPDATE.** `@Composition` cascade will re-save them or orphan-remove them. Always load with a fetch plan that omits `children` in `writeChatFinish`.
- **Self-invocation of `AuditWriter.writeXxx` from another `AuditWriter` method.** Bypasses the Spring proxy; `REQUIRES_NEW` silently collapses (Pitfall #3 from Phase 4 carry-over).
- **Writing retrieval audit inside the retrieval's own transaction.** Must go through `AuditWriter` (REQUIRES_NEW) so retrieval failures do not erase the row.
- **Rendering tree client-side (grouping in the DataGrid).** Violates Jmix-first rule and duplicates what `@Composition` + hierarchical loader already deliver.
- **Making `AuditKind` an enum.** CONTEXT.md D-03 says `String` constants so the column stays open-ended for host-defined kinds. Match the Liquibase `varchar(16)` column width.

## Common Pitfalls

### Pitfall 1: `@Composition` cascade re-saves children on root UPDATE

**What goes wrong:** `writeChatFinish` loads root, sets `finishedAt`, calls `DataManager.save(root)` — if `children` collection was populated by the load, cascade re-saves every child. Worse: if the children list was loaded as empty (e.g., lazy-loaded default), `orphanRemoval = true` may delete the child rows that were legitimately written by tool/retrieval decorators in separate `REQUIRES_NEW` txns.

**Why it happens:** `@Composition` + `cascade = CascadeType.ALL` + `orphanRemoval = true` is the standard Jmix parent-owns-children contract. It assumes all children pass through the parent's lifecycle. Mutable-root UPDATE violates that assumption.

**How to avoid:** Load the root inside `writeChatFinish` with a fetch plan that DOES NOT include `children`. When the collection is never navigated, EclipseLink does not mark it dirty and cascade skips it. See Pattern 2 code snippet. The tree-traversal read path (UI and tests) uses a DIFFERENT fetch plan that does include children.

**Warning signs:** Durability test (`AuditDurabilityTest`) fails with "N children expected, 0 found" after a chat turn completes. Direct SQL query shows child rows present before `writeChatFinish` runs and absent after.

### Pitfall 2: `RunContext.rootAuditId` cleared too early

**What goes wrong:** `AuditAdvisor` clears `RunContext` in `finally` — but `afterCommit` synchronizations and the retrieval hook run INSIDE the advisor's try block (retrieval) OR on a separate thread pool (if afterCommit is ever migrated async). Clearing rootAuditId before retrieval / tool audit writes their rows would make them orphans (`parentId = null`).

**How to avoid:** Keep `RunContext.clear()` in the advisor's `finally` block. Both retrieval and tool hooks run synchronously within the advisor chain, so they see the correct `rootAuditId`. `afterCommit` fan-out reads only the `auditId` — not `RunContext` — so the timing is safe.

**Warning signs:** Tree-traversal test sees children with `parent = null`.

### Pitfall 3: Retrieval hook can't reach `topK` / `filterExpression`

**What goes wrong:** The `DocumentRetriever.retrieve(Query)` SPI receives a `Query` that in M4 [ASSUMED] does NOT expose the advisor params (`FILTER_EXPRESSION`, `topK`). Those are wired into the retriever at construction time OR set as advisor params read by the advisor itself. The wrapper can see the docs returned, but not the parameters that shaped the retrieval.

**How to avoid:** Mirror `RunContext` with a `RetrievalParamContext` (ThreadLocal set by the service layer before `.call()`). The simpler path: stash the `ragFilter` toString() and `topK` that are ALREADY computed in `DefaultChatServiceImpl.java:192-207` onto the same `RunContext` as two new fields (`retrievalFiltersJson`, `retrievalTopK`). **This is the simpler path and the recommendation.**

**Warning signs:** Retrieval audit rows have `filtersJson = null` and `topK = null` in integration tests.

### Pitfall 4: Liquibase retire pattern leaves stale checksums

**What goes wrong:** `030-ai-tool-call-audit.xml` and `080-ai-tool-call-audit-runid.xml` stay in the `includeAll` tree. On a fresh DEV_CHANGELOG they execute normally (create old table, add columns). Then `090` runs `<dropTable>` + `<createTable>` so the final DB state is correct. On an already-initialised DB, `030`/`080` are skipped (DEV_CHANGELOG records them as executed), `090` runs, old table dropped, new table created — correct final state.

**How to avoid:** Do NOTHING to `030` / `080`. Do NOT edit them (that would change their checksums and fail on already-initialised DBs). Do NOT delete them (that would break fresh boots where `090` assumes the old table exists for the drop to succeed — actually `DROP TABLE IF EXISTS` sidesteps this on both Postgres and HSQLDB). Prefer unconditional `<dropTable>` with a `<preConditions onFail="MARK_RAN">` that checks for existence — portable on both DBs.
