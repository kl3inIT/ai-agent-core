## Pitfall #1 Sabotage Verification

Sabotaged the `writeChatFinish` fetch plan by adding `.add("children")` to intentionally
include children in the root UPDATE path, then ran
`AuditDurabilityTest.writeChatFinish_doesNotOrphanChildren_writtenInSeparateRequiresNew`.

**Result:** Test passed GREEN under sabotage as well as under correct code.

**Limitation acknowledged:** The regression guard catches the post-INSERT scenario (root loaded
with a child already committed, then re-saved) but is insufficient for the harder race
(concurrent INSERT between `load` and `save` on the root UPDATE). EclipseLink with
`orphanRemoval=true` preserves children already present in the loaded collection because the
orphan-removal pass is a DELETE-WHERE-NOT-IN over the hydrated list. The pure Pitfall #1
scenario — child INSERTed in a separate tx AFTER the parent is loaded but BEFORE it is
flushed — would require multi-threaded coordination that this integration test doesn't stage.

**Mitigation kept in production code:** the children-less fetch plan remains
the belt-and-suspenders defence (the collection is never hydrated, so
orphanRemoval's hydrated list cannot diverge from the DB state in the first place). Future
work: a dedicated concurrency stress test (not required for v1; documented as follow-up).

## Deviations from Plan

### Rule 3 — Test bootstrap blockers (not in plan scope but required for GREEN gate)

Plan 05 `files_modified` listed six files. Test-green required the following additional changes
because the `@Store(name="agentstore")` migration (Phase 2 / earlier) had never been fully
reflected in the test configuration, so EVERY `@SpringBootTest` had been silently failing
before this plan (previous waves of 7.2 only built `:compileJava`, not `:test`):

1. **[Rule 3 - Blocker] test-app.properties** — added `jmix.core.additional-stores=agentstore`,
   agentstore HSQL datasource (in-memory, random name per test run), corrected
   `main.liquibase.change-log` (stale path pointing at the renamed-away `changelog.xml`), and
   aligned `agentstore.liquibase.change-log` at `agentstore-changelog.xml`. Also added Spring AI
   JDBC chat-memory `initialize-schema=embedded` + explicit `schema-hsqldb.sql` path.

2. **[Rule 3 - Blocker] 060-ai-chat-memory.xml** — the postgres-only changeSet left HSQL runs
   without a `SPRING_AI_CHAT_MEMORY` table, so every test that went through
   `ProjectingChatMemoryRepository` (and therefore its delegate `JdbcChatMemoryRepository`)
   crashed with `BadSqlGrammarException`. Added an HSQL variant (ported from
   `spring-ai-model-chat-memory-repository-jdbc/.../schema-hsqldb.sql`) alongside the postgres
   changeSet. Production path untouched (`dbms="postgresql"`).

3. **[Rule 3 - Blocker] ai-agent.gradle** — bumped `test.maxHeapSize = '2g'`. PgVectorStore
   bean build under HSQL test context triggered `OutOfMemoryError` at 512 MB default.

4. **[Rule 3 - Blocker] Peripheral-test constructor/descriptor fan-out:**
   - `AskTypedRetryTest` + `ChatServiceFilterParamContractTest` — Plan 03 added
     `AiAgentRagProperties` to `DefaultChatServiceImpl` constructor (7th arg).
   - `RetrievalAugmentationAdvisorFactoryTest` — Plan 03 added `AuditWriter` +
     `CurrentAuthentication` to the factory method.
   - `AsyncIngestionWorkerTest` — Plan 05 (parent phase) added `SystemAuthenticator` to worker.
   - `GuardedToolCallingManagerTest` — `writeToolCall` signature changed (parentId-first, no
     phase literal).
   - `OrchestrationIntegrationTest` — `AiToolCallAudit` entity removed; test rewritten for
     `AiAuditEvent` (two asks = 2 CHAT root rows, not PRE+POST pairs).
   - `AdminViewAccessTest` — view ID `AiAgent_ToolCallAudit.list` → `AiAgent_AiAuditEvent.list`
     per Plan 04 rename.
   - `ToolCallAuditListViewTest` — descriptor path and column keys per Plan 04 rename.

5. **[Rule 3 - Blocker] StubVectorStoreConfiguration import** — added to the five audit /
   retrieval `@SpringBootTest` classes so `PgVectorStore` bean instantiation doesn't run
   against HSQL (stub `SimpleVectorStore` wins `@Primary`, but PgVectorStore bean creation
   still attempted and was consuming heap).
