## Summary

Phase 7.1 is a targeted refactor with a locked spec: swap the custom bubble/tool-card/markdown-renderer stack for Vaadin's stock `com.vaadin.flow.component.messages.MessageList` + `MessageInput`, modeled on `jmix-ai-backend/view/chat/ChatView.java`. All behavioral guarantees (streaming, Stop+CancellationRegistry+audit, conversation-id param, New-chat confirm, i18n, citation deep-links to KB) must carry forward unchanged.

The Vaadin API surface matches the reference's assumptions — `MessageList.setMarkdown(true)`, `MessageListItem.appendText(String)` for streaming accumulation, `setUserColorIndex(int)`, `setUserName(String)`, `setTime(Instant)`, `MessageInput.addSubmitListener(SubmitEvent→String getValue)` all exist in current flow-server and behave as the reference uses them [VERIFIED: vaadin.com/docs message-list + message-input pages, fetched 2026-04-21].

**Primary recommendation:** Follow the reference `renderStreamEvent(StreamingEvent) → String` pattern exactly, but pull labels through `MessageSource` (D-09) and delete only what is safe to delete. **Critical contradiction found with CONTEXT.md:** `MessageBubbleComponent` and `MarkdownRenderer` are still used by `ConversationDetailView` (Phase 7 replay view, explicitly out of scope per CONTEXT `Deferred Ideas`). **They CANNOT be deleted in this phase** without breaking UI-03. Flexmark stays until those are removed. See §Files-to-Delete Confirmation for the corrected deletion set.

### Pattern 1: `renderStreamEvent` as pure function with injected i18n

```java
// Source: adapted from jmix-ai-backend/view/chat/ChatView.java with D-09 MessageSource pull
// Signature — planner's discretion. Preferred:
static String renderStreamEvent(StreamingEvent event,
                                Map<String, String> labels,   // pre-resolved from MessageSource
                                CitationBuffer buffer) {
    String ts = formatTimestamp(Instant.now());
    return switch (event) {
        case StreamingEvent.Content c -> c.markdownChunk() == null ? "" : c.markdownChunk();
        case StreamingEvent.ToolCall tc ->
            "\n\n%s **%s**: %s".formatted(ts, tc.toolName(), shortArgs(tc.argsJson()));
        case StreamingEvent.ToolResult tr ->
            "  \n%s _%s %s %s_\n\n---\n".formatted(
                ts, tr.outcome(), labels.get("doneIn"), "—"); // duration not in our DTO
        case StreamingEvent.Citation c -> {
            String prefix = buffer.firstOfTurn()
                ? "\n\n---\n**%s**".formatted(labels.get("sources"))
                : "";
            String name = c.documentId() != null ? c.documentId().toString() : "source";
            yield prefix + "\n- [%s](/ai-agent/knowledge?documentId=%s)"
                .formatted(name, c.documentId());
        }
        case StreamingEvent.Error err  -> "\n\n---\n**error:** " + labels.get(err.messageKey());
        case StreamingEvent.Final f    -> ""; // stream terminator; finish on doOnComplete
    };
}
```

Pure function (no Vaadin deps) — unit-testable from a plain JUnit test, which D-08 explicitly asks for.

### Pattern 2: Streaming subscription (reference-aligned, Phase 7 audit contract preserved)

```java
// Source: reference ChatView.onSubmit + Phase 7 D-03 CancellationRegistry
Flux<StreamingEvent> source = chatService.stream(userId, conversationId, text, overrides);
activeStream = source
    .doOnNext(event -> ui.access(() -> {
        String md = renderStreamEvent(event, labels, citationBuffer);
        if (!md.isEmpty()) {
            botMsg.appendText(md);
            scrollToBottom();
        }
    }))
    .doOnError(e -> ui.access(() -> { notifyError(e); finish(); }))
    .doOnComplete(() -> ui.access(this::finish))
    .subscribe();
```

**Why not the reference's `.map(...).doOnNext(md -> ...)` chain:** our `StreamingEvent.Citation` needs stateful "first-of-turn?" tracking for the `**Sources:**` header — easier with `doOnNext` per event than mapping to a String first. Either works; planner picks.

### Pattern 3: Stop via CancellationRegistry (D-04, not bare dispose)

```java
// Source: Phase 7 D-03 contract
@Subscribe("stopButton")
public void onStopClick(ClickEvent<Button> ev) {
    UUID runId = currentRunId;  // captured from StreamingEvent.Final or from subscribe-time
    if (runId != null) {
        cancellationRegistry.cancel(runId);   // disposes + audits CANCELLED
    }
    // do NOT call activeStream.dispose() directly — that would bypass audit
}
```

Registry's `cancel(UUID)` disposes the stored `Disposable` **and** writes the audit row via the decorator chain. Reference's bare `disposeActiveStream()` skips audit — acceptable in reference, unacceptable here.

### Anti-Patterns to Avoid

- **Calling `activeStream.dispose()` directly on Stop click** — breaks audit contract (D-04).
- **Hardcoding English labels in `renderStreamEvent`** — reference does this; D-09 explicitly forbids it here.
- **Re-introducing `bufferTimeout`** — D-03 says per-event. If UAT surfaces thrashing, capture as deferred, don't add it back silently.
- **Deleting `MessageBubbleComponent` / `MarkdownRenderer` / flexmark in this phase** — `ConversationDetailView` still depends on them. Deletion requires its own follow-up phase.

## Common Pitfalls

### Pitfall 1: Deleting `MarkdownRenderer` / `MessageBubbleComponent` breaks `ConversationDetailView`
**What goes wrong:** Compilation error in `view/conversation/ConversationDetailView.java` (imports at lines 12–13, usages at 61, 100–110).
**Why it happens:** CONTEXT.md §Deferred Ideas explicitly says "ConversationDetailView keeps its current bubble-based replay" — but §Files to delete lists `MarkdownRenderer` and `MessageBubbleComponent` as deletions, contradiction.
**How to avoid:** Preserve `MarkdownRenderer.java` and `MessageBubbleComponent.java` in Phase 7.1. Keep flexmark dependency. Delete only `ToolCallCardComponent`, `CitationDialog`, `citation-dialog.xml`. Plan a follow-up phase to migrate `ConversationDetailView` to MessageList and complete the cleanup.
**Warning signs:** Planner writes a deletion task covering `MessageBubbleComponent.java` without also rewriting `ConversationDetailView`. Red-flag in plan-check.

### Pitfall 2: `MessageListItem.appendText` across multiple UI.access ticks
**What goes wrong:** Assumption that `appendText` just concatenates strings and skips re-rendering.
**Why it happens:** Reference's streaming works because the Vaadin client-side component efficiently reparses markdown on each append.
**How to avoid:** Nothing to do — it works. But: very fast providers may hit the client-side reparse cost. D-03 explicitly drops the bufferTimeout; capture re-introduction as deferred (already done in CONTEXT).
**Warning signs:** UAT shows janky scroll with fast providers.

### Pitfall 3: Stop click races with completing stream
**What goes wrong:** User clicks Stop right as `Final` event is about to arrive → `cancel(runId)` fires on an already-completed subscription → no-op → but audit row is `CANCELLED` for a run that actually completed.
**Why it happens:** Race between `doOnComplete` and button click.
**How to avoid:** `CancellationRegistry.cancel(runId)` should guard with `isDisposed()` before emitting the audit row — this is already the Phase 5/7 registry contract. Verify during planner's reading pass.
**Warning signs:** `AiToolCallAudit` row with `outcome=CANCELLED` but `endedAt > runStart + normalLatency`.

### Pitfall 4: `MessageInput` loses Shift+Enter when programmatically disabled mid-composition
**What goes wrong:** User typing multiline input, stream completes, input re-enables but cursor position / draft is lost if we `setEnabled(false)` mid-edit.
**Why it happens:** `setEnabled(false)` on an input element clears its pending state in some browser versions.
**How to avoid:** Only disable `MessageInput` *after* its own submit has fired. The reference does this correctly (disable in `onSubmit` handler).
**Warning signs:** User reports losing drafts.

### Pitfall 5: Setting `messageList.setItems(items)` after `appendText` resets accumulated markdown
**What goes wrong:** `setItems` replaces the list wholesale — if you call it after the bot item has been streamed into, the streamed content persists on the item object, but the MessageList server-side model is re-materialized.
**Why it happens:** `setItems` is a full sync.
**How to avoid:** Add new items, don't re-call `setItems` after subscription starts. The reference calls `setItems(items)` once when creating the user+bot pair, then only `appendText` on the bot item — that's the correct pattern.
**Warning signs:** Bot message reverts to blank mid-stream.
