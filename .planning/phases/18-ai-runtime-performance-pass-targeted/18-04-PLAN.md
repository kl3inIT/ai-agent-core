RESEARCH establish that `AiTaskFileMediaResolver.resolveActive(conversationId)` is ALREADY invoked once
per turn (`DefaultChatServiceImpl:350,617`, Phase 13.1), and within `resolveActive` each kept row reads
`FileStorage`/Tika exactly once already. Therefore PERF-04 is partly a re-encode GUARD, not necessarily
a new cache.

Build a call-count proxy over the per-file encode path (`FileStorage` read, Tika parse) and the
`AiUiSettingsResolver.resolveTaskFile*` singleton reads, and branch:
- If the proxy shows encode/settings already run at most once per `(conversationId, taskFileId)` per
  turn → ship the call-count REGRESSION ASSERTION that locks the good behavior; add NO new cache
  (Pitfall 5: a cache whose proxy never serves a second in-turn hit is redundant).
- If the proxy shows a SECOND in-turn encode for the same `(conversationId, taskFileId)` → memoize the
  encoded `Media` (and/or the settings singleton read) per `(conversationId, taskFileId)` for the turn in a
  SELF-CONTAINED resolver-level `ConcurrentHashMap` (NOT `RunContext.perTurnCache()`, which is a Wave-2
  Plan-02 artifact this Wave-1 plan must not depend on — review HIGH #5), evicted on attachment
  add/delete/TTL and on `AiSettingsChangedEvent(UI_SETTINGS)` (mirroring how the Plan 01 denylist evicts on
  `LlmExposureChangedEvent`). If the per-turn slot is genuinely preferred, re-sequence this plan's cache
  branch to Wave 2 with `depends_on: ["18-02"]`.

Keep `PerTurnMediaInjectionTest` + budget/TTL tests unchanged. Preserve the per-turn-all + LRU
budget-cap semantics and the constrained-`DataManager` row load (never `UnconstrainedDataManager`/raw
JPQL on the LLM-steerable data path).

Purpose: Guarantee no in-turn re-serialization of the same task file, the cheapest correct way —
regression-lock where already-optimal, cache only where a real second encode exists.

memo ONLY if the proxy proves it necessary.
