## 1. System Classification

**System Type:** Conversational assistant with tool use (agentic chat, single-turn blocking in Phase 4; RAG lands Phase 5; streaming deferred to Phase 7)

**Description:**
A Jmix add-on (`ai-agent-core`) that lets a host Jmix application expose an LLM-backed chat assistant to its end users. Phase 4 delivers the first end-to-end LLM path: a `ChatService.ask(userId, conversationId, message)` entry point that composes a Spring AI `ChatClient` with a verified advisor chain (Audit → Memory → Tool), persists conversations via a dual-layer scheme (Spring AI's `SPRING_AI_CHAT_MEMORY` + Jmix-owned `AiConversation`/`AiMessage` entities), enforces user-scoped conversation ownership at the service boundary, and captures a full audit pipeline (chat-level pre/post rows + per-tool-call rows under `REQUIRES_NEW` so audit survives tool rollbacks) with synchronous `AuditListener` SPI fan-out. "Good" means: the host injects `ChatService`, calls `.ask(...)`, and gets back a deterministic `ChatResponse` with every advisor having fired in the right order, the conversation replayable from Jmix-owned rows, and an audit trail that cannot be erased by tool failures.

**Critical Failure Modes:**
1. **Advisor-order drift** — `MessageChatMemoryAdvisor` fires before `AuditAdvisor` (inverted order), so audit captures only partial chain timing and cannot see pre-memory errors; or `ToolCallAdvisor` lands outside `MessageChatMemoryAdvisor`, so tool-call context leaks into the history the way Spring AI M4 explicitly warned against.
2. **Dual-layer persistence drift** — `AiMessage` rows silently desync from `SPRING_AI_CHAT_MEMORY` because projection ran in a separate transaction (violates D-07) or the decorator was bypassed on one code path; the Conversations replay view shows data that does not match what the model actually saw.
3. **Ownership bypass** — `ChatService.ask(userA, convId-owned-by-userB, ...)` either returns userB's data or returns a different exception than the "not found" message, allowing an attacker to probe conversation-id existence (violates success criterion #3).
4. **Audit loss under tool rollback** — `REQUIRES_NEW` is applied to the advisor method instead of the `AuditWriter` bean (violates D-11), so when an `@Tool` method rolls back, the tool-call audit row rolls back with it — audit is no longer the durable source of truth.
5. **Listener fan-out poisoning** — one throwing `AuditListener` bean blocks or breaks the chat request (missing per-listener try/catch), or listeners fire on uncommitted/rolled-back rows (missing `afterCommit` synchronization), violating the invariant that listeners only see persisted audit.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Horizontal — enterprise Java admin/operations applications built on Jmix 2.8. The add-on itself is vertical-agnostic; it is consumed by host apps across regulated and unregulated domains (sales ops, back-office admin, ERP-adjacent tooling, internal business portals). The Phase 4 "domain" is therefore **enterprise data-access chat with authorization, audit, and conversation fidelity as first-class concerns** — not a specific business vertical.

**User Population:**
- **End users of host Jmix apps** — authenticated business users (sales reps, operations staff, back-office admins, support analysts) who ask natural-language questions about data they already have permission to see through the standard Jmix UI.
- **Jmix integrators** (primary "domain experts") — developers at host organizations who drop the add-on into an existing Jmix app and must trust it to respect their role model without extra glue code.
- **Security/compliance reviewers** at host organizations — the gate keepers who must sign off that the chat surface does not widen the existing data-access footprint.

**Stakes Level:** **High.** The system reads live business data through a privileged service account (the Jmix application user) and returns it in natural language. A single ownership bypass or missed row-level-security hop leaks another user's conversation or records; a silent audit gap removes the forensic trail a host's compliance team depends on. Stakes are "High" rather than "Critical" only because Phase 4 ships read-only — no tool in this phase can mutate host data.

**Output Consequence:** Host end users act on the chat answer as if it came from the Jmix UI — they will make operational decisions (call a customer back, flag an order, escalate a ticket) on its basis. Host security/compliance reviewers pull the audit trail during incident response and GDPR-style data-subject requests; if the trail is incomplete or diverges from what the model actually saw, the incident review cannot be closed.

### What Domain Experts Evaluate Against

```
Dimension: Authorization parity with the host Jmix UI
Good: Every record the assistant surfaces would also have been visible to the same user through standard DataManager-backed views at the same moment. A user with no read policy on Customer receives no Customer data in chat — neither in tool results nor summarised in prose.
Bad: Chat returns a row, field, or summary the same user would have been denied in the Jmix UI. Includes the subtle case where the assistant paraphrases denied data ("based on the customer's credit limit...") without citing a row.
Stakes: Critical
Source: Jmix security model (AccessManager + row-level predicates + attribute policies); MEMORY note "AI is just another Jmix client"; OWASP LLM01 (Prompt Injection) and LLM06 (Sensitive Information Disclosure) guidance that LLM systems must inherit, not bypass, the caller's existing authorization.
```

```
Dimension: Conversation-id ownership opacity
Good: A request from user A for a conversationId owned by user B returns the exact same error (class, message, HTTP-equivalent status) as a request for a conversationId that does not exist. No timing, payload, or log-surface channel reveals which case it was.
Bad: User A gets "conversation not found" for a missing id and "access denied" (or a different exception type, status code, or latency signature) for user B's id — allowing an attacker to enumerate conversation ids.
Stakes: Critical
Source: CWE-204 (Observable Response Discrepancy) / CWE-209 (Information Exposure Through an Error Message); standard enterprise web-app practice; phase success criterion #3.
```

```
Dimension: Audit trail durability under partial failure
Good: For every `ChatService.ask()` invocation, both a pre-row and a post-row exist in `AiToolCallAudit`, and a per-tool-call row exists for every tool invocation — even when the tool method's own transaction rolled back, when the chat advisor chain threw, or when a downstream AuditListener threw. Audit is the source of truth that survives the thing being audited failing.
Bad: Any code path where a tool call that actually hit the LLM and executed leaves no audit row; any case where a throwing listener suppresses or corrupts the audit write; any case where uncommitted audit rows are visible to listeners.
Stakes: Critical
Source: SOX §404 internal-controls expectations for financial-system audit trails; GDPR Art. 30 record-of-processing obligations; ISO 27001 A.12.4 logging controls; Phase 4 success criterion #4.
```

```
Dimension: Replay fidelity (what the Jmix user sees == what the model saw)
Good: The `AiMessage` rows reachable via the Conversations replay view match, turn-for-turn and text-for-text, the message history that Spring AI's `SPRING_AI_CHAT_MEMORY` handed to the ChatClient on the next turn. No reordering, no dropped turns, no transcoded role labels.
Bad: The Jmix replay UI shows fewer (or different, or re-ordered) messages than the model actually processed. A reviewer answering "what did the model know when it said X?" gets a misleading answer.
Stakes: High
Source: Incident-response and regulated-domain review practice; GDPR Art. 22 right-to-explanation for automated decisions (host-configurable); Phase 4 D-05/D-06/D-07 dual-layer invariant.
```

```
Dimension: Integrator ergonomics — "trust on first drop-in"
Good: A Jmix developer adds the starter, sets `OPENROUTER_API_KEY`, restarts `bootRun`, injects `ChatService`, and the chat respects their existing `@ResourceRole` / row-level predicate configuration with no AI-specific policy code. The out-of-box defaults are safe; there is no "remember to also configure X or users can see everything" footgun.
Bad: Any configuration knob that, if forgotten, produces a silent widening of access — e.g. an audit listener that defaults to on-error-fail-open, a memory repository wired without the ownership pre-check, a tool that bypasses `DataManager`.
Stakes: High
Source: Jmix add-on ecosystem practice; "secure defaults" principle (NIST SP 800-160 Vol. 1, §3.3.5); repeated PROJECT.md / MEMORY emphasis on plug-and-play posture.
```

### Known Failure Modes in This Domain

1. **Tool-result leakage via paraphrase.** The six read tools (Phase 3) correctly return only authorized rows, but the LLM summarises across a history turn that included a previously-authorized-now-denied record (policy changed mid-conversation, user lost a role) and surfaces it in prose. The raw tool output was authorised; the paraphrase is not. Domain-specific because it is only visible when replay fidelity (above) is correct AND the host re-checks authorization per turn, not per conversation.
2. **Conversation-id probing via error-channel divergence.** Attackers do not need to read conversations to exploit them — being able to confirm "conversationId X exists" is a leak in multi-tenant / per-user-scoped chat. Historically this manifests as a different exception class, a 403 vs 404 divergence, a measurable latency difference (ownership check hits the DB; "not found" short-circuits), or a distinct stack-trace pattern in logs shared with third parties.
3. **Audit write coupled to tool transaction.** Developer places `@Transactional(REQUIRES_NEW)` on the advisor method (where `this.`-invocation bypasses Spring's proxy) instead of on the `AuditWriter` bean's methods — observed in production Spring Data + Spring AI deployments. Symptom: audit rows mysteriously disappear after tool rollbacks, only under load; unit tests that stub the advisor pass.
4. **Dual-memory drift after Spring AI minor upgrade.** Spring AI's `JdbcChatMemoryRepository` internal schema is not part of its public API; a 1.1.x → 1.2.x upgrade that reshapes its columns silently stops populating certain message types. The Jmix-owned `AiMessage` layer keeps working (decorator still writes), but the model sees a trimmed history. Failure is invisible until someone inspects a multi-turn conversation's raw context.
5. **Listener exception contagion (fan-out poisoning).** A host adds a Slack-notify `AuditListener` bean; Slack's webhook hiccups; without per-listener try/catch and `afterCommit` registration the throw propagates into the chat request thread, the user sees a 500, and (worse) the audit row that triggered the listener is rolled back. The add-on's own audit invariant is broken by a host-supplied listener.

### Regulatory / Compliance Context

The add-on is **domain-agnostic at the vertical level** (it ships across regulated and unregulated host apps) but the audit and ownership machinery is explicitly designed to help host apps meet **horizontal enterprise obligations** their existing Jmix app is already subject to:

- **GDPR (EU 2016/679).** Art. 5(1)(f) integrity/confidentiality — ownership enforcement prevents cross-subject conversation exposure. Art. 15 subject-access and Art. 17 erasure — the dual-layer `AiConversation`/`AiMessage` schema is queryable and deletable via DataManager, so a host can answer DSARs against chat content the same way they do for any other Jmix entity. Art. 30 records-of-processing — `AiToolCallAudit` is the evidence trail.
- **SOX §404 (host-dependent).** For hosts whose Jmix app is in scope of financial reporting, Phase 4's `REQUIRES_NEW` audit-writer contract and `afterCommit` listener semantics are the controls that make the chat surface auditable the same way the underlying Jmix entities are.
- **ISO 27001 Annex A.12.4 (logging) & A.9 (access control).** Audit-pre/post invariants + Jmix-native row-level enforcement align with A.12.4.1 (event logging) and A.9.4.1 (information access restriction) without the add-on introducing a parallel policy layer.
- **No vertical-specific regulations adopted in the add-on itself.** Phase 4 does NOT bake in HIPAA, PCI-DSS, FCA, FDA or similar — those are host-app concerns. The add-on's responsibility is to avoid undermining them: no content redaction pipeline, no PII detection, no jurisdiction-aware routing. Hosts that need those layer them on top via the SPI seams (`AuditListener`, `PromptContextContributor`, future `ToolGuard`).

The operational posture is "provide the audit and authorization primitives a regulated host needs; do not claim compliance on their behalf" — consistent with PROJECT.md's "honest security posture only" line in `Out of Scope`.

## 2. Framework Decision

**Selected Framework:** Spring AI (`spring-ai-starter-model-openai`) with OpenRouter `base-url` override

**Version:** 1.1.4 (pinned via `spring-ai-bom:1.1.4`; M4 API surface)

**Rationale:**
Phase 4 framework choice is a lock-in confirmation, not an open selection. Phases 1-3 already shipped on Spring AI 1.1.4: BOM pinned, `spring-ai-starter-model-openai` wired to OpenRouter, `BuiltInDataTools` as `@Tool`-annotated beans, `SPRING_AI_CHAT_MEMORY` Liquibase changelog with `initialize-schema: never`, stub `ChatClient` bean, stub `ChatService` with future-shaped signature. Every Phase 4 CONTEXT decision (D-01..D-16) is written against Spring AI primitives by name — `ChatClient`, `MessageChatMemoryAdvisor`, `JdbcChatMemoryRepository`, `ToolCallAdvisor`, `MethodToolCallback`, `OpenAiChatOptions`. Reopening the framework choice would invalidate three phases of committed work and violate the Jmix-native posture (Jmix 2.8 on Spring Boot 3).

Beyond the sunk-cost argument, Spring AI is the right fit on the merits: (1) Spring Boot auto-config ergonomics align with Jmix 2.8's `@AutoConfiguration` host model, (2) `ChatMemoryRepository` interface lets the add-on decorate `JdbcChatMemoryRepository` for dual-layer persistence (D-05) without patching framework internals, (3) advisor chain `Ordered` contract makes the Audit → Memory → Tool assembly verifiable by a test (success criterion #2), (4) `MethodToolCallback` gives a clean seam for per-tool-call audit wrapping without AOP, (5) `OpenAiChatOptions` per-request `.options(...)` support is what D-03 (per-`AiParameters`-profile options) depends on.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain4j 1.x | Only credible Java fallback. Would require rebuilding the advisor chain against `AiServices`/`ChatMemoryStore` abstractions (no direct advisor equivalent), re-deriving the JDBC memory + dual-layer projection without `ChatMemoryRepository` interface, and re-implementing `MethodToolCallback` audit wrapping against LangChain4j's tool-execution model. All sunk work from Phases 1-3 would re-land; no capability win. |
| Direct OpenAI SDK (Python microservice) | Polyglot boundary would force every Jmix security invariant (row-level predicate on `AiConversation.createdBy`, `AccessManager` roles, DataManager-only persistence) across an HTTP seam. Violates the "AI is just another Jmix client" posture locked in Phase 2. |
| Vertex AI SDK / AWS Bedrock SDK | Cloud-SDK lock-in incompatible with the OpenRouter model-provider-agnostic requirement. Swapping providers would require swapping the SDK, not just the `ChatModel` bean. |

**Vendor Lock-In Accepted:** Partial — locked to Spring AI's advisor/memory/tool abstractions (high switching cost, mitigated by Spring AI being Apache-2.0 and Pivotal/VMware-maintained); NOT locked to a model provider (OpenRouter `base-url` override + `OpenAiChatOptions.model` per-request selection keeps the `ChatModel` bean replaceable).

### Entry Point Pattern

Minimal blocking single-turn call showing the D-01 pattern (cached `ChatClient`, per-request `.tools(...)` and `.options(...)`):

```java
@Service
public class DefaultChatServiceImpl implements ChatService {

    private final ChatClient chatClient;                      // Cached at startup (D-01)
    private final ToolCallbackProvider builtInToolProvider;   // From Phase 3
    private final AiParametersResolver parametersResolver;    // Reads active profile (D-03/D-04)
    private final ConversationGateway conversationGateway;    // Ownership check + create (D-08/D-09)

    public DefaultChatServiceImpl(ChatClient chatClient,
                                  ToolCallbackProvider builtInToolProvider,
                                  AiParametersResolver parametersResolver,
                                  ConversationGateway conversationGateway) {
        this.chatClient = chatClient;
        this.builtInToolProvider = builtInToolProvider;
        this.parametersResolver = parametersResolver;
        this.conversationGateway = conversationGateway;
    }

    @Override
    public ChatResponseDto ask(UUID userId, UUID conversationId, String message) {
        // 1. Enforce ownership (D-09) — same exception for "missing" and "not yours"
        conversationGateway.loadOrCreate(userId, conversationId, message);

        // 2. Resolve per-request options from active AiParameters (D-03)
        AiParameters params = parametersResolver.resolveActive();
        OpenAiChatOptions options = OpenAiChatOptions.builder()
                .model(params.getModel())                     // OpenRouter slug e.g. "openai/gpt-4o-mini"
                .temperature(params.getTemperature())
                .topP(params.getTopP())
                .build();

        // 3. Invoke the cached ChatClient with per-request tools + options.
        //    CONVERSATION_ID param ties this call to SPRING_AI_CHAT_MEMORY history.
        ChatClientResponse response = chatClient.prompt()
                .system(params.getSystemPrompt())
                .user(message)
                .tools(builtInToolProvider)                   // Per-request (D-10 Phase 3)
                .options(options)
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId.toString()))
                .call()
                .chatClientResponse();

        return ChatResponseDto.from(response);
    }
}
```

The `ChatClient` bean itself (assembled once in `AIAutoConfiguration`):

```java
@Bean
ChatClient chatClient(ChatClient.Builder builder,
                      ChatMemory chatMemory,
                      ToolCallingManager toolCallingManager,
                      AuditAdvisor auditAdvisor) {

    // Memory advisor: inject history BEFORE tool calls see it
    CallAdvisor memoryAdvisor = MessageChatMemoryAdvisor.builder(chatMemory)
            .advisorOrder(BaseAdvisor.HIGHEST_PRECEDENCE + 200)
            .build();

    // Tool-call advisor: innermost; disable its internal history
    // so MessageChatMemoryAdvisor remains the sole source of truth.
    CallAdvisor toolAdvisor = ToolCallAdvisor.builder()
            .toolCallingManager(toolCallingManager)
            .disableMemory()                                   // D-02 — prevent double-history
            .advisorOrder(BaseAdvisor.HIGHEST_PRECEDENCE + 300)
            .build();

    // AuditAdvisor wraps everything: HIGHEST_PRECEDENCE so it sees true latency
    // and all errors. Writes via REQUIRES_NEW AuditWriter bean (D-11).
    return builder
            .defaultAdvisors(auditAdvisor, memoryAdvisor, toolAdvisor)
            .build();
}

@Bean
ChatMemory chatMemory(JdbcChatMemoryRepository repository) {
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(repository)
            .maxMessages(20)
            .build();
}
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `ChatClient` | Fluent builder facade wrapping `ChatModel` + advisors + default options. Built once via `ChatClient.Builder`. | Assembled in `AIAutoConfiguration` with `defaultAdvisors(...)`; consumed by `ChatService.ask()` via `.prompt()...call()`. |
| `CallAdvisor` (M4) | Interface replacing 1.0's `CallAroundAdvisor`. `adviseCall(ChatClientRequest, CallAdvisorChain)` is the hook point; ordering via `BaseAdvisor.HIGHEST_PRECEDENCE + offset`. | Implement for `AuditAdvisor`; use built-in `MessageChatMemoryAdvisor` and `ToolCallAdvisor`. |
| `MessageChatMemoryAdvisor` | Reads/writes messages from a `ChatMemory` keyed by `ChatMemory.CONVERSATION_ID` param. Order set via `.advisorOrder(...)` on the builder. | Second advisor in the chain (D-02); keyed by our `conversationId`. |
| `JdbcChatMemoryRepository` | Spring AI's JDBC-backed `ChatMemoryRepository` implementation for `SPRING_AI_CHAT_MEMORY`. Auto-configured by `spring-ai-starter-model-chat-memory-repository-jdbc`. | We DECORATE it with `ProjectingChatMemoryRepository` (D-05) to write `AiMessage` in the same tx. |
| `ToolCallAdvisor` | M4 advisor that routes tool calls through a `ToolCallingManager`. `.disableMemory()` opts out of its internal conversation-history management so `MessageChatMemoryAdvisor` stays the single source of truth. | Innermost advisor (D-02); MUST have `.disableMemory()` given our memory advisor is present. |
| `MethodToolCallback` | Wraps a reflected `Method` + target object as a `ToolCallback`. Built via `MethodToolCallback.builder().toolDefinition(...).toolMethod(...).toolObject(...)`. | Wrap each `@Tool` method from `BuiltInDataTools` so per-tool-call audit (D-10/D-11) can fire around the invocation. |
| `OpenAiChatOptions` | Per-request options (model, temperature, topP, maxTokens, tool config). Built with `.builder().model(...).temperature(...).build()`. | Constructed per request from active `AiParameters`; passed via `.options(...)` on `.prompt()`. |
| `ToolCallingManager` | Auto-configured bean that executes tool callbacks and handles multi-step tool-call loops. Config knobs (iteration cap) land in Phase 6. | Injected into `ToolCallAdvisor.builder()`; do not instantiate directly. |

### Common Pitfalls

1. **`ToolCallAdvisor` double-history when `MessageChatMemoryAdvisor` is present.** The tool advisor's default `conversationHistoryEnabled=true` maintains its own history for the tool-call loop. If both are enabled, the assistant sees each turn twice and tool context leaks into long-term memory. Fix: always call `.disableMemory()` on the `ToolCallAdvisor` builder when a `MessageChatMemoryAdvisor` is in the chain (this is D-02 and the reason the ROADMAP Phase 4 deliverable calls it out explicitly).
2. **`.defaultTools(...)` cements tools into the cached `ChatClient`.** Per D-10 Phase 3, per-user effective schema means the tool set must be assembled **per request**. Using `.defaultTools(...)` on the builder locks a single tool set into the cached client; D-09 Phase 3's `ToolCallbackProvider` must be passed via per-request `.tools(...)` only. The planner MUST NOT reintroduce `.defaultTools(...)` at Phase 4.
3. **`spring.ai.chat.memory.repository.jdbc.initialize-schema` defaults to `embedded`.** Without explicit `initialize-schema: never`, Spring AI auto-creates the `SPRING_AI_CHAT_MEMORY` table on HSQLDB/H2 tests, racing with our Liquibase changeset and sometimes producing column drift. Phase 2 D-05 set this to `never`; any override in a test profile must keep it that way.
4. **`MessageChatMemoryAdvisor` requires `CONVERSATION_ID` as an advisor param, not as a top-level argument.** Passing the id via `.user(...)` or as a system-message placeholder silently uses a default/no-op conversation id and history appears empty on the second turn. Correct idiom: `.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId.toString()))` on every `.prompt()` call.
5. **Advisor `getOrder()` confusion — lower = outermost.** Spring's `Ordered` contract: lower order runs first on the request phase and last on the response phase (i.e., outermost). `AuditAdvisor` must therefore be the LOWEST numeric order (`HIGHEST_PRECEDENCE` = `Integer.MIN_VALUE`), Memory next (`HIGHEST_PRECEDENCE + 200`), Tool innermost (`HIGHEST_PRECEDENCE + 300`). Getting this inverted is the single most common source of "why is my audit missing the outer latency?" bug reports.
6. **`OpenAiChatOptions.model` is an OpenRouter model slug, not an OpenAI model id.** OpenRouter uses slugs like `openai/gpt-4o-mini`, `anthropic/claude-3.5-sonnet`, `google/gemini-1.5-pro`. Using bare `gpt-4o-mini` sends the request but OpenRouter returns a 400 `model not found`. Validate format in `AiParametersResolver` (contains a slash).
7. **Calling `chatClient.prompt(userMessage)` instead of `.prompt().user(userMessage)` skips `.system(...)` / `.advisors(...)` / `.tools(...)` on the same fluent chain.** The single-arg overload is a shortcut for bare prompts; it cannot be composed with the other builders. Always use `.prompt().system(...).user(...).tools(...).options(...).advisors(...).call()`.

## 4. Implementation Guidance

**Model Configuration:**

Model is resolved **per request** from the active `AiParameters` row (D-03). No model is hard-coded in Java. Defaults live in `application.yml` under `jmix.ai-agent.defaults.*` and are used only if no active `AiParameters` profile exists (D-04 fallback).

Recommended defaults for Phase 4 MVP:

| Parameter | Default | Rationale |
|-----------|---------|-----------|
| `model` | `openai/gpt-4o-mini` (OpenRouter slug) | Cheap, fast, supports tools + large context. |
| `temperature` | `0.2` | Deterministic output for tool-use + audit reproducibility. |
| `topP` | `1.0` | Leave to temperature; don't combine truncation knobs. |
| `maxTokens` | set explicitly per profile (`800`–`2000`) | NEVER unbounded in production (see 4b.3). |
| `systemPrompt` | From `AiParameters.systemPrompt`, prepended with baseline context (D-15). | Profile-owned; composed by `BaselineContextProvider`. |

All assembled per request via `OpenAiChatOptions.builder()` and handed to `.options(...)`. Because `OpenAiChatOptions` is only consulted at call time, swapping profiles requires no `ChatClient` rebuild.

**Core Pattern:**

The orchestration-core pattern is a cached `ChatClient` with **immutable advisor chain** plus **per-request variability** (tools, options, conversation id). Concretely:

```java
// One-time assembly at startup (AIAutoConfiguration)
ChatClient chatClient = ChatClient.builder(chatModel)
        .defaultAdvisors(
                auditAdvisor,                                 // outermost (HIGHEST_PRECEDENCE)
                MessageChatMemoryAdvisor.builder(chatMemory)
                        .advisorOrder(BaseAdvisor.HIGHEST_PRECEDENCE + 200)
                        .build(),
                ToolCallAdvisor.builder()
                        .toolCallingManager(toolCallingManager)
                        .disableMemory()                      // single source of truth for history
                        .advisorOrder(BaseAdvisor.HIGHEST_PRECEDENCE + 300)
                        .build())
        .build();

// Per-request in ChatService.ask()
ChatClientResponse response = chatClient.prompt()
        .system(systemPromptFromProfile)                      // D-03
        .user(message)
        .tools(builtInToolProvider)                           // D-10 Phase 3: per-request only
        .options(optionsFromProfile)                          // D-03: per-request options
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, convId.toString()))
        .call()
        .chatClientResponse();
```

The `AuditAdvisor` skeleton (implementing M4 `CallAdvisor`):

```java
public class AuditAdvisor implements CallAdvisor {

    private final AuditWriter auditWriter;   // REQUIRES_NEW methods (D-11)

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE;    // outermost in the chain
    }

    @Override
    public String getName() {
        return "AuditAdvisor";
    }

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest req, CallAdvisorChain chain) {
        UUID runId = UUID.randomUUID();
        RunContext.set(runId);
        auditWriter.writeChatPre(runId, currentUser(), conversationIdFrom(req), hash(req));
        long t0 = System.nanoTime();
        try {
            ChatClientResponse resp = chain.nextCall(req);
            auditWriter.writeChatPost(runId, AiToolCallOutcome.SUCCESS,
                    elapsedMs(t0), null);
            return resp;
        } catch (Throwable t) {
            auditWriter.writeChatPost(runId, AiToolCallOutcome.FAILED,
                    elapsedMs(t0), t.getClass().getSimpleName());
            throw t;
        } finally {
            RunContext.clear();
        }
    }
}
```

**Tool Use:**

Tools come from the Phase 3 `BuiltInDataTools` `@Component`, exposed as a `ToolCallbackProvider`. Phase 4 wraps each `MethodToolCallback` from that provider in a `ToolCallbackAuditDecorator` that writes per-tool-call audit rows via `AuditWriter.writeToolCall(...)` (REQUIRES_NEW) before and after invoking the delegate.

Wire-up sketch (D-10 Phase 3 compliant — per-request, never `.defaultTools(...)`):

```java
@Component
public class AuditingToolCallbackProvider implements ToolCallbackProvider {

    private final ToolCallbackProvider delegate;  // BuiltInDataTools provider
    private final AuditWriter auditWriter;

    @Override
    public ToolCallback[] getToolCallbacks() {
        ToolCallback[] raw = delegate.getToolCallbacks();
        ToolCallback[] wrapped = new ToolCallback[raw.length];
        for (int i = 0; i < raw.length; i++) {
            wrapped[i] = new ToolCallbackAuditDecorator(raw[i], auditWriter);
        }
        return wrapped;
    }
}
```

`.disableMemory()` on the `ToolCallAdvisor` is load-bearing: without it, the tool-call loop maintains its own history and the outer `MessageChatMemoryAdvisor` records duplicate/drifted messages.

**State Management:**

Dual-layer per D-05/D-06/D-07:

- **Layer 1 — Spring AI `SPRING_AI_CHAT_MEMORY`** (driven by `JdbcChatMemoryRepository`): the model's context-window source. Framework-owned schema, treated as opaque.
- **Layer 2 — Jmix `AiConversation` + `AiMessage` entities**: host-visible, queryable, row-level-security-protected record of what the model actually saw.

Both writes happen in the **same transaction** via a `ProjectingChatMemoryRepository` decorator:

```java
public class ProjectingChatMemoryRepository implements ChatMemoryRepository {
    private final JdbcChatMemoryRepository delegate;
    private final DataManager dataManager;
    private final Metadata metadata;

    @Override
    @Transactional(propagation = Propagation.REQUIRED)    // D-07: same tx
    public void saveAll(String conversationId, List<Message> messages) {
        delegate.saveAll(conversationId, messages);       // Layer 1
        for (Message m : messages) {                      // Layer 2
            AiMessage jmixMessage = metadata.create(AiMessage.class);
            jmixMessage.setConversationId(UUID.fromString(conversationId));
            jmixMessage.setRole(mapRole(m.getMessageType()));
            jmixMessage.setContent(m.getText());
            dataManager.save(jmixMessage);
        }
    }
    // ...findByConversationId, deleteByConversationId delegate through
}
```

If the Jmix projection throws, Spring AI's memory insert rolls back too (invariant: every `SPRING_AI_CHAT_MEMORY` row has a matching `AiMessage`).

**Context Window Strategy:**

Phase 4 uses `MessageWindowChatMemory` with `maxMessages(20)` — Spring AI's default fixed-window strategy. This is adequate for Phase 4 because:

- No RAG yet (retrieved chunks land in Phase 5 and will re-shape the budget).
- Tools return bounded results (Phase 3 `<data>`-delimited formatter + hard `limit` cap).
- Phase 4 is blocking single-turn; no streaming back-pressure.

For 20 messages at ~500 tokens each = ~10k tokens, well under `gpt-4o-mini`'s 128k window. If a host profile targets a smaller-context model (`gpt-3.5-turbo` at 16k), they set `maxMessages` lower via a Phase 6 parameter. Summarization / compaction is deferred — the ROADMAP does not list it as an MVP deliverable.

## 4b. AI Systems Best Practices

> Cross-cutting patterns for building AI systems in Spring AI 1.1.4 on Jmix. Java 17 only — the template's Python/Pydantic placeholders have been translated to the Spring AI equivalent.

### Structured Outputs with Pydantic (Java: `BeanOutputConverter` + `.entity(Class)`)

> **Scope note:** Pydantic does not exist in Java. Spring AI's equivalent is `BeanOutputConverter<T>` wired through `ChatClient.CallResponseSpec.entity(Class<T>)`, with Jakarta Bean Validation annotations on the target POJO.
> **This section documents the pattern for forward-compatibility. It is NOT used in Phase 4.** Structured output lands in **Phase 6** (ROADMAP Phase 6 deliverable: "`BeanOutputConverter` + `.entity(Class)` path + bounded retry (max 2)"). Phase 4 `ChatService.ask()` returns a plain `ChatResponseDto` carrying assistant text; no schema-constrained output path is exercised.

Pattern (Phase 6 territory — shown here only so the planner does not invent an incompatible shape):

```java
// 1. Target POJO with Jakarta Bean Validation annotations (Pydantic analogue).
public record OrderSummary(
        @NotBlank String customerName,
        @NotNull @PositiveOrZero BigDecimal total,
        @NotEmpty List<@NotBlank String> lineItems) {}

// 2. Call .entity(Class) — Spring AI generates a JSON schema hint from the type,
//    appends it to the user prompt, parses the model response, and binds it.
public OrderSummary summarize(UUID orderId) {
    return chatClient.prompt()
            .user(u -> u.text("Summarize order {id}").param("id", orderId))
            .call()
            .entity(OrderSummary.class);
}

// 3. Retry-on-validation-failure (Phase 6: bounded to 2 attempts).
//    Jakarta @Valid triggers ConstraintViolationException on binding failure;
//    Phase 6's StructuredOutputRetryAdvisor catches, re-prompts with the
//    violation message, and retries once more before surfacing.
```

Retry policy (Phase 6): max 2 retries, log each failure at WARN with the constraint violation message, surface the final typed error (`StructuredOutputValidationException`) to the caller. **Never** retry unbounded — the ROADMAP Phase 6 success criterion explicitly caps at 2.

### Async-First Design

Spring AI 1.1.x offers both synchronous `.call()` and reactive `.stream()` paths on `ChatClient`. **Phase 4 is blocking only (D-16).** `ChatService.ask()` returns a synchronous `ChatResponseDto`; streaming (`Flux<String>`, Vaadin Flow server push) is deferred to **Phase 7** when a UI consumer validates `ToolCallAdvisor`-with-streaming behavior end-to-end.

Sync pattern used in Phase 4:

```java
// Blocking — returns when the full response (including any tool-call rounds)
// is assembled. Runs on the caller's thread; NOT suitable for Vaadin UI
// threads (Phase 7 will push to a worker).
ChatClientResponse resp = chatClient.prompt()
        .user(message)
        .tools(toolProvider)
        .options(options)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, convId))
        .call()
        .chatClientResponse();
```

The one common mistake (do **not** do this in Phase 4):

```java
// WRONG — mixes sync + reactive surface; the .block() negates streaming and
// trips Reactor's "block()-on-non-blocking-thread" guard on WebFlux servers.
String content = chatClient.prompt().user(message).stream().content().blockLast();
```

Choose-one rule: use `.call()` for Phase 4 (blocking, integrates cleanly with `@Transactional` methods and the Phase 4 audit advisor); Phase 7 will introduce `.stream()` behind a separate `ChatService.askStreaming(...)` method so advisor and audit behavior can be re-verified for the reactive path.

### Prompt Engineering Discipline

**System vs. user separation:** Never concatenate system guidance into the user message. The system prompt comes from `AiParameters.systemPrompt` and is set via `.system(...)` on the `.prompt()` builder; the user message is the raw input. Mixing the two lets prompt-injection in the user input override system rules (exactly the failure the Phase 3 `<data>`-delimited formatter is designed to prevent at the tool-result layer).

```java
chatClient.prompt()
        .system(params.getSystemPrompt())   // profile-owned, static per call
        .user(userInput)                    // untrusted; NEVER concatenate system into here
        .call()...
```

**Few-shot:** Keep few-shot examples in the system prompt (or, in Phase 5, retrieved from a curated exemplar store via RAG). Do **not** inline them in Java string literals — profile-owned system prompts are human-editable via the Phase 6 UI; hard-coded examples are not.

**Baseline context (D-15):** `BaselineContextProvider` composes `{current user id, roles, locale, conversation id}` into the system prompt **before** SPI `PromptContextContributor` beans run. This is first-class, not an SPI default. The prompt assembly order is: baseline → profile system prompt → (Phase 6) SPI contributors → user message.

**Token budget — set `maxTokens` explicitly.** `OpenAiChatOptions.builder().maxTokens(...)` MUST be set per profile. Leaving it unbounded in production causes two observable bad outcomes: runaway cost on pathological prompts, and OpenRouter rejecting the request with a 400 for certain routes that require an explicit cap. Phase 4 default: `maxTokens = 1000` in `jmix.ai-agent.defaults.max-tokens`.

### Context Window Management

**For this system type (conversational + tool use, no RAG in Phase 4):**

- `MessageWindowChatMemory` with `maxMessages(20)` — fixed window; oldest messages dropped when the cap is exceeded. No summarization in Phase 4.
- Tool results are already bounded by the Phase 3 `limit` cap and `<data>`-formatter; they do not balloon context on their own.
- Per-turn assembly: `system prompt` + `N message history` + `current user message` + `tool-definition schemas`. For `gpt-4o-mini` (128k window) and our defaults, this sits at ~12–15k tokens even in worst case — well under the cap.

**Phase 5 (RAG) will add:** a reranker before `QuestionAnswerAdvisor` context insertion so retrieved chunks stay within a per-turn budget (not Phase 4's problem).

**Phase 6 (guardrails) will add:** a per-session token circuit breaker that cuts off a runaway conversation before it hits the model's hard limit. Phase 4 does NOT ship this — it is called out in the ROADMAP as GUARD-04.

**Multi-agent / autonomous compaction:** N/A — this is a single-agent conversational system; no sub-agent chain to compact.

### Cost and Latency Budget

**Framework for estimation (not invented numbers):**

OpenRouter bills per 1K input + 1K output tokens, passed through from the underlying provider. Exact rates vary by model slug and change; see https://openrouter.ai/models. The Phase 4 cost model for a single `ChatService.ask()`:

```
cost_per_call ≈ (prompt_tokens × input_rate + completion_tokens × output_rate) × (1 + avg_tool_rounds)
```

Tool rounds multiply because each tool invocation is a round-trip: the model emits a tool call, the framework invokes the tool, the result re-enters the prompt, and the model generates again. With Phase 6's default iteration cap of 6, a worst-case chat could incur up to 6× the token cost of a bare Q&A. Phase 4 has no cap yet — a deliberate gap the ROADMAP closes in Phase 6 (`GUARD-02`).

**Measurement in Phase 4:** every `ChatClientResponse.getMetadata().getUsage()` exposes `promptTokens` / `completionTokens` / `totalTokens`. The `AuditAdvisor` captures these on the post-row so cost per conversation is computable from the audit trail without external tracing. No external tracing tool (Langfuse, Phoenix) is provisioned in Phase 4 — deferred to Phase 8.

**Caching strategies (deferred):**

- **Exact-match request caching** — keyed by `(normalized prompt, tool set, options)` hash. NOT in Phase 4; would interact with conversation state. Revisit in Phase 6.
- **Semantic caching** — vector-similarity-based deduplication of near-identical prompts. Requires RAG infra; reconsider post-Phase 5.
- **Tool-result caching across turns** — explicitly deferred (CONTEXT §Deferred: "every tool call re-executes"). Every Phase 4 tool invocation hits `DataManager` fresh.

**Sub-task model routing:** N/A in Phase 4. Per-conversation model selection lives in `AiParameters` and is already a knob; no automatic routing between "cheap for classification, expensive for synthesis" pipelines in this phase. Host applications that need it can set a cheaper model per profile (e.g. `openai/gpt-4o-mini` for routine queries; upgrade a specific conversation via Phase 6 per-conversation overrides).

**Streaming cost note:** Streaming does not reduce token cost (the model still generates the same output) — it only reduces time-to-first-byte. Phase 7 scope; irrelevant to Phase 4's cost model.

**Latency expectations (measurement, not promise):**
- Bare Q&A, `gpt-4o-mini` via OpenRouter: typically single-digit seconds end-to-end (network + inference). Varies by route.
- With one tool round-trip: roughly 2× the bare Q&A latency (two model calls + one DataManager query).
- With iteration-cap hit (Phase 6): up to ~6× bare latency in the worst case.

These are **order-of-magnitude observations** from Spring AI community reports, not SLAs. Phase 4 captures `latencyMs` on every audit post-row; actual distribution should be measured against real host traffic before any SLA is promised.

## 5. Evaluation Strategy

> Phase 4 is a Jmix add-on, not a product. "Eval" here means **JUnit 5 + Spring Boot integration tests** that assert the structural invariants the domain rubrics in §1b call for — advisor ordering, ownership opacity, audit durability, dual-layer fidelity, listener isolation. LLM-as-judge is explicitly out of scope for Phase 4: the risks the domain experts flagged (authorization parity, audit durability, ownership opacity) are *deterministic* properties, not *subjective* quality properties, so code-based measurement is the right tool. One `@Tag("live")` semantic-similarity smoke exists purely to confirm the OpenRouter wire-up still behaves; it is not a judge over quality.

The `-PincludeLiveTests=true` pattern mirrors Phase 1 D-04 (`@Tag("live")` gating). CI pipelines run `./gradlew test` on every PR; the live tier runs on a schedule or on-demand, never blocking merge.

### Reference Dataset

**Size:** ≈20–30 scripted scenarios (JUnit `@ParameterizedTest` inputs + fixture data), hand-curated. This is not a "chat quality corpus" — it is a structured-invariant test vector.

**Composition:**

| Scenario family | Approx. count | What it exercises |
|---|---|---|
| Ownership negatives (userA probes userB's convId, userA probes nonexistent convId, same for admin user) | 4 | E2, ties into E7. Every row in §1b's "Conversation-id probing" failure mode. |
| Advisor-order structural assertion | 1 | E5. Uses the real `AIAutoConfiguration` — no scenario text needed. |
| Forced tool-failure with rollback | 3 | E3a: tool throws; E3b: advisor throws post-tool; E3c: tool-invocation succeeds but downstream DB write fails. |
| Throwing-listener isolation | 2 | E3 + E6. One listener throws `RuntimeException`, one throws `Error`. |
| Dual-layer consistency (scripted 3-turn chat with 1 tool call, 1 tool-failure variant) | 3 | E4. Also happens to exercise the happy path end-to-end with a mocked `ChatModel`. |
| Authorization parity (restricted user asks a question that would require a denied row) | 3 | E1. One customer-row case, one order-row case, one cross-entity case. |
| Integrator-ergonomic smoke (`jmix-app` consumer test) | 1 | E7. One call with default config. |
| OpenRouter live smoke | 1 | E8. `@Tag("live")`. |
| Edge cases (empty message, whitespace-only message, very long user message at max-tokens boundary) | 3 | Sanity. Not tied to a domain rubric; present because they are cheap. |

**Labeling:**

Every scenario has an **expected outcome encoded as JUnit assertions**, not a labelled string. The "labeller" is the test author — a Senior Jmix integrator (per §1b Domain Expert Roles) during code review. Security/compliance reviewer sign-off is required for the Ownership-negatives family (E2) and the Authorization-parity family (E1) because these are the Critical-stakes rubrics that explicitly call for host-representative calibration.

Fixture data (users, roles, Customer/Order rows) lives in `jmix-app/src/test/resources/test-data.sql` (per CLAUDE.md test conventions); the fixture schema itself is curated by the Jmix integrator role and reused across scenarios to keep the dataset small and legible.

## 6. Guardrails

> Phase 4 guardrails are **structural**, not content-filtering. Content-filtering guardrails (ToolGuard, iteration cap, structured-output retry) are Phase 6 (GUARD-01..05) and are explicitly deferred — this section MUST NOT invent them ahead of schedule. Every online guardrail below is a code-path the chat request cannot skip; every offline signal below is a column (or computable aggregation) on `AiToolCallAudit` that later phases will operationalize.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|---|---|---|
| **Pre-chain ownership check** (D-09) | Every `ChatService.ask(userId, convId, ...)` call, before any advisor runs. | **Block** — throw `ConversationNotFoundException` with a fixed message; same exception for "row does not exist" and "row exists but row-level-predicate filtered it". No tool call, no LLM call, no history write. |
| **Row-level predicate as defence in depth** (D-08 Phase 2 + D-09) | Every `DataManager` load of `AiConversation` / `AiMessage` — including the pre-chain check above. | **Filter** — Jmix AccessManager removes non-owned rows before the pre-chain check even sees them. Guards against any future regression that bypasses the service-layer pre-check. |
| **`AuditWriter.writeXxx` `REQUIRES_NEW` transaction boundary** (D-11) | Every audit write — chat pre, chat post, per-tool-call pre, per-tool-call post. | **Isolate** — audit write commits independently of the advisor/tool transaction. When the tool or advisor rolls back, audit rows survive; audit is the durable source of truth. |
| **`afterCommit` listener fan-out with per-listener try/catch** (D-13/D-14) | Every successful audit write triggers fan-out via `TransactionSynchronizationManager.registerSynchronization`. | **Suppress** — each listener runs inside its own `try { listener.onEntry(row); } catch (Throwable t) { log.warn(...); }`. No listener can break another listener or the chat request. Listeners never see rolled-back rows. |
| **`ToolCallAdvisor.disableMemory()` enforced at bean assembly** (D-02) | `AIAutoConfiguration` builds `ToolCallAdvisor` with `.disableMemory()` unconditionally; Phase 4 does NOT expose a knob to turn it off. | **Constrain** — prevents the "double-history" pitfall (Pitfall #1 in §3). Structural, not runtime; but a boot-time `@PostConstruct` assertion confirms the flag is set (defensive against future refactor). |
| **Dual-layer same-transaction projection** (D-05/D-07) | Every `ChatMemoryRepository.saveAll` call. | **Atomic** — `ProjectingChatMemoryRepository` decorator writes both layers in the same `REQUIRED` transaction. If Jmix projection throws, Spring AI memory insert rolls back too; cannot desync. |

Phase 4 ships **no content-filtering guardrails** (no PII scrubber, no output moderation, no tool-denial guard). These are called out in PROJECT.md's honest-security posture and in the CONTEXT.md Deferred list.

### Offline (Flywheel)

> Phase 4's flywheel role is **emit the audit data** that Phase 5+ will mine. The metrics below are computable from `AiToolCallAudit` columns as of Phase 4; dashboards / alerts / retraining signals are Phase 8 territory. This table is the honest scope.

| Metric | Sampling Strategy | Action on Degradation |
|---|---|---|
| **Chat-level outcome distribution** (`SUCCESS` / `FAILED` ratio over the `AiToolCallAudit` post-row set, grouped by day + model + profile) | Batch query over `AiToolCallAudit` where `kind=CHAT`; no sampling — Phase 4 volume is low enough to compute over the full set. | **Manual review (Phase 4)** — a spike in `FAILED` outcomes triggers human investigation of the last N failed `runId`s by the Jmix integrator role. No automated retraining loop; the add-on does not have a training surface. |
| **Tool-call rate per conversation** (count of `kind=TOOL` rows per `conversationId`) | Batch aggregation grouped by `conversationId`. | **Signal only (Phase 4)** — high tool-call rates feed the Phase 6 iteration-cap default (`GUARD-02`). Phase 4 just records the data. |
| **Ownership-rejection rate** (`ConversationNotFoundException` count as surfaced in structured logs; Phase 4 does NOT write a dedicated audit row for pre-chain rejections — this is a deliberate decision to keep rejection cheap and to prevent the rejection path from leaking existence via audit-row presence) | Log-based (structured JSON via logback) — host forwards to whatever log aggregator they already have. | **Alert candidate (host-operational)** — a sudden spike plausibly indicates conversation-id enumeration. Phase 4 does NOT ship alerting; the metric is documented so hosts can wire it into their existing SIEM. |
| **Per-model latency percentiles** (p50 / p95 / p99 of `latencyMs` on `kind=CHAT` post-rows, grouped by `AiParameters.model`) | Full-set computation at current volume. | **Profile tuning** — a profile consistently above p99 target is a candidate for a different model slug. Phase 4 records; Phase 6 exposes the profile-editing UI that acts on the signal. |
| **Listener-failure count** (listener exceptions observed via WARN-log count) | Log-based; listeners do NOT write audit rows (by design — listeners are host-owned and could themselves be misconfigured). | **Host-owned** — if a host's listener is throwing, the host owns the fix. Phase 4's invariant is that the fail-out does not damage the chat request or the audit row. |

## 7. Production Monitoring

> Phase 4 is MVP; it ships with structured logging and `AiToolCallAudit` as its observability surface. Arize Phoenix (the workflow default) is recommended as an **optional host integration** — Spring AI 1.1.x can emit OpenTelemetry spans that Phoenix ingests, but the add-on itself does NOT bundle an OTel exporter (that would force a dependency on every host). Phase 4 documents the hook; host applications opt in.

**Tracing Tool:**

- **Phase 4 default (shipped):** `AuditAdvisor` is the tracing source of truth. Every `ChatService.ask(...)` produces one `kind=CHAT` pre-row + one post-row linked by `runId`; every tool invocation produces one `kind=TOOL` pre-row + one post-row also linked by `runId`. The `AiToolCallAudit` table + structured JSON logs are sufficient to reconstruct any chat request after the fact.
- **Phase 4 optional (host integration):** **Arize Phoenix**, self-hosted, via OpenTelemetry. Recommended wiring: host adds `io.opentelemetry:opentelemetry-exporter-otlp` + a Phoenix collector URL; the add-on's `AuditAdvisor` + `ToolCallbackAuditDecorator` emit OTel spans alongside the DB writes so Phoenix's trace view shows the same advisor chain the audit table records. **Emitting OTel spans from the advisor is deferred to Phase 8** — Phase 4's structured logs + audit table are the MVP observability posture; promoting Phoenix to a hard requirement is only justified when host traffic volume exceeds what the audit table + ad-hoc DataManager queries can answer.
- **Alternatives:** Langfuse / LangSmith / Braintrust are Python/Node-first; they are not a natural fit for a Jmix-Spring-Java add-on. If a host already runs Langfuse for other services, the OTel path reaches them too; Phoenix is recommended as the default because it is open-source, Java-friendly, and tracing-focused rather than LLM-platform-focused.

**Key Metrics to Track:**

All five are derivable from `AiToolCallAudit` rows (plus structured logs for the last one) — no external instrumentation is required in Phase 4.

1. **`kind=CHAT` outcome distribution** — `SUCCESS` / `FAILED` / (future) `TIMEOUT` ratio. The headline health signal. Degradation here is the single most important trigger for investigation.
2. **Chat latency percentiles** — p50 / p95 / p99 of `latencyMs` on `kind=CHAT` post-rows, grouped by `AiParameters.model`. Baselines what "slow" looks like per model slug; drives Phase 6 profile decisions.
3. **Tool-call rate per conversation** — mean / p95 of `count(kind=TOOL) per runId`. A runaway conversation (tool loop) shows here first; feeds the Phase 6 iteration-cap tuning.
4. **Ownership-rejection rate** — count of `ConversationNotFoundException` over time. A spike is a plausible enumeration-attempt signal; hosts wire this into their existing SIEM.
5. **Listener-failure count** — WARN-log count per listener bean name. A persistently-failing listener is a host-misconfiguration that the host owns the fix for; the add-on just keeps it from breaking the chat.

**Alert Thresholds:**

> Phase 4 does NOT ship alert rules; the numbers below are **order-of-magnitude defaults** that a host's SRE tunes against their actual traffic. Promoting any of these to a hard SLA requires real traffic measurements (per §4b "Cost and Latency Budget").

| Metric | Suggested default | When to tighten |
|---|---|---|
| `kind=CHAT` `FAILED` rate | `> 5%` over a rolling 1-hour window → investigate | Tighten to `> 1%` once the system has baseline traffic + the failure modes are understood. |
| Chat latency p95 | `> 15s` sustained over 15 minutes → investigate | Tighten per model: `gpt-4o-mini` should not hold `p95 > 10s` in a healthy steady state. |
| Ownership-rejection rate | `> 10× baseline` over 5 minutes → security alert | Baseline is measured, not assumed. |
| Listener-failure WARN count | `> 0` for any given listener bean over 15 minutes → notify host team | A single throw is an incident the host owns. |
| Audit-write failure (meta-guardrail) | `> 0` ever → page immediately | Audit is the durable source of truth; any crack is an outage of the observability layer itself. |

**Smart Sampling Strategy:**

Signal-based, not random. The `AiToolCallAudit` row itself is the signal source — keeping **100% of interesting rows** and **sampling boring rows at a configurable ratio** is viable at v1 volume. Concretely:

- **Always kept (100%):**
  - `kind=CHAT` rows where `outcome != SUCCESS`.
  - `kind=TOOL` rows where `outcome != SUCCESS` (`FAILED`, and when Phase 6 ships, `DENIED` / `TIMEOUT`).
  - Rows where `latencyMs > p99_baseline_for_this_model` (computed weekly, fed from the same table).
  - Rows with a non-null `errorClass`.
  - Ownership-rejection log events (they do NOT write audit rows by design — see §6).
- **Sampled at ratio R (default `R=1.0` — keep all — in Phase 4):**
  - `SUCCESS` rows. Rationale: Phase 4 volume is low enough that 100% retention is fine; the sampling ratio exists as a knob for Phase 8 when a host's volume makes full retention expensive.
- **Manually promoted to review:**
  - Any `runId` flagged by the Jmix framework practitioner role (§1b) — e.g. "this conversation felt weird" → pull every row with that `runId`, walk the advisor trace.

Retention in Phase 4 is a host concern — the add-on does not prune `AiToolCallAudit`. A Phase 8 retention policy (e.g. "kept-forever for `FAILED`, 90 days for `SUCCESS`") is the natural follow-up; for Phase 4 the explicit non-commitment is documented here.
