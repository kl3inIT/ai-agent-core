## 1. System Classification

**System Type:** Hybrid — tool-calling conversational assistant with prompt-contract hardening and output guardrails.

**Description:**
Phase 9 hardens the already-shipped Jmix AI Copilot tool and prompt boundary. The LLM receives a richer, deterministic, leakage-resistant view of the host Jmix schema through `agent.entities`, `agent.permissions`, richer `describe_entity` metadata, stricter `unknown_entity` recovery hints, and output-scanner leakage patterns. The phase stays read-only: no new entities, no mutation tools, and no behavioral change to Jmix data-access policy. "Good" means the model can discover and discuss host data using labels and allowed metadata, while Jmix `AccessManager`, `DataManager`, `MetadataTools`, `MessageTools`, and `FetchPlan` remain the authority for access, loading, labels, and projection.

**Critical Failure Modes:**
1. **Prompt/schema leakage across users** — `agent.entities`, `agent.permissions`, `describe_entity`, or tool callbacks expose an entity, attribute, CRUD bit, or tool surface that the current Jmix user should not see.
2. **Internal vocabulary leak in user-facing prose** — final replies contain host-prefixed metaclass names such as `jmixapp_Customer`, raw tool names such as `find_records`, advisor names such as `RETRIEVAL`, or wrapper internals instead of business labels.
3. **Non-deterministic prompt contract** — equivalent user, locale, role, and schema state produces different ordering or shape in baseline context or tool metadata, breaking prompt-hash stability, regression tests, and audit replay.
4. **Wrong `unknown_entity` recovery** — the model guesses entity names, loops over discovery tools, or reports "no data" when the correct behavior is one `list_entities` call followed by exact retry or explicit no-such-entity response.
5. **Fetch-plan widening mistaken for security** — a host `ToolFetchPlanCustomizer` returns a plan containing denied attributes and the add-on loads them before pruning, leaking data into JVM memory or tool output.

## 1b. Domain Context

**Industry Vertical:** Developer tooling / enterprise internal applications — a horizontal Jmix AI add-on embedded into host systems of record.

**User Population:** Authenticated Jmix operators using chat over host data; admin operators configuring the add-on; Jmix/security architects validating that the AI surface obeys the same permissions, labels, and audit expectations as the host UI.

**Stakes Level:** High.

**Output Consequence:** The AI response can influence operational decisions inside an enterprise app, reveal host schema/security structure, or create audit evidence used by administrators during incident review. Phase 9 is read-only, but mistakes at this layer become the contract future exposure and mutation phases build on.

### What Domain Experts Evaluate Against

```
Dimension: Prompt-contract determinism
Good: The same user, locale, roles, and schema produce byte-stable agent.entities,
      agent.permissions, and describe_entity ordering; prompt diffs are explainable
      by real metadata or permission changes.
Bad:  Entity order, permission key order, or metadata field order changes between
      equivalent runs, making prompt regressions, cache behavior, and audit replay
      non-reproducible.
Stakes: High
Source: Enterprise audit/release practice; NIST AI RMF measurable-system-behavior guidance.
```

```
Dimension: UI/security parity
Good: The AI-visible entity list, per-attribute readability, CRUD bits, and returned
      records match what the same authenticated user could discover through normal
      Jmix UI/DataManager access.
Bad:  The prompt lists an entity, attribute, or modifiable field that the user's Jmix
      UI hides, or suppresses something the user is permitted to see.
Stakes: Critical
Source: Jmix AccessManager, entity/attribute permissions, and row-level role model.
```

```
Dimension: User-facing vocabulary hygiene
Good: End-user replies use business labels and instance names; raw host-prefixed entity
      names such as jmixapp_Customer, built-in tool names such as find_records, and
      RAG/advisor internals never appear in user-facing prose.
Bad:  The assistant says it used describe_entity, tells the user to call list_entities,
      or exposes internal metaclass names that help attackers infer the host data model.
Stakes: High
Source: OWASP LLM sensitive-information and tool-surface leakage risks; Phase 9 PROMPT-03/04/06.
```

```
Dimension: Unknown-entity recovery
Good: On unknown_entity, the model calls list_entities exactly once, retries only with an
      exact listed entity name when there is a clear match, and otherwise tells the user
      no such entity exists.
Bad:  The model guesses semantically similar entities, loops over discovery tools, treats
      denied entities as accessible-but-empty, or tells the user "no records found" when
      the failure was a bad entity name.
Stakes: High
Source: Phase 9 PROMPT-05; production agent failure pattern where tool errors trigger
        retries, loops, or wrong-tool recovery.
```

```
Dimension: Permission-narrowed fetch plans and audit trail
Good: A host ToolFetchPlanCustomizer can narrow/optimize projection, but any returned
      plan is intersected with current user attribute permissions before DataManager
      load; dropped attributes are silently omitted from LLM output and recorded as
      PLAN_NARROWED audit evidence.
Bad:  A custom fetch plan widens access beyond the user's permissions, or denied
      attributes disappear without any audit signal for security review.
Stakes: Critical
Source: Jmix fetch plans are projection/performance controls, not authorization;
        Jmix security remains the access-control source of truth.
```

### Known Failure Modes in This Domain

- **Cross-user or stale schema leakage:** a cached or non-deterministic baseline prompt exposes another role's entity inventory or permission map, even if later tool calls are denied.
- **Internal-name/tool leakage in final answers:** the assistant reveals metaclass prefixes, tool names, advisor names, or XML wrapper internals, turning a business copilot into a schema-reconnaissance surface.
- **Wrong recovery after unknown entity:** the model guesses an entity, retries repeatedly, or reports "no data" instead of following the exact list-once recovery contract.
- **Fetch-plan widening mistaken for authorization:** a host projection includes sensitive attributes; without permission intersection, the AI sees data the UI would not show. Without audit, administrators cannot distinguish expected pruning from policy drift.

### Regulatory / Compliance Context

No single sector regulation directly governs the add-on because it is horizontal developer tooling. Compliance obligations are inherited from the host Jmix application and deployment context.

For enterprise hosts, the directly relevant expectations are least-privilege access, traceable audit evidence, deterministic release/regression behavior, and no unnecessary disclosure of personal or confidential data. GDPR may apply when host data includes EU personal data. SOC 2 / ISO-style enterprise reviews will care about access-control parity, change evidence, and audit completeness.

OWASP LLM / Agentic AI guidance and NCSC prompt-injection guidance are the practical AppSec baseline: system prompts are not a security boundary, tool access must be constrained outside the model, and audit surfaces must not become leakage surfaces.

## 2. Framework Decision

**Selected Framework:** Spring AI 1.1.4.

**Version:** 1.1.4, BOM-managed in the existing Gradle build.

**Rationale:**
Spring AI is already the project framework and exactly fits Phase 9's narrow goal: harden the existing Java/Jmix tool and prompt contract without introducing a second agent runtime. Phase 9 needs per-request tool callbacks, advisor-chain output scanning, `@Tool`/`@ToolParam` method discovery, optional structured-output support for tests and host code, and provider abstraction through `ChatModel`. Spring AI already supplies those primitives, while Jmix supplies the metadata, security, data loading, labels, and fetch plans. A new framework would churn the shipped chat, audit, RAG, guard, and tool contracts for no Phase 9 benefit.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain4j 1.12.1 | Credible Java alternative, but it would replace already-shipped Spring AI advisor/tool/RAG/audit integration and create a parallel model/tool abstraction. |
| Raw OpenAI/OpenRouter SDK | Would require rebuilding tool schema generation, tool-call loop, advisor ordering, tracing hooks, retries, and model abstraction already provided by Spring AI. |
| Python agent frameworks | Incompatible with the Java/Jmix add-on packaging and would create a second runtime beside the host Spring Boot application. |

**Vendor Lock-In Accepted:** Partial. Framework-level lock-in to Spring AI is accepted because the roadmap already depends on it. Model-provider lock-in is avoided by using Spring AI's `ChatModel` abstraction; the default remains OpenAI-compatible/OpenRouter and can be replaced by the host.

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|------------|-----------------|
| `ChatClient` | Spring AI fluent chat entry point | Singleton client; each request supplies prompt, options, tools, and advisor params. |
| `ToolCallback` / `@Tool` / `@ToolParam` | Spring AI tool-calling surface | Built-in data tools and host-contributed tools. In 1.1.4 use `callback.getToolDefinition().name()` for names. |
| `MethodToolCallbackProvider` | Reflects `@Tool` methods on a bean | Existing replacement for non-existent `ToolCallbacks.from(bean)`. |
| `ToolCallAdvisor` | Executes the model/tool loop | Keep current advisor order and conversation-history behavior for OpenAI-compatible tool-message pairing. |
| `BeanOutputConverter<T>` | Java equivalent of Pydantic-style schema prompting/parsing | Used by `askTyped` and eval harnesses; not needed for server-generated tool DTOs. |
| Jmix `MetadataTools` / `MessageTools` | Metadata and locale-aware labels | Rich `describe_entity`, captions, enum labels, instance names. |
| Jmix `AccessManager` | Entity/attribute permission authority | `agent.permissions`, readable schema, fetch-plan intersection. |
| Jmix `DataManager` | Secure data loading | All tool reads. No `EntityManager`; no mutation in Phase 9. |
| Jmix `FetchPlan` | Projection/performance shape | Host override surface, then permission-narrow before `DataManager.load(...)`. |

### Common Pitfalls

1. **Using `defaultToolCallbacks(...)` leaks tool/schema visibility across users.** Tool availability depends on the current Jmix security context, so callbacks must be rebuilt per request.
2. **Calling `ToolCallback.getName()` may not compile in the installed Spring AI API.** Use `callback.getToolDefinition().name()`.
3. **`ToolCallbacks.from(bean)` is not present in the installed 1.1.4 API.** Use `MethodToolCallbackProvider.builder().toolObjects(bean).build().getToolCallbacks()`.
4. **Disabling `ToolCallAdvisor` conversation history can break OpenAI-compatible tool turns.** Keep assistant tool-call messages paired with tool responses.
5. **A host `FetchPlan` override can accidentally expose denied attributes unless narrowed.** Always intersect returned plans with `CurrentUserSchemaAccess` before calling `DataManager`.
6. **Catching bare `Exception` around structured-output retries hides guard denials and provider failures.** Retry only parse/validation failures.

**Core Pattern:**
Phase 9 is a thin contract layer over existing Spring AI and Jmix primitives:

1. Build per-request baseline prompt context in `BaselineContextProvider`.
2. Keep per-request tool callbacks through `AgentToolCallbacks`.
3. Extend `BuiltInDataTools.describeEntity(...)` and `ToolResultFormatter` DTO rendering.

### Baseline Prompt Contract

Render `agent.entities` and `agent.permissions` from the same source as the built-in tools: `CurrentUserSchemaAccess`.

Rules:
- `agent.entities`: sorted by `MetaClass.getName()`, one line per readable entity: `name (label)`.
- Empty schema: omit the key entirely.
- Default cap: 100 entities. Add trailing line: `... (truncated, call list_entities for full list)`.
- `agent.permissions`: compact deterministic JSON with keys ordered by entity and attribute.
- Locale-sensitive labels are rendered at request time but never included in a cache key.

```java
Map<MetaClass, Set<String>> schema = currentUserSchemaAccess.getReadableSchema();

String entities = schema.keySet().stream()
        .sorted(Comparator.comparing(MetaClass::getName))
        .limit(properties.entityInventoryLimit())
        .map(metaClass -> metaClass.getName() + " (" + messageTools.getEntityCaption(metaClass) + ")")
        .collect(Collectors.joining("\n"));

Map<String, Object> permissions = new TreeMap<>();
for (MetaClass metaClass : schema.keySet()) {
    CrudEntityContext crud = new CrudEntityContext(metaClass);
    accessManager.applyRegisteredConstraints(crud);

    Map<String, Object> entry = new LinkedHashMap<>();
    entry.put("r", crud.isReadPermitted() ? 1 : 0);
    entry.put("u", crud.isUpdatePermitted() ? 1 : 0);
    entry.put("c", crud.isCreatePermitted() ? 1 : 0);
    entry.put("d", crud.isDeletePermitted() ? 1 : 0);
    entry.put("modifiable", modifiableAttributes(metaClass));
    permissions.put(metaClass.getName(), entry);
}
```

```java
private AttributeDescription describeAttribute(MetaClass metaClass, MetaProperty property) {
    Range range = property.getRange();
    MetaProperty primaryKey = metadataTools.getPrimaryKeyProperty(metaClass);

    String comment = metadataTools.getMetaAnnotationValue(property, Comment.class);
    boolean persistent = metadataTools.isJpa(property);

    List<EnumValueDescription> enumValues = null;
    if (range.isEnum()) {
        enumValues = range.asEnumeration().getValues().stream()
                .map(value -> (Enum<?>) value)
                .map(value -> new EnumValueDescription(value.name(), messages.getMessage(value)))
                .toList();
    }

    EntityRef target = null;
    if (range.isClass()) {
        MetaClass targetMetaClass = range.asClass();
        target = new EntityRef(targetMetaClass.getName(), messageTools.getEntityCaption(targetMetaClass));
    }

    return new AttributeDescription(
            property.getName(),
            messageTools.getPropertyCaption(property),
            comment,
            property.getType().name(),
            range.getCardinality().name(),
            property.isMandatory(),
            property.isReadOnly(),
            persistent,
            !persistent,
            Objects.equals(primaryKey, property),
            enumValues,
            target,
            maxLength(property)
    );
}
```

Document exclusions in Javadoc only: DDL column names, JPA fetch type, cascade rules, raw annotations, internal store name, and framework-managed audit fields. Configurable entity/attribute LLM exposure is not Phase 9 and must not be confused with this fixed metadata omission list.

### Unknown Entity Retry Contract

When entity resolution fails, return `unknown_entity` with the fixed `expected` list.

```java
private static final List<String> UNKNOWN_ENTITY_EXPECTED = List.of(
        "call list_entities exactly once",
        "if a name in list_entities matches your intent, retry the original tool with that exact name",
        "if no entity in list_entities matches, tell the user no such entity exists - do not guess"
);

private MetaClass resolveReadableEntityOrThrow(String entityName) {
    try {
        MetaClass metaClass = metadata.getClass(entityName);
        if (metaClass != null && currentUserSchemaAccess.canReadEntity(metaClass)) {
            return metaClass;
        }
    } catch (RuntimeException ignored) {
        // Collapse all misses to the same LLM-facing contract.
    }
    throw new ToolUserError("unknown_entity", "no readable entity named " + entityName,
            UNKNOWN_ENTITY_EXPECTED);
}
```

Also add the system prompt rule in `DefaultChatServiceImpl` so the model knows the retry contract before the first tool error.

### ToolFetchPlanCustomizer SPI

This SPI overrides the data fetch plan only. The default data plan remains `_base`; `_instance_name` stays a Jmix label-projection concern and is not overridden by Phase 9. Hosts needing different labels should model that through Jmix `@InstanceName` / instance-name configuration.

```java
public interface ToolFetchPlanCustomizer {
    Optional<FetchPlan> overrideFor(String toolName, MetaClass metaClass, FetchPlanContext context);
}

public record FetchPlanContext(RunContext run, UserDetails user) {
}
```

Resolution pattern:

```java
FetchPlan defaultPlan = fetchPlans.builder(metaClass.getJavaClass())
        .addFetchPlan(FetchPlan.BASE)
        .build();

FetchPlan requested = customizers.stream()
        .map(customizer -> customizer.overrideFor(toolName, metaClass, context))
        .flatMap(Optional::stream)
        .findFirst()
        .orElse(defaultPlan);

// fetch plan is projection, not security
FetchPlan narrowed = fetchPlanIntersector.intersectReadable(metaClass, requested);
```

The intersector must silently drop denied attributes and audit the drop before `DataManager` sees the plan.

```java
public FetchPlan intersectReadable(MetaClass metaClass, FetchPlan requested) {
    FetchPlanBuilder builder = fetchPlans.builder(metaClass.getJavaClass()).partial(false);

    for (FetchPlanProperty property : requested.getProperties()) {
        String name = property.getName();
        if (!currentUserSchemaAccess.canReadAttribute(metaClass, name)) {
            auditPlanNarrowed(metaClass, name);
            continue;
        }

        MetaProperty metaProperty = metaClass.findProperty(name);
        FetchPlan nested = property.getFetchPlan();
        if (metaProperty != null && nested != null && metaProperty.getRange().isClass()) {
            MetaClass target = metaProperty.getRange().asClass();
            FetchPlan narrowedNested = intersectReadable(target, nested);
            builder.add(name, nestedBuilder -> nestedBuilder.merge(narrowedNested), property.getFetchMode());
        } else {
            builder.add(name);
        }
    }

    return builder.build();
}
```

### AUD-07 Plumbing

```java
public final class AuditFieldHasher {

    private AuditFieldHasher() {
    }

    public static String sha256Hex(String raw) {
        if (raw == null) {
            return null;
        }
        try {
            byte[] digest = MessageDigest.getInstance("SHA-256")
                    .digest(raw.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(digest);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("SHA-256 is not available", e);
        }
    }
}
```

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic-Equivalent Java Records

This Java project does not introduce Python Pydantic. The equivalent contract is a Java record or POJO plus Jackson annotations plus Jakarta Bean Validation. Spring AI integrates through `BeanOutputConverter<T>` and `ChatClient.call().entity(Class<T>)`.

```java
@JsonPropertyOrder({"answer", "entityLabelsUsed", "internalNameLeak", "toolNameLeak"})
public record PromptContractAnswer(
        @NotBlank String answer,
        @NotNull List<@NotBlank String> entityLabelsUsed,
        boolean internalNameLeak,
        boolean toolNameLeak
) {
}
```

Canonical parsing path:

```java
BeanOutputConverter<PromptContractAnswer> converter =
        new BeanOutputConverter<>(PromptContractAnswer.class);

String prompt = userQuestion + "\n\nReturn JSON matching this schema:\n" + converter.getFormat();

PromptContractAnswer answer = chatClient.prompt()
        .system(systemPrompt)
        .user(prompt)
        .options(ChatOptions.builder()
                .model("openai/gpt-4o-mini")
                .temperature(0.0)
                .maxTokens(800)
                .build())
        .call()
        .entity(PromptContractAnswer.class);

Set<ConstraintViolation<PromptContractAnswer>> violations = validator.validate(answer);
if (!violations.isEmpty()) {
    throw new ConstraintViolationException(violations);
}
```

Retry policy:
- Retry only on Jackson parse failure or `ConstraintViolationException`.
- Log target class, attempt number, schema hash, and a redacted raw-output preview.
- Surface `StructuredOutputException` after exhaustion. Never return a partially parsed object.
- Server-generated tool DTOs such as `ToolErrorDto` and `DescribeEntityResult` are developer contracts, not LLM parse targets.

### Async-First Design

Spring AI has two terminal modes:
- `.call()` waits for the complete response.
- `.stream()` returns a Reactor `Flux`.

Use `.stream()` for chat UX because existing chat surfaces render streaming content and tool events. Use `.call()` for structured output because validation requires the complete JSON payload.

Do not call `.block()` on a Spring AI stream inside a Reactor or Vaadin push pipeline. Do not mark `@Tool` methods `@Async`; Spring AI expects a concrete return value from the tool callback.

### Prompt Engineering Discipline

Keep system and user roles separate:
- System prompt: server-controlled rules, baseline `agent.*` context, `unknown_entity` retry contract, internal-name/tool-name leakage rules.
- User prompt: raw user text only.
- Tool results: structured payloads with `<data>` wrappers for untrusted host data.

Do not concatenate user input into the system prompt. Do not put tool results into the system prompt. The model should see tool payloads as data, never as instructions.

Few-shot guidance is acceptable only for stable micro-contracts like `unknown_entity` recovery. Dynamic retrieval is for business knowledge, not for the six built-in tool grammar.

### Context Window Management

Phase 9 adds more baseline context, so the prompt must stay deterministic and bounded.

- Cap `agent.entities` at 100 entries and add a truncation hint.
- Keep `agent.permissions` compact: CRUD bits plus modifiable attribute names only.
- Keep `describe_entity` on-demand. Do not dump every attribute of every entity into the baseline.
- Keep tool result limits: default 20 rows, max 100 rows, `truncated=true` with a `count_records` hint.
- RAG remains top-k and threshold controlled.
- Spring AI has no autonomous compaction equivalent. Conversation summarization should be a future explicit advisor, not hidden behavior in Phase 9.

### Cost and Latency Budget

Do not bake provider prices into code or tests; model pricing changes. Recalculate before production rollout from the active provider contract.

Operational targets:
- Baseline context generation p95 under 25 ms for ordinary host schemas.
- `OutputScannerAdvisor` regex pass p95 under 5 ms on capped 8 KiB final messages.
- Fetch-plan intersection overhead p95 under 10 ms for ordinary `_base` plans.
- No provider call should run with unbounded `maxTokens`.

Caching:
- Exact-match cache only for non-user-specific prompts or keys that include user id, role set, locale, model, profile, and schema version.
- Do not exact-cache `find_records` results across users.
- Semantic cache is safe for documentation/RAG answer candidates, not for permissioned Jmix entity rows.
- Cache `BeanOutputConverter.getFormat()` per target class.

Cheaper model routing:
- Use cheaper models for classification, routing, summarization, and prompt-contract eval fixtures only when the eval objective allows it.
- Use the active profile model for main user turns.
- Never use a cheaper model to make authorization decisions. Jmix `AccessManager` is the authority.

## 6. Guardrails

### Online Guardrails

| ID | Guardrail | Trigger | Action | Latency Budget | Critical Failure Mode |
|----|-----------|---------|--------|----------------|-----------------------|
| G-01 | Current-user schema boundary | Every baseline render and schema/tool metadata response | Build from `CurrentUserSchemaAccess`; omit denied entities/attributes before prompt or tool payload exists | p95 < 25 ms baseline render | Prompt/schema leakage |
| G-02 | Fetch-plan permission intersection | Every `find_records`, `get_record`, `get_related_records` load after `ToolFetchPlanCustomizer` | Drop denied properties recursively before `DataManager.load(...)`; audit `PLAN_NARROWED` with stable details | p95 < 10 ms intersection | Fetch-plan widening |
| G-03 | OutputScanner host-prefix/tool-name patterns | Every final assistant message | Flag and audit stable pattern key; do not block by default; do not expose raw match to user/audit | p95 < 5 ms on 8 KiB reply | Internal vocabulary leak |
| G-04 | Unknown-entity structured recovery | Every failed entity resolution | Return uniform `unknown_entity` with exactly three `expected` hints; preserve denied-entity opacity | negligible | Wrong recovery / schema guessing |
| G-05 | Label-first untrusted data wrapper | Every tool result rendered to model context | Put business label before internal type and wrap rows in `<data>`; model treats data as untrusted | formatter-only | Prompt injection / vocabulary leak |
| G-06 | AUD-07 hashing contract | Phase 9 unit surface only | Keep hasher/properties ready and uncalled by mutation code until Phase 11; tests prevent raw sensitive hash regressions | n/a | Future audit privacy drift |

## 7. Production Monitoring

### Tracing and Telemetry

Primary Phase 9 observability is Java-native:

- `AiToolCallAudit` is the durable record for tool calls, output scanner flags, `unknown_entity`, and `PLAN_NARROWED`.
- Micrometer/Actuator exports counters and timers.
- Structured logs include stable hashes/keys only, never raw scanner matches or sensitive field values.
- OpenTelemetry/Phoenix may be used by hosts already running it, but it is not a Phase 9 dependency or eval stack.

### Sampling Strategy

- 100% of output-scanner flagged responses.
- 100% of `PLAN_NARROWED` rows for the first two weeks after any host customizer is introduced; then 10%.
- 100% of conversations with repeated `unknown_entity`; otherwise 10% sample of unknown-entity recoveries.
- 5% random sample of successful host-data conversations, stratified by locale and role.
- All live `@Tag("live")` failures retained as new fixture candidates.

| Alert | Severity | Response |
|-------|----------|----------|
| Any internal name/tool name leak flag | P2 | AppSec reviews audit row, confirms no raw match was persisted, adds case to scanner corpus |
