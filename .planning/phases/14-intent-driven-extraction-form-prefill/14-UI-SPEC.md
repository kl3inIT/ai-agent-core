# Phase 14 — UI Design Contract

> Visual and interaction contract for the **intent card-row picker** above `messageInputSlot` and the **inline "Open form to confirm" button** rendered on `open_form_with_draft` tool-result payloads.
> Generated by gsd-ui-researcher; verified by gsd-ui-checker.
> Tech stack: Java 21 + Jmix 2.8 + Vaadin Flow 24.8 + Lumo theme. **Not** a React/shadcn project — shadcn gate is not applicable; design tokens are sourced from Lumo CSS custom properties. Phase 14 reuses the Phase 13.1 token set and locale namespace verbatim.

## Layout Contract

Phase 14 introduces two new UI surfaces inside the existing Phase 13.1 split layout:

1. **Card-row intent picker** (`intentCardRow`) — placed **above** `messageInputSlot`, **below** `messageListSlot`, inside the left-pane `chatPanel` `<vbox>`.
2. **Inline confirm button row** (`ai-agent-intent-confirm`) — appended as a sibling DOM element inside `messageListSlot` immediately after the assistant `MessageList` block whose final `ToolResult` carried the `open_form_with_draft` payload. Mirrors Phase 13.1's `appendNoticeRow` pattern (raw `<div>` sibling of the `<vaadin-message-list>`).

The Phase 13.1 right-pane `attachmentsPanel` (and its `<split splitterPosition="68">` parent) is **untouched**.

### Inline confirm-button row (rendered by `StreamEventRenderer` collaborator + `ChatPanelFragment.appendIntentConfirmRow`)

When `StreamEventRenderer.renderStreamEvent(...)` receives a `StreamingEvent.ToolResult` whose JSON parse yields `action == "open_form_with_draft"`, it returns a structural marker (e.g. an empty markdown string PLUS a side-channel callback the host invokes — plan-phase chooses the exact wiring). `ChatPanelFragment` appends a sibling DOM element to `messageListSlot` via the same Phase-13.1 `appendNoticeRow` pattern.

The button is rendered as a **server-side Vaadin component**, NOT as a markdown link inside `MessageList` — `MessageList.setMarkdown(true)` consumes only markdown, and the click handler MUST run controller-side (it touches `AccessManager`, `ViewNavigators`, `DraftLoader`).

| Slot | Component | Source / behavior |
|------|-----------|-------------------|
| Container | Raw `com.vaadin.flow.dom.Element("div")` with class `ai-agent-intent-confirm` (sibling of `<vaadin-message-list>`, mirrors Phase 13.1 `ai-agent-attachment-notice` pattern) | Bypasses markdown-only `MessageList`; click handlers attach via `Element` API. |
| Summary line | `<span classNames="ai-agent-intent-confirm__summary">` text resolved via `Messages.formatMessage("com.vn.agent", "chatView.intent.confirmButton.summary", instanceName)` (NEW key) — escaped via `Element.setText(...)` per Phase 13.1 T-13.1-17 mitigation. | One-line; Lumo `--lumo-font-size-s` (14px) at 400; `--lumo-secondary-text-color`. |
| Confirm button | Jmix `Button` (`com.vaadin.flow.component.button.Button`) with `themeNames="primary small"` (Vaadin Lumo built-in primary button). Text resolved via `Messages.getMessage("chatView.intent.confirmButton")` (NEW key — "Open form to confirm" / "Mở biểu mẫu để xác nhận"). Icon prefix: `VaadinIcon.EXTERNAL_LINK.create()` (16px). | Click handler delegates to `OpenFormWithDraftHandler.open(draftId, entityName, instanceName)` (CONTEXT D-09). Idempotent — re-clickable while draft exists (CONTEXT D-11). |
| Disabled / expired state | Same DOM, Vaadin `Button.setEnabled(false)`. Replaces summary line with `Messages.getMessage("chatView.intent.draftExpired")` ("Draft expired — ask again" / "Phiên nháp đã hết hạn — hãy hỏi lại"). Button text replaced with the same expired-message OR kept and disabled — plan-phase locks the exact transition copy after reading existing `Notification` enabled/disabled patterns. | Triggered when `OpenFormWithDraftHandler.open(...)` raises `DraftNotFoundException` (TTL-reaped or already-saved-and-deleted draft). |
| Permission-denied state | NO in-bubble inline rendering of denied state. Click handler renders a `Notifications.Type.ERROR` toast with `Messages.getMessage("chatView.intent.permissionDenied")` (NEW key — "You don't have access to this form." / "Bạn không có quyền mở biểu mẫu này.") and leaves the button enabled (so the user can re-click after their permissions change). | Triggered when `accessManager.isPermitted(new ViewContext(detailViewId))` returns false. |

**Idempotency contract.** `OpenFormWithDraftHandler.open(...)` re-loads the `AiExtractionDraft` row on every click and reopens the detail view prefilled from the same `payloadJson`. No client-side caching of `draftId`. The DOM element persists in `messageListSlot` for the lifetime of the chat session (until `clearMessageList()` is called via "New chat").

## Spacing Scale

This project uses Lumo spacing tokens (CSS custom properties) — multiples of 4 by Lumo convention. Phase 14 declares ONLY Lumo tokens; no raw pixel values introduced in XML. The single `min-width: 12rem` / `max-width: 16rem` card width and `min-height: 4rem` confirm-row height exceptions are `rem`-based, resolve to multiples of 4 at default Lumo theme, and are documented below.

| Token | Lumo CSS property | Resolved px @ default Lumo theme | Usage in this phase |
|-------|-------------------|----------------------------------|---------------------|
| xs | `var(--lumo-space-xs)` | 4px | Card-row inter-card gap, card-header icon-to-label gap, confirm-row icon-to-label gap |
| s | `var(--lumo-space-s)` | 8px | Card content padding, card-row vertical margin (8px above + 8px below `intentCardRow`), confirm-row inner padding, confirm-row vertical margin |
| m | `var(--lumo-space-m)` | 16px | Card body horizontal padding, confirm-row horizontal padding, confirm-row max-width clamp inner padding |
| l | `var(--lumo-space-l)` | 24px | (Reserved; not used in 14) |
| xl | `var(--lumo-space-xl)` | 32px | (Reserved; not used in 14) |

**Card-width clamps:** `min-width: 12rem` (192px) and `max-width: 16rem` (256px) on `.ai-agent-intent-card`. Both resolve to multiples of 4 at default Lumo `1rem = 16px`. Documented exception — verbatim-style card sizing matches Phase 13.1 attachment-card width discipline (right-pane width-stretch but capped for predictable wrapping when many intents are eligible).

**Confirm-row height clamp:** `min-height: 4rem` (64px) on `.ai-agent-intent-confirm`. Multiple of 4. Ensures the row stands out as a CTA without crowding the message list. Documented exception — same `rem`-based discipline as Phase 13.1's `min-height: 8rem` drop-zone clamp.

**Touch-target exception:** the confirm button uses `themeNames="primary small"` (Lumo small-primary button = 28px height). Acceptable for desktop-primary enterprise UI per Phase 13.1 precedent (project does NOT enforce 44px touch targets).

## Interaction Contract

| Event | Trigger | Reaction |
|-------|---------|----------|
| Page load | `ChatPanelFragment.onReady` → `refreshIntentCardRow()` | Resolve `IntentRegistry.eligibleFor(currentUser)`. If non-empty, populate `intentCardRow.setItems([Auto, ...intents])`, `setValue(Auto)`, `setVisible(true)`. If empty, `setVisible(false)`. |
| Card click | `<radioButtonGroup>` value change event (`@Subscribe(id="intentCardRow") onIntentCardRowValueChange(ComponentValueChangeEvent<RadioButtonGroup<IntentOption>, IntentOption>)`) | Stash selected `intentId` into the existing chat-send request shape (`DefaultChatServiceImpl` consumes the `intentId` field per CONTEXT integration point). Visual: re-render the card list so the new selection's card carries `.ai-agent-intent-card--selected` and the prior selection drops the class. |
| Send turn (Auto selected) | `messageInputSlot` send button click | Default chat path — `intentId` field on send request is null. NO change to the existing Phase 13.1 send wiring. Card row stays on Auto. |
| Send turn (named intent selected) | `messageInputSlot` send button click | Send request carries `intentId={selected}`. AFTER the request is dispatched (BEFORE the response arrives), `intentCardRow.setValue(Auto)` — auto-reset per CONTEXT D-08. The user sees Auto highlighted while the response streams in; the named-intent card remains visible (just not selected) for re-selection on the next turn. |
| Tool-result `open_form_with_draft` arrives | `StreamEventRenderer` parses `StreamingEvent.ToolResult.payloadJson` → `action == "open_form_with_draft"` | Renderer signals the host (`ChatPanelFragment.appendIntentConfirmRow(draftId, entityName, instanceName)`); host appends a `<div class="ai-agent-intent-confirm">` sibling element to `messageListSlot.getElement()` containing the summary line + confirm button. Markdown content of the assistant bubble is unchanged. |
| Confirm button click | `Button.ClickEvent` on the inline confirm button | (1) `OpenFormWithDraftHandler.open(draftId, entityName, instanceName)` runs. (2) `accessManager.isPermitted(new ViewContext(detailViewId))` checked. (3a) If permitted: `viewNavigators.detailView(host, entityClass).newEntity().withInitializer(e -> draftLoader.apply(draftId, e)).navigate()`. The detail view registers an `AfterSaveEvent` listener that deletes the draft. (3b) If NOT permitted: `Notifications.create(messages.getMessage("chatView.intent.permissionDenied"), Notifications.Type.ERROR).show()`; button stays enabled. (4) If draft is gone (TTL-reaped or already saved): summary line replaced with `chatView.intent.draftExpired`, button `setEnabled(false)`. |
| Conversation switch / "New chat" | `ChatPanelFragment.clearMessageList()` (existing) | All `<div class="ai-agent-intent-confirm">` siblings are removed alongside Phase 13.1's `<div class="ai-agent-attachment-notice">` siblings (existing `messageListSlot.getElement().removeAllChildren()` pass already handles both). Card-row state is preserved (Auto remains the default selection). |

### State transitions

```
[card-row hidden]   ──registry has ≥1 eligible intent──▶ [card-row visible, Auto selected]
[Auto selected]     ──card click named-intent──────────▶ [named-intent selected]
[named-intent sel]  ──card click Auto──────────────────▶ [Auto selected]
[named-intent sel]  ──send turn dispatched─────────────▶ [Auto selected (auto-reset, response still streaming)]
[no draft yet]      ──tool-result open_form_with_draft─▶ [confirm-row appended in messageListSlot]
[confirm-row]       ──click button, permitted─────────▶ [detail view opens, prefilled, draft kept until Save]
[confirm-row]       ──click button, denied─────────────▶ [confirm-row unchanged + ERROR toast]
[confirm-row]       ──click button, draft expired──────▶ [confirm-row: summary→draftExpired, button disabled]
[confirm-row]       ──new chat / clearMessageList─────▶ [confirm-row removed]
```

### Mobile / narrow-viewport behavior

Out of scope for v1.1 — same desktop-primary stance as Phase 13.1. The `<radioButtonGroup themeNames="horizontal">` reflows to multiple lines below ~600px viewport via Vaadin's native flex-wrap, so functional usability degrades gracefully without dedicated breakpoints.
