<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build-time → runtime | A wrong FQCN in `@JmixModule(dependsOn=)` is caught at compile (Class literal), not at runtime. |
| add-on → host app | Widening dependsOn affects host-app bean initialisation order; a cycle would manifest at `bootRun` startup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09-01 | Tampering | `@JmixModule(dependsOn=...)` array | mitigate | Array uses `.class` literals (compile-checked). Reviewer must see all 4 classes listed; `acceptance_criteria` greps enforce presence. |
| T-02-09-02 | Denial of Service | Module initialisation cycle | mitigate | Four target modules (data, security, eclipselink, flowui) have no known cycles with `com.vn.agent` in Jmix 2.8; plan 10's `@SpringBootTest` boot smoke test will fail loudly if a cycle is introduced. |
| T-02-09-03 | Elevation of Privilege | Role scanner runs before add-on package is on classpath | mitigate | Declaring `SecurityConfiguration.class` as a dependency guarantees Jmix's role registry is initialised *before* `com.vn.agent`'s `@ComponentScan` completes, so `@ResourceRole` / `@RowLevelRole` annotated interfaces in `com.vn.agent.security` are reliably registered. Verified empirically by plan 10 smoke test (asserts 3 roles present). |
| T-02-09-04 | Repudiation | Unnecessary `DataConfiguration` dep hides the real minimal set | accept | Research assumption A3 flags this as empirically-verifiable overhead. If plan 10 boot test passes with only Security + Eclipselink + Flowui, a follow-up phase can trim. Declaring it now is the safer default. |
